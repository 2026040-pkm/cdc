    cdc GitHub Actions — SSH 키 · self-hosted 러너 셋업

    GitHub Actions가 배포 대상 서버(230)에 SSH로 접속하기 위한 키페어를 만드는 것부터, 공개키 등록 · GitHub Secrets/Variables 등록 · self-hosted 러너(Windows 로컬 · Podman) · 연결 확인 워크플로(check-docker-host.yml) 실행까지 처음부터 끝까지 다룹니다.

    대상 서버 230 키 타입 ed25519 passphrase 없음 범위: keygen → 워크플로 실행

    00범위와 전제

    먼저 이 문서가 어디까지인지 못 박습니다. 다음 단계와 섞이면 키가 잘못 배치됩니다.

    이 문서에서 하는 것

    • 230 서버에서 ed25519 키페어 생성
    • 개인키 · 공개키 파일 위치와 권한 확인
    • 공개키를 접속 계정 authorized_keys 에 등록 (04)
    • 개인키를 클립보드로 복사(붙여넣기 준비)
    • GitHub Secret SSH_USER · SSH_PRIVATE_KEY, Variable DOCKER_HOST_IP 등록 (06)
    • self-hosted 러너를 Windows PC 의 Podman 에 띄우기 (07)
    • 연결 확인 워크플로 작성 · 실행 (08)
    • 리눅스 서버 러너 방식 비교 · 조직 등록 · 저장소 변경 (10)

    이 문서에서 하지 않는 것 (다음 단계)

    • 실제 배포 잡(빌드 · 이미지 반영) 작성
    • push · PR 트리거 자동 실행
    • 리눅스 러너 실제 설치 · 검증 (10 은 방식 검토와 절차까지)

    전제

    230 서버에 SSH로 접속할 수 있는 계정이 있어야 하고, 그 계정 홈에 ~/.ssh 디렉터리를 만들 수 있어야 합니다. GitHub 저장소의 Settings 접근 권한(Secrets · Variables 등록)은 06 에서 필요합니다.

    01230 서버에 접속

    키는 배포 대상인 230에서 만듭니다. 개인키가 230 밖으로 새지 않도록, 이후 복사도 230 안에서 다룹니다.

    내 PC 터미널
    ssh <user>@230           # <user> 는 230의 접속 계정으로 교체

    230 이 IP/도메인이면

    230 자리에 실제 주소를 넣습니다. 예: ssh deploy@10.0.0.230, 포트가 22가 아니면 ssh -p 2222 deploy@10.0.0.230.

    02키페어 생성 (핵심)

    GitHub Actions는 대화형 입력을 못 하므로 passphrase 없이(-N "") 만듭니다. 키 파일은 기본 id_ed25519 대신 용도가 드러나는 이름(gha_deploy)을 씁니다.

    230 서버 안
    ssh-keygen -t ed25519 -C "github-actions-deploy" -f ~/.ssh/gha_deploy -N ""

    옵션이 하는 일:

    옵션의미
    -t ed25519키 알고리즘. RSA보다 짧고 안전하며 GitHub Actions에서 표준으로 쓰임
    -C "..."키에 붙는 주석(라벨). 어느 용도의 키인지 식별용 — 접속에는 영향 없음
    -f ~/.ssh/gha_deploy키 파일 경로·이름. 개인키 = 이 경로, 공개키 = 뒤에 .pub
    -N ""passphrase를 비움. 자동화(무인 접속)에 필수 — 프롬프트가 뜨지 않음

    주의

    같은 경로에 파일이 이미 있으면 덮어쓸지 물어봅니다. 기존 배포 키를 실수로 덮어쓰면 그 키를 쓰던 접속이 전부 끊깁니다. -f 이름을 확인하고 진행하십시오.

    03생성 결과 확인

    파일 두 개가 올바른 권한으로 생겼는지 봅니다. 개인키 권한이 느슨하면 SSH가 키를 거부합니다.

    1
    파일 두 개
    gha_deploy(개인키) · gha_deploy.pub(공개키)
    2
    개인키 권한
    600(소유자만 읽기/쓰기)이어야 함
    3
    .ssh 권한
    디렉터리는 700
    230 서버 안 — 확인
    ls -l ~/.ssh/gha_deploy*
# 권한이 다르면 바로잡기
chmod 700 ~/.ssh
chmod 600 ~/.ssh/gha_deploy

    정상 출력 예

    -rw------- 1 deploy deploy 411 ... gha_deploy
    -rw-r--r-- 1 deploy deploy 100 ... gha_deploy.pub

    04공개키 등록 (authorized_keys)

    ssh-keygen 은 파일 두 개를 만들 뿐 어디에도 등록하지 않습니다. 공개키를 접속 계정의 ~/.ssh/authorized_keys 에 넣어야 그 개인키로 로그인됩니다. 이 단계를 빠뜨리면 키가 멀쩡해도 워크플로가 Permission denied (publickey,password) 로 실패합니다.

    실제로 난 장애

    230 에서 키를 만들고 개인키를 SSH_PRIVATE_KEY 에 넣었지만 공개키 등록을 빠뜨려 check-docker-host 가 아래처럼 실패했습니다. 러너 연결·네트워크·키 형식은 모두 정상이었고, 아래 한 줄로 해결됐습니다. 
    Warning: Permanently added '192.168.122.230' (ED25519) to the list of known hosts.
***@192.168.122.230: Permission denied (publickey,password).
Error: Process completed with exit code 255.

    A. 등록 (핵심)

    반드시 SSH_USER 로 쓸 계정(예: sit-ml)으로 로그인해서 실행합니다.

    230 서버 안 — SSH_USER 계정으로
    cat ~/.ssh/gha_deploy.pub >> ~/.ssh/authorized_keys
    기호동작
    >>파일 끝에 추가. 기존 키는 그대로 두고 새 키가 마지막 줄로 붙음. 파일이 없으면 새로 만듦
    >덮어쓰기. 기존 키가 전부 지워져 그 키로 들어오던 접속이 끊김 — 쓰지 않음

    authorized_keys 는 한 줄에 키 하나입니다. 여러 줄이 있어도 sshd 가 전부 확인합니다.

    B. 안전하게 넣기 (권장)

    기존 파일 마지막 줄에 줄바꿈이 없으면 새 키가 그 줄 뒤에 붙어 두 키가 함께 깨집니다. 같은 명령을 두 번 돌리면 같은 키가 두 줄 들어갑니다. 아래는 둘 다 막습니다.

    230 서버 안 — SSH_USER 계정으로
    # 마지막 줄바꿈이 없으면 먼저 붙인다
[ -s ~/.ssh/authorized_keys ] && [ -n "$(tail -c1 ~/.ssh/authorized_keys)" ] && echo >> ~/.ssh/authorized_keys
# 이미 있으면 건너뛰고, 없을 때만 추가
grep -qF "$(cat ~/.ssh/gha_deploy.pub)" ~/.ssh/authorized_keys 2>/dev/null || cat ~/.ssh/gha_deploy.pub >> ~/.ssh/authorized_keys

    C. 권한 정리

    sshd 의 StrictModes(기본 켜짐)는 홈 · ~/.ssh · authorized_keys 중 하나라도 그룹이나 다른 사람이 쓸 수 있거나 소유자가 본인이 아니면 그 파일을 무시합니다. 남이 자기 공개키를 끼워 넣어 이 계정으로 들어오는 걸 막기 위해서입니다.

    230 서버 안 — SSH_USER 계정으로
    chmod go-w ~
chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys
ls -ld ~ ~/.ssh ~/.ssh/authorized_keys     # 그룹·기타 자리에 w 가 없고 소유자가 본인이면 OK

    D. 다른 계정으로 키를 만들었다면

    예를 들어 root 로 키를 만들었는데 SSH_USER 는 sit-ml 이면, 키를 다시 만들지 말고 공개키만 sit-ml 쪽에 넣습니다. 소유자를 바꾸지 않으면 C 의 이유로 무시됩니다.

    230 서버 안 — root / sudo
    sudo mkdir -p /home/sit-ml/.ssh
sudo sh -c 'cat /root/.ssh/gha_deploy.pub >> /home/sit-ml/.ssh/authorized_keys'
sudo chown -R sit-ml:sit-ml /home/sit-ml/.ssh
sudo chmod 700 /home/sit-ml/.ssh && sudo chmod 600 /home/sit-ml/.ssh/authorized_keys

    E. 등록 확인

    ① 지문 비교 — 개인키 지문이 authorized_keys 목록 안에 있으면 짝이 맞습니다.

    230 서버 안 — SSH_USER 계정으로
    ssh-keygen -lf ~/.ssh/gha_deploy            # 256 SHA256:AbCd... github-actions-deploy (ED25519)
ssh-keygen -lf ~/.ssh/authorized_keys       # 위 SHA256 값이 이 목록에 있어야 함

    ② 워크플로와 같은 조건으로 자기 자신에게 접속 — 비밀번호를 묻지 않고 계정 이름이 나오면 성공입니다.

    230 서버 안 — SSH_USER 계정으로
    ssh -i ~/.ssh/gha_deploy -o BatchMode=yes -o StrictHostKeyChecking=accept-new sit-ml@localhost whoami
    결과뜻 · 조치
    sit-ml짝이 맞음. 05 로 넘어가 개인키를 시크릿에 넣음
    Host key verification failed 키 문제가 아님. 처음 접속하는 호스트라 확인 질문이 필요한데 BatchMode 가 질문을 막은 것. -o StrictHostKeyChecking=accept-new 를 붙이면 됨
    Permission denied (publickey,...) 공개키 미등록(A) · 권한(C) · 다른 계정에 등록(D) 중 하나. 이유는 서버 로그에 나옴: sudo journalctl -u ssh -n 30 --no-pager (bad ownership or modes 면 C)

    05개인키 복사 (붙여넣기 준비)

    06 에서 개인키 전체를 GitHub 시크릿 SSH_PRIVATE_KEY 에 붙여넣습니다. 환경에 맞는 방법 하나를 고릅니다. 줄바꿈과 마지막 줄 개행까지 그대로 복사되어야 파싱 오류가 없습니다.

    A. 헤드리스 서버 → 내 PC에서 바로 뽑기 (권장)

    230에 클립보드 도구가 없어도, 내 PC(Windows)에서 SSH로 읽어 Windows 클립보드에 넣습니다.

    내 PC (PowerShell)

    B. 230에 GUI/클립보드 도구가 있을 때

# xclip 이 없으면

    C. 화면에 출력해서 수동 복사

    복사 범위

    -----BEGIN OPENSSH PRIVATE KEY----- 줄부터 -----END OPENSSH PRIVATE KEY----- 줄까지, 줄바꿈 그대로 전부 복사합니다. 중간 줄을 빠뜨리거나 공백을 넣으면 키가 깨집니다.

    06GitHub Secrets · Variables 등록

    워크플로가 쓸 값 세 개를 저장소에 넣습니다. 숨겨야 하는 값은 Secret, 숨길 필요 없는 설정값은 Variable 로 나눕니다.

    종류이름값 (예)워크플로에서 읽는 법
    SecretSSH_USERsit-ml${{ secrets.SSH_USER }}
    SecretSSH_PRIVATE_KEY05 에서 복사한 개인키 전체${{ secrets.SSH_PRIVATE_KEY }}
    VariableDOCKER_HOST_IP192.168.122.230${{ vars.DOCKER_HOST_IP }}

    Secret

    • 등록 뒤 값을 다시 볼 수 없음 — 덮어쓰기만 가능
    • 로그에 찍히면 *** 로 가려짐
    • 포크에서 온 PR 워크플로에는 전달되지 않음

    Variable

    • 값이 화면·로그에 그대로 보임
    • IP · 포트 · 경로 같은 설정값용
    • 언제든 열어 보고 고칠 수 있음

    07self-hosted 러너 셋업 (Windows 로컬 · Podman)

    230(192.168.122.230)은 사설 IP라 GitHub 호스티드 러너가 닿지 못합니다. 230에 닿는 사내 PC에 러너를 띄워 워크플로(runs-on: self-hosted)를 거기서 돌립니다. 지금은 Windows PC의 Podman 컨테이너 방식만 다룹니다.

    구성

    • 저장소 2026040-pkm/cdc (구 pkm0817/cdc)
    • 러너 이름 cdc-pc, 라벨 self-hosted, Linux, X64, podman
    • 이미지 myoung34/github-runner:ubuntu-jammy + Somansa 루트 CA
    • 잡의 docker 명령 → podman 머신 rootless 소켓

    파일 위치 util/github-runner/

    • docker-compose.yml — 러너 서비스
    • Dockerfile — 사내 루트 CA 신뢰
    • somansa-root-ca.crt — Windows 인증서 저장소에서 내보낸 CA (git 제외)
    • .env.example → .env (토큰, git 제외)

    7-1. 전제 확인

    Podman 머신이 떠 있고, podman compose 가 동작하며, 머신 안에서 230:22 로 나가지는지 봅니다.

    내 PC (PowerShell)
    podman machine list                      # podman-machine-default 가 Running
podman compose version                   # Docker Compose version ... 이 나오면 OK
podman machine ssh "timeout 3 bash -c '</dev/tcp/192.168.122.230/22' && echo SSH_OK"

    러너 이미지는 Linux

    GitHub의 New self-hosted runner 화면에서 고른다면 Linux · x64 입니다. Podman은 Windows 위의 리눅스 VM 에서 컨테이너를 돌리므로 Windows 옵션이 아닙니다. 이 문서 방식은 그 화면의 명령을 직접 치지 않고 컨테이너가 등록까지 합니다.

    7-2. 토큰(PAT) 준비

    러너가 스스로 등록 토큰을 받아 오도록 PAT를 씁니다. 재시작해도 다시 등록할 필요가 없습니다.

    종류권한
    Fine-grained PAT (권장)저장소 2026040-pkm/cdc 만, Administration = Read and write
    Classic PATrepo 스코프

    토큰 주인 = 저장소 관리자

    PAT 를 만든 계정이 그 저장소의 admin 이어야 합니다. 계정 이름이 바뀐 저장소는 API 조회는 옛 이름으로도 되지만 러너 등록은 리다이렉트를 따르지 않아 404 가 납니다. REPO_URL 은 반드시 현재 이름 (https://github.com/2026040-pkm/cdc)으로 적습니다.

    7-3. 사내 루트 CA 내보내기

    사내망은 Somansa SSL 검사가 github.com · *.actions.githubusercontent.com 인증서를 다시 서명합니다. 컨테이너가 이 CA 를 모르면 등록이 # Authentication 에서 멈춥니다. 이 파일은 공개 저장소에 사내망 정보를 드러내지 않도록 .gitignore 로 빠져 있으니, 러너를 띄우는 PC 마다 한 번 내보냅니다.

    내 PC (PowerShell) — util\github-runner 에서
    $c = Get-ChildItem Cert:\LocalMachine\Root | Where-Object Subject -like '*Somansa Root CA*' | Select-Object -First 1
$pem = "-----BEGIN CERTIFICATE-----`n" + [Convert]::ToBase64String($c.RawData, 'InsertLineBreaks').Replace("`r`n", "`n") + "`n-----END CERTIFICATE-----`n"
[IO.File]::WriteAllText("$PWD\somansa-root-ca.crt", $pem)
    Dockerfile
    FROM docker.io/myoung34/github-runner:ubuntu-jammy

COPY somansa-root-ca.crt /usr/local/share/ca-certificates/somansa-root-ca.crt
RUN update-ca-certificates

# JS 액션(actions/checkout 등)의 node 는 시스템 저장소를 보지 않는다.
ENV NODE_EXTRA_CA_CERTS=/usr/local/share/ca-certificates/somansa-root-ca.crt

# 사설 IP 라 GitHub 호스팅 러너에서는 닿지 않으므로 self-hosted 러너에서 돈다.
#
# 필요한 저장소 Secrets
#   SSH_USER         : 접속 계정
#   SSH_PRIVATE_KEY  : 그 계정의 개인키 (PEM 전체)
# 선택 Variables
#   DOCKER_HOST_IP   : 기본값 확인할 서버 IP

name: check-docker-host

on:
  workflow_dispatch:

jobs:
  docker-ps:
    runs-on: self-hosted
    timeout-minutes: 5
    env:
      HOST: ${{ vars.DOCKER_HOST_IP }}
    steps:
      - name: SSH 키 준비
        shell: bash
        run: |
          mkdir -p ~/.ssh
          printf '%s\n' "${{ secrets.SSH_PRIVATE_KEY }}" > ~/.ssh/ci_key
          chmod 600 ~/.ssh/ci_key

      - name: docker ps
        shell: bash
        run: |
          ssh -i ~/.ssh/ci_key \
              -o StrictHostKeyChecking=no \
              -o UserKnownHostsFile=/dev/null \
              -o ConnectTimeout=10 \
              -o BatchMode=yes \
              "${{ secrets.SSH_USER }}@${HOST}" \
              'hostname && docker ps'

      - name: 키 정리
        if: always()
        shell: bash
        run: rm -f ~/.ssh/ci_key

    10-1. 결론 먼저

    • 잡에서 docker 가 필요하면 러너 계정을 docker 그룹에 넣음

    컨테이너 방식이 맞는 경우

    • 잡마다 깨끗한 환경이 필요할 때 (EPHEMERAL=true)
    • 한 서버에 러너 여러 개를 서로 격리해 돌릴 때

    10-2. 러너를 컨테이너로 올릴 때 문제점

    작업 폴더 경로 어긋남러너 안의 docker 명령은 호스트 dockerd 가 받으므로 -v 경로를 호스트 기준으로 해석함. 컨테이너 액션 · services: · container: 에서 빈 폴더가 붙거나 실패작업 폴더를 호스트와 같은 경로로 마운트. /tmp 는 피함 (tmpfs 이거나 부팅 때 비워짐 — 9-3 의 장애)
    소켓 = 호스트 rootdocker.sock 을 넘기면 잡 안에서 docker run -v /:/host 로 호스트 전체 접근 가능. 공개 저장소면 포크 PR 도 해당외부 기여자 승인 필수(07 공개 저장소 주의), 러너 전용 서버
    파일 소유권myoung34 이미지는 root 로 돎. 잡 컨테이너가 만든 파일도 root 소유라, 러너를 일반 계정으로 바꾸면 _work 정리가 Permission deniedroot 유지 또는 잡 끝에 정리 단계
    등록 정보 · 토큰RUNNER_TOKEN 은 1시간 1회용. 볼륨을 지우고 다시 올리면 같은 이름의 offline 러너가 GitHub 에 남음PAT 또는 GitHub App, 볼륨 유지, 남은 러너는 화면에서 삭제
    자동 업데이트러너가 컨테이너 안에서 스스로 업데이트하고, 컨테이너를 새로 만들면 이미지 버전으로 돌아감. 너무 오래된 버전은 잡을 못 받음자동 업데이트를 두거나, 끄면 이미지를 주기적으로 다시 빌드
    네트워크잡이 띄운 컨테이너는 러너의 형제라 러너 안의 localhost 로 닿지 않음. 사내 CA 는 잡 컨테이너에도 필요같은 docker 네트워크 · 컨테이너 이름으로 접속, 잡 이미지에도 CA
    도구 · 디스크이미지에 JDK · Gradle · Node 가 거의 없어 setup-* 액션이 매번 내려받음. 잡 이미지 · 빌드 캐시가 호스트에 쌓임/opt/hostedtoolcache 볼륨, docker system prune 주기 실행
    동시 실행 · 종료러너 하나 = 잡 하나. 잡 도중 docker stop 하면 그 잡은 실패러너마다 이름을 다르게, stop_grace_period 넉넉히

    10-3. docker 빌드는 어느 자원을 쓰나

    소켓 마운트 방식에서 러너 컨테이너에 있는 건 docker CLI 뿐입니다. 빌드와 컨테이너 실행은 호스트 dockerd 가 합니다. CLI 가 빌드 컨텍스트(소스)를 소켓으로 보내므로 docker build 는 경로를 맞추지 않아도 됩니다.

    10-4. 직접 설치 · 등록

    저장소(또는 조직) → Settings → Actions → Runners → New self-hosted runner → Linux · x64 화면의 다운로드 명령을 받은 뒤 아래처럼 등록합니다.

    리눅스 서버 (러너 전용 계정)
    # 저장소 러너
./config.sh --url https://github.com/2026040-pkm/cdc --token <등록 토큰> \
            --name cdc-linux --labels linux,x64 --unattended

# systemd 서비스로 등록 · 시작 (재부팅 자동 시작)
sudo ./svc.sh install
sudo ./svc.sh start
sudo ./svc.sh status

# 잡에서 docker 가 필요할 때만
sudo usermod -aG docker $(whoami) && sudo ./svc.sh stop && sudo ./svc.sh start

    등록 토큰은 1시간짜리 1회용

    등록이 끝나면 필요 없지만, 문서 · 스크립트 · 커밋에는 넣지 않습니다. 사내망 서버라면 7-3 과 같은 이유로 사내 루트 CA 를 서버 OS 저장소(update-ca-certificates)에 넣고, 러너 폴더의 .env 에 NODE_EXTRA_CA_CERTS=<CA 경로> 를 적은 뒤 서비스를 재시작합니다.

    10-6. 다른 저장소로 옮기기 (재등록)

    등록 정보는 저장소 하나에 묶여 있어 URL 만 고쳐서는 안 됩니다. 해제 → 새 저장소로 등록 이고, 설치 파일은 그대로 써서 5분 정도면 끝납니다.

    직접 설치
    sudo ./svc.sh stop
sudo ./svc.sh uninstall
./config.sh remove --token <제거 토큰>

./config.sh --url https://github.com/<계정>/<새 저장소> \
            --token <새 등록 토큰>
sudo ./svc.sh install && sudo ./svc.sh start
    컨테이너 (myoung34)
    docker compose down
# 볼륨을 안 지우면 예전 저장소로 다시 붙음
docker volume rm github-runner_runner-data
# .env / compose 의 REPO_URL 을 새 저장소로
docker compose up -d

    • 놓치기 쉬운 것: 컨테이너 볼륨 삭제, 예전 저장소에 남은 offline 러너 삭제
