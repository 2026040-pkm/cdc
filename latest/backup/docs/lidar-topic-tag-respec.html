    LiDAR 토픽·메시지·태그화 재정립

    지금까지는 latest/docs/lidar-data-path.html(cdc PoC 실측)을 기준으로 개발했다. 이 문서는 ocean-inshop-process/docs/필드인터페이스정의서.md(v0.3, 2026-09-22)를 기준으로 삼아 실제로 나올 토픽·메시지 스키마·태그화 규칙을 다시 정리하고, cdc가 지금 하는 것과 무엇이 다른지 못박는다.

    기준 문서: 필드 인터페이스 정의서 v0.3 교차 검증: intersyslink-v4 Mqtt.Agent 소스 미결정: 상태 토픽에 device_id 포함 여부 정리 2026-09-22

    00범위와 배경

    두 문서가 서로 다른 시점에 다른 목적으로 자랐다 — 지금 합치지 않으면 계속 어긋난다.

    이 문서가 정리하는 것

    • 조립·선행의장 3계열(상태·실적·산출물)의 최종 토픽 패턴
    • 채널별 메시지(JSON) 스키마 — 필드 인터페이스 정의서 v0.3 그대로
    • 메시지가 Mqtt.Agent 안에서 태그(TagId·value·changedAt)로 바뀌는 규칙
    • cdc PoC가 지금 쓰는 것과의 차이 — 무엇을 재등록해야 하는지

    이 문서가 정리하지 않는 것

    • Engine 이후 ISL DB Provider·판별 서비스·Hot Data DB 적재 스키마(필드 인터페이스 정의서 범위 밖, §5.3)
    • 선행도장 Modbus 태그(§7) — LiDAR 메시지형 채널만 다룬다
    • 대수·shop/bay 목록 확정(§9.1 — 현장 레이아웃 미확정)

    전제

    본 문서가 인용하는 토픽·스키마는 필드 인터페이스 정의서의 확정 제안이다(ISL 벤더 합의 전, §9.2). 상태 토픽의 device_id 포함 여부(§06)는 그 문서도 아직 열어 둔 질문이며, 이 문서에서 결론을 내리지 않는다.

    02토픽 3계열 — 최종본(실제 구현 기준, 2026-09-22)

    토픽이 곧 TagId 가운데 마디다. 아래는 util/mqtt-lidar-sim/lidar-sim.cs가 실제로 발행하는 6개 그대로다(소스 확인) — 필드 인터페이스 정의서 v0.3 문면(장비마다·shop/bay마다 별도 토픽)과는 다르다. 그 차이는 이 절 하단과 §06에서 다룬다.

    채널토픽(zone당 1개, 총 6개)id 소스태그 분리 단위태그 수
    상태ot/device/assembly/status
    ot/device/outfitting/status    		device.Id장비별350 (조립 210 + 의장 140)
    실적ot/sensor/assembly/actual
    ot/sensor/outfitting/actual    		device.Id장비별350
    산출물ot/pipeline/assembly/artifact
    ot/pipeline/outfitting/artifact    		{device.Id}-{artifactType}장비+종류별1,050 (350 × 3종)

    토픽 6개는 zone(조립·의장) × 채널(상태·실적·산출물)로만 갈린다 — device_role·device_id·shop·bay·stage는 전부 payload와 등록 CSV의 deviceId 열로 옮겨졌다. 등록 CSV·구독은 zone당 1개 문자열만 있으면 되고(§05), 그 안에서 몇 개의 태그가 나올지는 등록 행 수(위 "태그 수" 열)가 정한다.

    필드 인터페이스 정의서 v0.3 문면과는 토픽·그레인 둘 다 다르다

    스펙 문면은 ot/device/{zone}/{device_role}/{device_id}/status(장비마다 별도 토픽)와 ot/sensor·pipeline/{zone}/{shop}/{bay}/…(shop/bay마다 별도 토픽, 실적은 태그도 shop×bay 단위 1개를 의도)를 제안한다 — 위 표와는 토픽 개수·그레인이 다 다르다. 어느 쪽이 맞는지는 아직 벤더 확인 전이라 "제안" 단계다(§9.2). 상세 비교는 §06.

    실적 payload는 v0.2와 다르다 — stage가 빠졌다

    v0.2까지는 ot/sensor/{stage}/actual 류로 공정 단계(stage)가 토픽·payload에 있었다. v0.3에서 뺐다 — LiDAR는 형상 대조로 진척률만 낼 뿐 지금 보는 대상이 어느 공정 단계인지는 판별하지 못하기 때문이다 (워크오더·공정 일정과 대조해야 아는 정보). stage는 판별 서비스가 사후에 매긴다(필드 인터페이스 정의서 §4.3·§9.4).

    05태그 등록 요구사항 (선등록 모델)

    등록 전에는 publish해도 수집되지 않는다 — 순서를 틀리면 데이터가 조용히 사라진다. 그리고 등록 행 수와 실제 구독 토픽 수는 다르다 — 이 차이를 이용하는 게 §06·§07의 핵심이다.

    단계내용
    1. Device Registry 등록장비 신규 설치·교체 시 registry에 행 추가(device_id 확정) — 모델·벤더·시리얼은 여기서만 관리(§4.1·§8)
    2. Engine 태그 등록registry 행에서 파생되는 TagId를 Engine에 등록. 등록 파일은 한 파일 = 한 토픽, 컬럼은 topic,qos,tagMode,deviceId,field,dataType,monitoring — topic 열은 여러 행에서 같은 문자열을 공유해도 된다(장비마다 deviceId만 다르게)
    3. Agent 수집 시작Agent가 갱신된 수집 대상 목록을 받아 해당 토픽 구독(또는 이미 구독 중인 토픽의 필터 갱신)을 시작 — 실제 SUBSCRIBE는 등록 행 수가 아니라 고유 topic 문자열 수만큼만 나간다

    토픽 문자열을 등록 행마다 다르게 쓰면 등록 행 수만큼 SUBSCRIBE가 나간다

    ConfigDtos.ReadTopics가 HashSet<string> seen으로 동일 topic 문자열을 자동 dedup하지만(소스 확인), 애초에 등록 행마다 topic 문자열이 다르면(예: device_id·device_role을 토픽에 박은 경우) dedup될 게 없다. MqttRuntimeController가 foreach + await SubscribeAsync로 순차 구독하므로, 토픽이 많을수록 기동·재연결 시간이 그만큼 늘어난다. 실제로 몇 개나 차이 나는지는 message.md에서 두 설계를 문자열로 다 펼쳐서 셌다 — 상태·실적·산출물 합쳐 Design A(스펙 문면 그대로) 378개 vs Design B(공유 토픽) 6개. §06의 표는 그 결론을 반영한다.

    TagId 100자 상한

    Engine의 TagCatalogId 컬럼 제약이자 MqttTagId.MaxLength다. 산출물 채널은 종류 접미사(-TRANSFORMATION_MATRIX 등)까지 붙어 여유가 가장 적다 — shop·bay 이름이 길어지면 초과할 수 있다. device_id·device_role을 토픽에 또 넣으면(§4.3 스펙 문면) TagId 안에 같은 값이 두 번 들어가는 구간이 생겨({id}.{topic}.{field}의 id와 topic 양쪽에) 여유가 더 줄어든다 — 상태 채널 기준 약 59자 → 약 73자.

    07열린 질문 — 결정하고 시작해야 할 것

    둘 다 §04·§06에서 나온, 아직 어느 쪽으로도 확정되지 않은 설계 갈림길이다.

    ① 상태 토픽에 device_id를 넣을 것인가

    스펙(§02)은 장비마다 별도 토픽(~350개)을 요구한다. 반면 cdc PoC는 Mqtt.Agent 소스로 직접 확인한 사실 — MonitoredTagSet이 메시지의 payload id + 토픽 조합으로 TagId를 재구성해 필터링하므로, 같은 토픽을 여러 장비가 공유해도 등록 CSV에 장비마다 한 행(같은 topic, 다른 deviceId)을 넣으면 Engine에서 정확히 장비별로 분리된다 — 는 방식으로 토픽을 2개(zone별)로 줄였고 실제 ISL v4 Engine에서 350/350 태그 분리를 검증했다. 벤더가 이 방식을 프로덕션에서도 보장하는지 확인 전까지는 "제안"에 머문다(필드 인터페이스 정의서 §9.2).

    ② 실적·산출물 채널의 payload id 자리를 무엇으로 채울 것인가 — cdc는 이미 답을 냈다

    해결(실무적으로): device.Id를 그대로 쓴다. shop/bay 합성 id를 새로 만들지 않고, 이미 있는 장비 id를 재사용해서 §04의 "id 없으면 태그가 안 만들어지는" 문제를 피해 갔다 (lidar-sim.cs 소스 확인, §06).
    그래서 새로 남는 질문: 이게 v0.3 스펙의 "shop/bay 채널 태그" 의도(§4.3·§5.1)를 포기하고 장비별 그레인으로 가겠다는 뜻인가? 장비별로 남으면 등록 수가 스펙 의도(14)보다 훨씬 많아지지만(실적 350·산출물 1,050), Engine에서 장비 단위 조회가 가능하다는 이점은 그대로 유지된다 — 결정 안 하면 스펙 문서와 실제 등록 수가 계속 어긋난 채로 간다.

    그 외 필드 인터페이스 정의서 §9의 미확정 항목(shop/bay 목록, LiDAR 대수 출처 불일치, PCD 스토리지 정책 등)은 본 문서 범위에서 반복하지 않는다 — 원문을 참고한다.
