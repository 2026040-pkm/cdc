    00결론 — RDB 와 TSDB 가 각각 맡는 것

    권고안

    RDB 는 "지금 값과 업무 목록", TSDB 는 "받은 순서대로 쌓이는 이력" 입니다. 세 채널이 같은 모양입니다 — 키로 찾는 현재 행 1개(RDB) + 수신 이벤트마다 1행(TSDB). 상태는 최신값 + 이력, 실적과 산출물은 스캔에 묶인 목록 + 이력이며 두 행은 같은 트랜잭션에 씁니다. 태그마다 표를 만들거나 TSDB 만으로 업무 표를 대신하는 안은 제외했습니다 — 두 번 쓰는 근거는 §02 에 있습니다.

    status 최신값은 장비가 아니라 태그 기준입니다

    같은 장비가 여러 그룹에 등록될 수 있어 최신 상태 키는 tag_key 입니다. 장비당 한 상태가 필요한 화면은 승인된 대표 status 태그를 선택합니다. 수집원이 서로 다른 값을 임의로 합치지 않습니다.

    actual 에는 stage 를 다시 만들지 않습니다

    최신 발행기에 stage 가 없습니다. 이후 판별 서비스가 만든다면 별도 결과 표에 판별 출처 · 시각을 저장합니다. START / COMPLETE 는 공정 이름이 아닙니다. 진척률은 정정되거나 새 주기에서 낮아질 수 있으므로 GREATEST 로 고정하지 않습니다.2

    키의 전제: 같은 scan_id 안에서 동일 event_type 의 확정 결과는 하나로 봅니다. 동일 스캔의 PROGRESS 가 여러 번 갱신되는 실제 계약이라면 source revision 을 키에 추가해야 합니다. 같은 키로 다른 내용이 오는 경우를 조용히 덮어쓰지 않는 이유입니다.

    artifact 가 actual 보다 먼저 올 수 있습니다

    먼저 scan 연결 행을 만들고 artifact 를 저장합니다. scanned_at 은 actual 도착 시 채웁니다. 같은 스캔의 장비 · 위치 · 블록이 다르면 덮어쓰지 않고 격리합니다. 비세그먼트의 segment_id=null 은 segment_key='' 로 정규화해 NULL 이 UNIQUE 를 통과하는 문제를 피합니다.7

    등록 PCD 1개 + 행렬 1개 + 세그먼트 10개는 12행입니다. PCD 본체는 외부 스토리지에, URI · 크기 · 체크섬은 DB 에 둡니다. 행렬은 숫자 16개라 배열로 저장합니다. 메타 수신과 파일 검증 완료는 file_state 로 구분합니다.

    왜 같은 이벤트를 두 번 쓰는가 — RDB 행과 TSDB 행은 다른 질문에 답합니다

    같은 PostgreSQL 안의 두 스키마라 한 트랜잭션에 함께 커밋되고 한쪽만 남는 상태가 없습니다. 두 행은 복제본이 아니라 변경 · 유일성 · 수명 · 전달 이 다른 행입니다. 어느 한쪽만 두면 다른 쪽 성질을 잃습니다.

    TSDB 만으로 업무 표를 대신하지 않는 이유

    하이퍼테이블 유일 키에는 시간이 들어가야 해서 "같은 스캔의 같은 산출물이 두 번" 을 DB 가 막지 못하고, 압축 뒤에는 file_state · 정정 갱신이 비싸며, 압축 청크는 CDC → HANA 대상이 아닙니다. 이 셋이 RDB 현재 행이 있어야 하는 이유이고, 반대로 605만 행/일의 DELETE 보관 정리와 시간 버킷 집계가 TSDB 이력이 있어야 하는 이유입니다.

    6개 등록 CSV 를 직접 세어 1,750행임을 확인했습니다. 기본 발행 가정에서 status 350행/s, actual 약 5.83행/s, artifact 70행/s 로 하루 약 3,024만 / 50.4만 / 604.8만 행입니다. 코드 주기의 산술값이며 처리 성능 실측이 아닙니다. status 는 이력 INSERT + 최신값 UPDATE, actual · artifact 는 RDB 1행 + TSDB 1행씩이라 INSERT 는 채널 행 수의 2배로 잡습니다. 이력 행에는 JSONB 원문이 없어 바이트 기준으로는 2배 미만입니다. 선택 표를 켜면 쓰기 · WAL 이 더 늘어납니다.

    파일 용량과 DB 용량은 분리합니다. DB 에는 메타만 보관합니다. RDB 는 키 수 × 실측 bytes/행 × 업무 보관 일수, TSDB 는 일 이벤트 수 × 실측 bytes/행 × 31일 을 따로 구해 더하고 WAL · 백업을 추가합니다. 압축 배수는 여기서 가정하지 않습니다.

    HANA 요구전달 대상의미
    최신 상태 + 실적 + 산출물status_current, scan, actual_result, artifact + 필요 마스터기본안. status 원본 전량 보장은 아님
    모든 status 원본도 필요위 대상 + 선택 status_event_buffer이력과 같은 트랜잭션으로 매 행 저장. 전달 완료 후 단기 정리
    압축된 TSDB 이력기본 대상에서 제외압축 청크 직접 전달은 커넥터 · 버전 별도 검증

    보존은 단순 max(event_time) 이 아니라 미전달 · 지연 · 격리가 없는 연속 완료 구간으로 판정합니다. RDB 보존 정리 DELETE 와 HANA 업무 삭제를 구분해야 합니다. 파일 삭제는 참조와 실제 스토리지 상태를 확인하며 DB TTL 만으로 파일이 지워지지 않습니다.
