02. 어떤 구조인가

상태는 최신값 + 이력, 실적 · 산출물은 스캔별 목록입니다

03. 실제 스키마

테이블 8개, 조인 키는 등록부 · 장비 · 스캔 셋뿐입니다

PK 주황 · FK 청 · 점선은 컬럼 복사

선택 표 3개는 필요할 때만 켭니다

tsdb.actual_metric_history (진척률 시간 집계) · tsdb.artifact_event_history (파일 상태 변화) · rdb.status_event_buffer (status 원본 전량 CDC). 켜면 같은 트랜잭션에 쓰기가 늘어납니다.

ingest_reject 만 FK 가 없습니다 — 검증에 실패한 원문을 그대로 두고 조사하는 표라서 다른 표에 묶지 않습니다. 전체 DDL 은 격리 DB (PostgreSQL 17.11 · TimescaleDB 2.29.2) 에서 통과했습니다.7

HotDB 기준 LiDAR RDB · TSDB 스키마
발표자 노트tag_key 는 긴 TagId(80자대) 를 매 행 반복 저장하지 않으려는 숫자 키. edge_group_id + tag_id 가 등록부의 유일 키.
03. 실제 스키마

표 하나가 맡는 "한 행" 을 먼저 정했습니다

한 행의 정의가 곧 기본 키입니다
rdb.device사업장의 장비 1대PK (site, device_id)
rdb.tag_catalog등록 CSV 의 태그 1개 · 원래 토픽 · 채널 · 종류PK tag_key · UQ (edge_group_id, tag_id)
rdb.status_current태그의 최신 상태 1행 · 화면 · 선택적 CDCPK tag_key
tsdb.status_history상태 측정 1건 · 6시간 청크 · 압축 대상PK (tag_key, event_time, event_key)
rdb.scan스캔 1회 · 장비 · 블록 · 위치 앵커PK (site, scan_id)
rdb.actual_result스캔의 이벤트 1건 · 진척률 · 신뢰도PK (site, scan_id, event_type)
rdb.artifact스캔의 산출물 1개 · 파일 메타 또는 행렬PK (site, scan_id, artifact_type, segment_key)
rdb.ingest_reject검증 실패 수신 1건 · 원문 · 사유PK reject_id · FK 없음

status 최신값은 장비가 아니라 태그 기준

같은 장비가 여러 그룹에 등록될 수 있어 키는 tag_key 입니다. 장비당 한 상태가 필요한 화면은 대표 status 태그를 고릅니다. 수집원이 값을 임의로 합치지 않습니다.

actual 에 stage 를 다시 만들지 않습니다

최신 발행기에 stage 가 없습니다. START · COMPLETE 는 공정 이름이 아닙니다. 진척률은 정정될 수 있어 GREATEST 로 고정하지 않습니다.2
HotDB 기준 LiDAR RDB · TSDB 스키마
발표자 노트비세그먼트 산출물의 segment_id=null 은 segment_key='' 로 정규화한다. NULL 은 UNIQUE 에서 서로 다르게 취급되어 중복이 통과하기 때문.
04. 데이터가 들어가는 법

태그 1개가 데이터 1건이 아닙니다

tagMode=raw · JSON 본문 전체가 태그 값

태그 ID 로 중복 제거하면 안 됩니다

세그먼트 10개가 같은 tagId · 같은 발생 시각으로 들어옵니다. (tag_id, changed_at) 도 고유 키가 아닙니다.1

그래서 산출물 키는 넷

site + scan_id + artifact_type + segment_key. 수신 배열의 항목마다 처리하고, 태그별 마지막 값 하나로 합치지 않습니다.

격리 DB 에서 확인

세그먼트 10개 + PCD + 행렬 = 12행 저장, 재전송 후에도 12행 유지, 중복 PCD 등록 거부.7
HotDB 기준 LiDAR RDB · TSDB 스키마
발표자 노트현재 tagMode=raw 에서는 온도 · 상태 · 진척률마다 별도 태그가 생기지 않는다. JSON 한 덩어리가 문자열 태그 값이다.
