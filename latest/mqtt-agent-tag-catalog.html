    MQTT 브로커에서 Mqtt.Agent 태그 생성까지

    EMQX 로 들어온 LiDAR MQTT 메시지가 Mqtt.Agent 안에서 태그(TagId · 값 · changedAt)로 접히는 규칙을 필드 단위로 정리한다. Engine 이후 NATS · Kafka · DB 경로는 범위 밖이며 §09 참고자료로 넘긴다.

    범위: EMQX → Mqtt.Agent 출처: nats-tag-stream · mqtt-lidar-sim · lidar-compare 미확정: 상태 주기 · Engine 가져오기 여부 정리 2026-09-22 · 재검증 2026-09-23

    AR시스템 구성도

    Field · OT · IT 레이어에 어떤 서비스가 있고 데이터가 어디로 흐르는지 한 장으로 본다. 이 문서는 그중 MQTT Broker → 조립·의장 Agent 구간을 다룬다.

    출처: 시스템 아키텍쳐.drawio · "시스템 아키텍쳐" 페이지 (2026-09-22). 그림을 누르면 원본 크기로 열린다.

    00범위와 전제

    태그가 어디서 끝나는지를 먼저 그어야 카탈로그가 흩어지지 않는다.

    이 문서가 다루는 것

    • MQTT 토픽 · 메시지 봉투 (EMQX 수신 시점까지)
    • Mqtt.Agent 가 만드는 태그의 필드 대응표 (TagId · valueKind · value · changedAt)
    • 태그 등록 파일(CSV) 형식과 등록 누락 현황

    이 문서가 다루지 않는 것

    • Engine → NATS → Kafka Provider / Db.Provider → 소스 DB 경로 (docs/cdc/lidar-source-pipeline.html §05 이하)
    • 세 적재 경로(A·B·C) 비교 · 성능 수치 (src/lidar-compare/README.md)
    • TimescaleDB 스키마 · 보존 정책

    전제

    페이로드 규격 자체가 필드 정의서 §6.2~§6.4 의 제안 규격이며 ISL 벤더 합의 전 미확정이다. 아래 표의 "미확정" 칩이 붙은 값은 코드 기본값이지 합의값이 아니다.

    2026-09-22 재설계로 아래 토픽 예시가 바뀌었다 — 숫자는 이 문서에서 최신화했지만, 흐름·태그화 규칙 설명은 그대로 유효하다

    이 문서를 쓴 뒤 같은 날 util/mqtt-lidar-sim/lidar-sim.cs가 다시 짜였다. 실적 토픽은 ot/sensor/{stage}/actual(6개, stage 있음)에서 ot/sensor/{zone}/actual(2개, stage 없음)로, 산출물 토픽은 shop/bay마다 있던 14개에서 zone마다 2개로 줄었다 — 상태 토픽의 lidar 세그먼트도 빠졌다. 아래 §02·§03·§05·§06의 숫자·예시는 그 최종 형태로 고쳐 두었다. 최신 전체 그림·실제 코드 대조는 latest/docs/lidar-topic-tag-respec.html·latest/docs/message.md 를 본다.

    02토픽 카탈로그 — 6개

    토픽 이름이 곧 TagId 의 한 조각이 된다. 여기서 정한 문자열이 태그 생성까지 그대로 따라간다.

    채널토픽 패턴토픽 수실제 값주기토픽당 태그
    상태ot/device/{zone}/status2assembly · outfitting1초210 · 140
    실적ot/sensor/{zone}/actual2assembly · outfitting1분210 · 140
    산출물ot/pipeline/{zone}/artifact2assembly · outfitting1분630 · 420 (장비×3종)

    산출물 태그 수가 장비 수의 3배인 것은 장비 하나가 산출물 종류마다 다른 id 로 발행하기 때문이다(-REGISTERED_PCD · -TRANSFORMATION_MATRIX · -SEGMENTED_PCD). 발행기 기준 태그 총량은 6 토픽 · 1,750개다(상태 350 + 실적 350 + 산출물 1,050) — 상세는 §06.

    실적(actual) 채널 — stage 처리 현황

    실적 토픽 ot/sensor/{zone}/actual 에는 공정 단계(stage)가 없다. 빠뜨린 것이 아니라 2026-09-22 재설계에서 뺀 것이다.

    확정된 것

    • 토픽 · payload 어디에도 stage 가 없다 — 필드 인터페이스 정의서 v0.3 §4.3 · §6.3. LiDAR 는 형상 대조로 진척률만 낼 뿐 공정 단계(ARRANGEMENT · PROCESSING · INSPECTION · OUTBOUND)를 판별하지 못한다는 게 이유다. 공정 단계는 워크오더 · 공정 일정과 대조해야 알 수 있다.
    • 이 변경은 토픽 개수에 영향이 없다 — 개수는 zone(× shop × bay)으로만 정해지고 stage 는 애초에 곱하지 않았다. 대신 태그 등록 단위가 shop × bay × stage 에서 장비 단위로 바뀌어, stage 별 등록 누락(FITTING)도 함께 없어졌다.
    • payload 의 idempotency_key 도 {scan_id}:{stage}:{event_type} 에서 stage 가 빠졌다. 남은 구분은 event_type(START · PROGRESS · COMPLETE)이다.

    근거 위치와 남은 불일치

    • 발행기 커밋 e7f4ce4(2026-09-22) · 코드 주석 util/mqtt-lidar-sim/lidar-sim.cs 26–28행 · latest/backup/docs/message.md "실적(actual) 채널 — stage 처리 현황".
    • 원본 ocean-inshop-process/docs/필드인터페이스정의서.md 는 아직 v0.2(2026-09-02) 이고 §4.3 · §5.1 · §6.3 에 stage 가 남아 있다 — v0.3 반영 필요 미반영
    • 이미 구현된 조립공장뷰 FR-5 는 레거시 bayStage(송선 현공정 코드)로 공정 단계를 쓴다. 판별 서비스가 나중에 stage 를 만들면 둘 중 무엇을 쓸지 정해야 한다(정의서 §9.4).

    브로커 포트

    이 저장소 주변에 MQTT 를 받는 컨테이너가 셋이다. mqtt-emqx = 1884, mqtt-mosquitto = 1883, mqtt-nats = 1885. 기본값은 EMQX(1884)다.

    03메시지 봉투

    세 채널 모두 봉투 모양이 같다 — Agent 의 계약이 그 모양 하나만 받는다.

    Mqtt.Agent.Core.Domain.MqttPayloadParser 가 받는 형식 그대로, id 와 raw_payload 한 겹뿐이다. 필드 정의서의 중첩 객체(device_ids 등)는 브로커로 나갈 때 평탄화한다 — 중첩을 두면 나중에 tagMode=fields 로 바꿨을 때 키 이름이 달라지기 때문이다.

    아래 각 줄의 뜻은 실제 동작과 스펙 둘 다 적었다 — 스펙과 다름 이 붙은 줄에 마우스를 올리면 발치에 "실제 동작: … / 스펙: …" 형태로 뜬다. 스펙 원문은 ocean-inshop-process/docs/필드인터페이스정의서.md §6.2~§6.4 다(§09 참고자료).

    프로토콜 3.1.1 고정

    MqttNetSession.BuildOptions 와 같은 조건으로 붙기 위해서다. v5 로 붙으면 브로커가 CONNACK 0x01 로 즉시 끊는다(발행기 · 시뮬레이터 공통 주의사항).

    05태그 등록 파일 (CSV)
