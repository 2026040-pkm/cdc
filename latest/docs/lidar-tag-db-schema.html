    채널쉽게 말하면RDBTSDB

    태그마다 테이블 생성태그와 표가 일대일태그 추가 때마다 DDL이 늘고 채널 전체 조회가 어려워 제외
    공통 tag_value JSON 이력 하나새 필드 수용이 쉬움임시 원문 수신에는 가능. 스캔·세그먼트 키와 타입 검사가 약해 최종 업무 표로는 제외
    모든 필드를 개별 측정 행으로 저장범용 수치 태그 처리에 유리현재 raw JSON은 한 이벤트 묶음. 행 수 증가·행렬·NULL·같은 스캔 연결 문제로 기본안에서 제외
    채널별 타입 표 + 상태만 TSDB 기본조회 키·중복 규칙·파일 관리가 명확권고. 새 payload 버전에는 매핑·DDL 관리 필요

    향후 장비별 필드가 빈번하게 달라지는 수치 태그 서비스로 바뀐다면 별도 scalar 측정 모델을 재검토합니다. 지금의 “최적”은 현재 raw 태그 계약과 조회 요구에 대한 조건부 판단입니다.

    01태그 하나와 데이터 한 건은 다릅니다

    현재 tagMode=raw에서는 JSON 본문 전체가 문자열 태그 값입니다. 온도·상태·진척률 필드마다 별도 태그가 만들어지지 않습니다.13

    같은 산출물 태그가 여러 행이 되는 예
    tagId = LDR-GJ-A1B3-01-SEGMENTED_PCD.ot_pipeline_assembly_artifact.raw_payload

같은 tagId + 같은 scan_id + SEG-001 → artifact 1행
같은 tagId + 같은 scan_id + SEG-002 → artifact 1행
...
같은 tagId + 같은 scan_id + SEG-010 → artifact 1행

태그 1개 ≠ 데이터 1건. 이 경우에는 산출물 10행입니다.

    태그 ID로만 중복 제거하면 안 됩니다

    세그먼트들이 같은 tagId와 같은 발생 시각으로 들어올 수 있어 (tag_id, changed_at)도 산출물 고유 키가 아닙니다. HotDBProvider는 수신 배열의 각 항목을 처리해야 합니다. 태그별 마지막 값 하나로 합치면 산출물이 빠집니다.
    식별자무엇을 식별하는가사용처
    edgeGroupId + tagId그룹의 등록 태그tag_catalog 유일 키
    tag_key등록 태그의 내부 숫자 키긴 TagId 반복 저장 대신 참조
    site + device_id사업장의 장비장비 마스터

    site + scan_id + artifact_type + segment_key스캔의 산출물 1개artifact 기본 키

    등록 CSV 6개의 태그는 status 350, actual 350, artifact 1,050개로 총 1,750개입니다. DB 전체 행 수가 아닙니다. 장비 350대·상태 1초·스캔 1분·세그먼트 10개는 발행기 기본 가정이며 현장 확정값은 아닙니다.2

    03RDB 스키마: 장비·태그·스캔·목록

    테이블한 행 / 기본 키역할
    rdb.device사업장 장비 / (site,device_id)등록 기준
    rdb.tag_catalog등록 태그 / tag_key원래 토픽·장비·채널·종류 연결
    rdb.status_current태그의 최신 상태 / tag_key최신 조회·선택적 CDC
    rdb.scan스캔 1개 / (site,scan_id)장비·블록·위치 연결, artifact 선도착 허용
    rdb.actual_result스캔 이벤트 / (site,scan_id,event_type)진척률 결과. stage 없음
    rdb.artifact산출물 / (site,scan_id,artifact_type,segment_key)파일 메타 또는 행렬
    rdb.ingest_reject검증 실패 수신 / reject_id오류·키 충돌 조사

    상태 최신값은 태그별로 관리합니다

    같은 장비가 여러 그룹에 등록될 수 있어 최신 상태 키는 tag_key입니다. 장비당 한 상태가 필요한 화면은 승인된 대표 status 태그를 선택합니다. 수집원이 다른 값을 임의 합치지 않습니다.

    actual에는 stage를 다시 만들지 않습니다

    최신 발행기에 stage가 없습니다. 이후 판별 서비스가 만든다면 별도 결과 표에 판별 출처·시각을 저장합니다. START/COMPLETE는 공정 이름이 아닙니다. 진척률은 정정되거나 새 주기에서 낮아질 수 있으므로 GREATEST로 고정하지 않습니다.2

    키의 전제: 같은 scan_id 안에서 동일 event_type의 확정 결과는 하나로 봅니다. 동일 스캔의 PROGRESS가 여러 번 갱신되는 실제 계약이라면 source revision을 키에 추가해야 합니다. 같은 키로 다른 내용이 오는 경우를 조용히 덮어쓰지 않는 이유입니다.

    artifact가 actual보다 먼저 올 수 있습니다

    먼저 scan 연결 행을 만들고 artifact를 저장합니다. scanned_at은 actual 도착 시 채웁니다. 같은 스캔의 장비·위치·블록이 다르면 덮어쓰지 않고 격리합니다. 비세그먼트의 segment_id=null은 segment_key=''로 정규화해 NULL 중복 문제를 피합니다.7

    등록 PCD 1개 + 행렬 1개 + 세그먼트 10개는 12행입니다. PCD 본체는 외부 스토리지에, URI·크기·체크섬은 DB에 둡니다. 행렬은 숫자 16개라 배열로 저장합니다. 메타 수신과 파일 검증 완료는 file_state로 구분합니다.

    05TSDB 스키마: 시간 분석이 필요한 이력만

    테이블내용 / 키정책 출발점
    status_history · 기본상태 타입 컬럼 / (tag_key,event_time,event_key)6시간 청크, tag_key 묶음, event_time 정렬
    actual_metric_history · 선택진척률·신뢰도 / (site,scan_id,event_type,event_time)1일 청크. 확정된 결과의 시간 집계
    artifact_event_history · 선택수신·파일 확인·삭제 / (event_id,event_time)1일 청크. 파일 카탈로그 사본 아님

    하이퍼테이블 고유 키는 시간 파티션 컬럼을 포함합니다. 동일 이벤트가 다른 시간으로 다시 오면 이 키만으로 전역 중복 제거되지 않습니다. 재전송 시 발생 시각을 바꾸지 않는 입력 계약이 필요합니다.

    status의 6시간 청크, 3일 후 압축, 31일 보관은 기존 설정에서 가져온 후보값입니다. 행 크기·인덱스·지연 도착을 측정한 후 정합니다. DDL에는 자동 보존 삭제를 넣지 않습니다. 생성 옵션의 자동 컬럼 저장 정책은 DDL에서 명시적으로 제거합니다. 합의된 압축 시점으로 정책을 추가해야 자동 압축이 시작됩니다.

    actual 정정 계약은 미확정이므로 RDB 결과를 기본으로 유지합니다. artifact는 파일 상태 갱신이 있어 일반 목록으로 둡니다. 실적·산출물 RDB도 스캔마다 커집니다. TSDB를 선택하지 않았다고 고정 크기가 되는 것은 아닙니다.

    ④ 커밋 후 완료
    내구성 수신 경로의 ACK
    검증 실패
    격리 저장 · 정상 건과 구분
    DB 실패

    상황규칙

    status event_keySHA-256(canonical JSON 배열 [edgeGroupId,tagId,정밀 UTC 발생시각,source_event_key])
    같은 status 키·다른 내용payload_hash 비교 후 충돌 격리. DO NOTHING만으로 숨기지 않음
    status 역순과거 이력 저장, 최신값은 더 늦은 event_time만 반영
    같은 시각·다른 status 측정source sequence가 없으면 선후 불명. 임의 최신화하지 않고 동률 충돌 기록
    actual·artifact 동일 자연 키업무 내용 hash 같으면 중복, 다르면 정정/재생성 계약 전까지 격리
    파일 상태 갱신검증 서비스가 갱신. 수신 재시도가 verified를 되돌리지 않음
    DB 실패롤백 후 같은 키 재시도. 내구성 수신 완료는 커밋 후
    검증 실패ingest_reject에 원문 저장. 격리 저장 실패 시에도 완료 ACK 금지

    payload_hash는 키 순서·숫자·시각 표기를 정규화한 업무 필드 기준입니다. 전송 정보와 재시도 때 바뀔 수 있는 ingested_at은 제외합니다. revision이 정의되기 전에는 다른 값의 재수신을 무조건 최신 정정으로 처리하지 않습니다.

    .NET 시각은 PostgreSQL 마이크로초보다 정밀할 수 있어 source_time_text로 원문을 보존합니다. event_key는 DB 시각 반올림 전에 생성합니다. 발신 status 키는 초 단위, actual 키는 UUID 앞 8자 기반이므로 이 값만으로 고유성을 보장하지 않습니다.2

    완료 범위

    테이블·키·컬럼·중복 처리 원칙을 검토 가능한 제안으로 정리합니다. 확인한 Providers 경로에서 HotDBProvider 구현은 찾지 못했으며 수신·ACK·정정 규칙은 추가 구현 사항입니다. 기존 수집기·DB·CDC 설정은 변경하지 않습니다.

    실제로 실행한 검증

    신규 격리 컨테이너에서 기본·선택 DDL 생성, artifact 선도착, 같은 태그의 세그먼트 10개 + PCD + 행렬 12행, 재전송 후 12행 유지, 중복 PCD 거부, 잘못된 행렬/빈 세그먼트/파일 URI 누락 거부, 동일 UUID 앞 8자의 다른 스캔 2건 구분, 진척률 범위 검사, status 중복 제거와 압축 후 2행 조회를 확인했습니다.

    현재값 표에 최신 fixture를 넣는 것까지 검증했습니다. Provider의 실제 역순 갱신 방지, hash 생성, 충돌 격리, 재시도·ACK, HANA 전달은 구현·통합 시험이 남아 있습니다. 이것들을 실행 완료로 표시하지 않습니다.
