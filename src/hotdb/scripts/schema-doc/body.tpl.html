목차
    Schema & Data Flow

    필드 데이터는 tsdb 에 쌓이고, 판별 모듈 RDB 로 CDC 되어 다시 SAP 로 갑니다

    Hot DB(PostgreSQL 한 대)에 만들어진 스키마 · 표 · 컬럼 전체와, 필드 한 칸이 MQTT 메시지에서 tsdb 를 거쳐 판별 모듈 RDB · SAP 까지, 그리고 레거시(SAP · Oracle) 표가 폴링으로 Hot DB 에 들어오는 길을 적습니다. 표 정의는 손으로 옮긴 것이 아니라 기동 중인 DB 에서 조회해 생성했습니다1.

    스키마 10 · 계정 10 · publication 2 · 슬롯 5 tsdb 5표 · 판별 모듈 5표 × 4 (관계형) · ops 5표 · 레거시 178표 Flyway v8 · TimescaleDB 2.29.2 · PG 17.11 페이로드는 ISL 벤더 합의 전 제안 규격

    판별 모듈 표는 하나만 적습니다

    판별 모듈의 RDB 는 스키마 svc 하나입니다(V9). 모든 표에 module 컬럼이 있고, 행 수준 보안이 계정 svc_<모듈> 에게 자기 행만 보이게 합니다. 모듈은 ops.provision_module() 로 늘립니다. 레거시 표(erp · mes · lgs · geo)는 별도 레거시 DB 에 있습니다(V10). 레거시 표는 이름 · 값을 지어낸 시험용 178표입니다.

    03tsdb — 필드 데이터

    세 채널(status · actual · artifact)을 채널별 하이퍼테이블에 둡니다. "출처" 칸은 태그 카탈로그 v1 의 실제 발행 필드입니다2.

    하이퍼테이블청크압축보존segmentby · orderbyCHECK 제약

    압축을 7일 뒤로 미룬 이유

    압축은 원본 청크의 행을 이벤트 없이 비웁니다. 권역 서비스가 아직 읽지 않은 행이 압축되면 그 행은 CDC 로 나오지 않습니다. TimescaleDB 2.29 가 자동으로 붙이는 기본 압축 정책은 V2 에서 지우고 7일로 다시 겁니다.

    관계와 도착 순서

    모듈 안 FK(device_status_change → current, actual_result · artifact → scan)는 DEFERRABLE INITIALLY DEFERRED 라 커밋 때 검사합니다. 한 배치는 라우트 설정 순서(부모 먼저)로 쓰고, 산출물이 START 보다 먼저 오면 scan-stub 라우트가 last_event_at = -infinity · PENDING 인 부모 자리를 먼저 만듭니다. 장비 마스터 FK((site, device_id) → tsdb.device)는 즉시 검사 — 장비 행은 이력보다 항상 먼저 있습니다(tag_catalog FK).

    인덱스: device_status_current (applied_at) · scan (hull_no, block_id) · scan (device_id) · actual_result (scan_id) · artifact (applied_at). 모듈 사이 · 레거시와는 FK 없이 키 값(hull_no · block_id)으로 잇습니다.

    08레거시 스키마와 폴링

    레거시 표는 별도 레거시 DB(hotdb-legacy-db)에 있고, 폴링 경로를 시험하려고 지어낸 표입니다 — 이름 · 컬럼 · 값은 지어냈고 표 수 · PK · 컬럼 수만 실제와 비슷합니다(scripts/gen-sample-legacy.py). 데이터는 RFC Service · DB Agent 가 폴링으로 채웁니다4.
