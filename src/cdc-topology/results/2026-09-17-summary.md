# 스파이크 결과 요약 — 2026-09-17

이미지 `timescale/timescaledb:2.29.2-pg17` (TimescaleDB 2.29.2 · PostgreSQL 17.11). 원자료는
`hypertable-decoding-20260917-1457.txt`. Q6 은 같은 컨테이너에서 손으로 돌린 것이라 아래에 명령과 출력을 옮겨 둔다.

| # | 질문 | 결과 | 근거 (원자료 단계) |
|---|---|---|---|
| Q1 | `CREATE PUBLICATION … FOR TABLE <하이퍼테이블>` 로 행이 나오는가 | **안 나온다.** 부모 `h` 만 publication 에 들고, 청크에 들어간 행은 pgoutput 에 0건. 이후 새로 생긴 청크도 마찬가지 | 1 · 7단계 `s_h` 에 `public.r` 만 있음 |
| Q1b | `FOR ALL TABLES` 면 | 나온다. 단 **청크 이름**(`_timescaledb_internal._hyper_1_N_chunk`)으로, 그리고 `_timescaledb_catalog.*` 변경이 같이 섞인다. 1단계 뒤 publication 이 가리킨 표 36개 중 내부 표 6개 | 1단계 `s_all` |
| Q2 | 압축이 DELETE 로 나오는가 | **DELETE 도 TRUNCATE 도 안 나온다.** 원래 행 350개는 이벤트 없이 사라지고, `_hyper_1_1_chunk_compressed` 에 압축 뭉치 INSERT(세그먼트 수만큼)와 카탈로그 UPDATE 가 나온다 | 3단계 · Q6 |
| Q2b | 압축 청크에 늦게 들어온 행 | 원래 청크 이름으로 INSERT 가 나온다 | 4단계 |
| Q3 | `drop_chunks` 가 이벤트를 남기는가 | **데이터 행 삭제는 0건.** 카탈로그 표 DELETE 4건만 | 5단계 |
| Q4 | 연속 집계 refresh | materialization 하이퍼테이블 청크에 INSERT 700건 + 카탈로그 변경 수십 건. 집계가 또 하나의 쓰기 소스가 된다 | 6b단계 |
| Q5 | 부모에 건 REPLICA IDENTITY 가 새 청크에 상속되는가 | **상속된다** (`relreplident = f`) | Q5 표 |
| Q6 | `FOR ALL TABLES` publication 이 있을 때 하이퍼테이블을 새로 만들 수 있는가 | **못 만든다.** `create_hypertable` 도, 연속 집계도 `cannot create hypertable for table "…" because it is part of a publication` 으로 거부된다. publication 을 먼저 만들기 전에 있던 하이퍼테이블은 청크 생성·압축이 계속 된다 | 6a단계 · Q6 |
| C1 | 행당 WAL (3,500행) | 하이퍼테이블 INSERT(인덱스 3개) **350 B** · 상태 표 UPDATE FULL **280 B** · DEFAULT **254 B** | C1 표 |

C1 은 체크포인트 직후 첫 변경의 full page image 가 섞인 값이다. 절대값보다 "셋이 같은 자릿수" 라는 점을 본다.

## 기존 문서와 달라진 점

`docs/cdc/timescaledb-cdc-impact.html` B2 는 "압축이 청크 한 개 분량의 DELETE 이벤트로 흘러가 target 을 지운다" 로
적었다. 이 버전에서는 **반대로 조용하다** — DELETE 가 안 나오므로 target 이 지워지지는 않지만, 압축 뭉치 INSERT 가
해석할 수 없는 모양으로 온다. "원천에서 행이 사라졌다" 는 사실은 어느 쪽이든 CDC 로 알 수 없다.
Q6 은 그 문서에 없던 제약이다 — `FOR ALL TABLES` 로 청크를 잡으려는 순간 원천에서 새 하이퍼테이블 · 연속 집계를
만드는 일이 막힌다.
