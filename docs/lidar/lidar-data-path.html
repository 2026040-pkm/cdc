    09왜 LiDAR 만 tsdb 와 rdb 두 스키마로 나눴나

    나누는 선은 데이터 종류가 아니라 "행 단위 CDC 가 성립하는가" 하나입니다. 이 DB 에서 그 선의 양쪽에 모두 데이터가 있는 것은 LiDAR 뿐이라, LiDAR 에서만 나뉘어 보입니다 6.

    tsdb · 하이퍼테이블 + 연속 집계

    lidar_status · lidar_scan_actual · lidar_scan_artifact, 1분 집계 4개.
    초당 수백 행이 시간 순으로 쌓이고, 6시간(실적은 1일)마다 새 청크 표가 생기고, 3일 뒤 압축, 31일 뒤 청크째 삭제됩니다.

    CDC 로 못 옮깁니다. 새 청크는 publication 이 모르는 표 이름으로 변경을 내고, 압축은 행을 내부 표로 옮기며, 보존은 DROP 이라 행 삭제로 보이지 않습니다. 그래서 lidar-ingest 가 Kafka 에서 직접 적재합니다.

    rdb · 일반 표

    lidar_device_state · lidar_block_progress · lidar_block_artifact · lidar_status_message · lidar_ingest_reject · lidar_tag_catalog, 그리고 embedded-cdc 검증용 원천 표 car · computer · grade · member · cdc_heartbeat.

    CDC 로 옮깁니다. 행 단위 INSERT/UPDATE/DELETE 만 있어 publication embedded_cdc_pub 과 REPLICA IDENTITY FULL 로 cdc-service 가 수신 DB 로 복제합니다.

    질문답
    왜 LiDAR 에서만 나뉘나다른 원천 표(car · member 등)는 시계열이 아니라 전부 rdb 한쪽에 있습니다. LiDAR 는 시계열 원본(tsdb)과 그 원본을 줄인 최신 상태 · 누계 · 등록부(rdb)가 한 DB 에 함께 있어서 선이 LiDAR 안을 지나갑니다.
    왜 주석이 아니라 스키마로 나눴나publication 에 하이퍼테이블이 실수로 끼어드는 것을 구조로 막기 위해서입니다. 캡처 대상은 전부 rdb 에 있고, tsdb 에 있는 것은 넣지 않는다는 규칙 하나로 끝납니다(04-cdc-lidar.sql).
    하이퍼테이블을 CDC 에 태우면치명 3건 · 주의 5건: 청크 이름으로 온 이벤트는 전부 무시되고, 압축 · 보존이 수신 측 데이터를 조용히 지우거나 갈라지게 하며, 초기 스냅샷이 안 되고, 실측 처리량 2,467/초가 피크 8,000/초에 못 미칩니다(B안) 9.
    그러면 수신 측은 무엇을 받나rdb 의 요약 표입니다. 장비 350대의 최신 상태, 블록별 공정 진척과 산출물 누계, 레코드 추적, 격리 원문, 태그 등록부 — 수신 측이 숫자 tid 를 장비로 되돌리려면 카탈로그도 같이 있어야 해서 함께 옮깁니다.
    조회할 때 스키마를 알아야 하나아닙니다. ALTER DATABASE lidar SET search_path = tsdb, rdb, public 이 걸려 있어 select * from lidar_status 로 됩니다.
    스키마 이름 tsdb 와 WITH (tsdb.hypertable) 는 같은 것인가무관합니다. 뒤엣것은 TimescaleDB 의 스토리지 옵션 이름공간입니다.

    1세그먼트 PCD 가 스캔마다 10건 중 평균 2.5건만 도착
    유실    		 세그먼트 10건이 모두 같은 id(…-SEGMENTED_PCD) → 같은 TagId → 같은 ParameterId 로 들어갑니다.     2레코드 추적 표에서 토픽 둘이 사라짐
    결함    		 rdb.lidar_status_message 의 PK 가 (kafka_partition, kafka_offset) 로 토픽이 빠져 있습니다. 세 토픽 모두 파티션 0 이라 오프셋이 겹치면 먼저 쓴 쪽만 남습니다. 최근 10분 동안 artifact 543건, status 1건, actual 0건이 남았습니다. 데이터 행은 영향 없음. verify 의 채널 분포와 CDC 로 옮겨지는 추적 행이 틀립니다. PK 에 kafka_topic 추가 필요(수신 측 02-lidar.sql · LidarPassthroughHandlers 까지 네 곳 동시 수정).
    3Kafka lag 지표가 토픽 하나만 보임
    결함    		 lidar_ingest_kafka_lag 레이블이 partition 뿐이라 세 토픽의 파티션 0 이 같은 시계열을 덮어씁니다. 합계 lidar_ingest_source_lag 는 맞습니다. 레이블에 topic 추가.
    4Agent 배치 설정이 먹지 않음
    어긋남    		 Mqtt.Agent.json 이 Telemetry* 키를 "MqttSession" 아래 두었지만 코드는 "Telemetry" 절을 읽습니다. 지금은 기본값과 같은 값이라 증상이 없습니다. 값을 바꾸는 순간 무시됩니다.

    문서    		 README 는 pm_mode 를 tid 앞에 적었습니다. 실제 순서는 timestamp, tid, value, pm_mode 입니다. JSON 이라 파싱 영향은 없습니다. 예시만 고칩니다.
