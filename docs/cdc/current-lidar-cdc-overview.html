    장비 식별과 추적용 일반 테이블

    • lidar_tag_catalog: Kafka의 (send_topic, param_id)를 장비·태그 정보로 변환합니다.
    • lidar_status_message: 입력 레코드와 채널별 항목 수 등 수신 기록을 남깁니다.
    • lidar_ingest_reject: 해석할 수 없는 입력을 격리합니다.

    카탈로그에 없는 장비는 상태 채널에서 idempotency key로 복원을 시도하고, 복원이 안 되는 경우 #숫자 식별자가 남을 수 있습니다. 누락 여부는 lidar_ingest_tag_unresolved_total로 확인합니다.3

    write_batch()는 원본 INSERT, 장비·블록 상태 UPSERT, 격리·수신 기록을 한 트랜잭션으로 처리합니다. 실패하면 같은 배치를 재시도하며, DB 저장 성공 전에는 소스 commit을 호출하지 않습니다.3

    원본 중복 방지와 누계 정합성은 구분해야 합니다

    원본 INSERT는 (idempotency_key, time) 충돌을 무시합니다. 반면 블록 상태 UPSERT의 누계 컬럼은 기존 값에 입력 값을 더하고, 상태 계산에는 전달된 배치 전체를 사용합니다. 코드상 재전달 때 누계가 다시 더해질 가능성이 있어 재전달 시나리오 검증이 필요합니다. 이 문서는 시스템 전체의 exactly-once를 보장하지 않습니다.3

    원본 시계열의 위치

    status · actual · artifact 하이퍼테이블은 이 프로젝트의 publication에 포함하지 않습니다. 수신 DB가 TimescaleDB여도 원본 시계열 전체가 자동으로 전달되는 구성은 아닙니다.

    일반 PoC 표 car · computer · grade · member 및 heartbeat도 커넥터 목록에 별도로 존재합니다.

    원천 publication은 embedded_cdc_pub, 이 수신 스택의 slot은 embedded_cdc_tsdb_slot입니다. SQL 등록, 커넥터 include 목록, 수신 테이블 정의가 함께 맞아야 합니다.789

    기존 설명과 실제 코드의 차이

    README 일부는 LiDAR CDC 대상을 4개로 설명하지만 현재 SQL·설정·수신 DDL에는 블록 진척과 산출물 대장을 포함한 6개가 있습니다. 또한 기존 src/embedded-cdc를 가리키는 설명이 남아 있어 실행 경로는 현재 파일 기준으로 확인해야 합니다.

    06비교 기준은 같은 시간 구간의 도달률입니다

    메시지 수, Kafka 레코드 수, DB 적재 행 수는 서로 다른 단위입니다.

    채널기본 발행 가정5분 기대 항목 수근거
    status350대 × 초당 1건105,000기본 설정·산식 1011
    actual350대 × 분당 1건1,750기본 설정·산식 1011
    artifact350대 × 분당 12건21,000기본 설정·산식 1011

    총 기대 입력은 127,750항목 / 5분, 평균 약 425.8항목 / 초입니다. 이는 기본 설정의 계산값이며 실측 처리량이 아닙니다. 발행 옵션·장비 상태·기동 시점이 다르면 기준을 조정해야 합니다.

    verify.ps1은 이벤트 시각 기준으로 최신 1분을 제외한 직전 5분을 기본 조회합니다. 채널별 행 수, 기대 대비 도달률, 장비 수, 미해석 장비, 평균·p95 지연을 두 DB에서 비교합니다. 양쪽 SQL은 각 DB의 now()를 사용하므로 엄밀한 비교에서는 동일한 고정 시작·끝 시각을 사용해야 합니다.10
