02

TimescaleDB 로 무엇을 얻는가

1개월 보존이 요구사항입니다. 그 조건에서 일반 PostgreSQL 과 실제로 얼마가 갈리는지 재 봤습니다.

02. 보존 비용

31일 보존이 349GB 에서 61GB 로 내려갑니다

실측 압축비 12.6배 적용 · 인덱스 제외

무엇을 실측했나

운영 표 tsdb.lidar_status 의 사본 321,061행을 컬럼스토어로 전환했습니다. 111MB → 8,984kB, 행당 362B → 28.7B.5 보존 창 전체로는 최근 3일이 압축되지 않은 채 남으므로 5.7배이고, 압축 구간만 보면 12.6배입니다.
OT LiDAR 필드 데이터 TimescaleDB 적재 검증
발표자 노트용량보다 더 큰 차이는 지우는 방식이다. 일반 PostgreSQL 로 31일 보존을 하면 매일 3,000만 행을 DELETE 해야 하고 그만큼 VACUUM 이 따라온다. TimescaleDB 는 청크째 DROP 이라 그 비용이 없다.
02. 혼재

실시간과 10분 주기를 같은 DB 에서 따로 받습니다

채널별 청크 · 집계 설정

초당 350행과 10분당 1행을 한 표에 담으면 어느 쪽에 맞춰도 다른 쪽이 망가집니다. 채널을 표로 나누고 청크 간격을 따로 준 이유입니다.

채널유입청크 간격하루 행 수연속 집계가 답하는 질문

원본 31일, 연속 집계 1년. 원본이 사라져도 1분 단위 추이는 남습니다. 원본 삭제는 DELETE 가 아니라 청크 DROP 이라 VACUUM 부담이 없습니다.

OT LiDAR 필드 데이터 TimescaleDB 적재 검증
발표자 노트하루 행 수는 운영 전제(status 실시간, 나머지 10분)로 계산했다. 발행기 기본값은 actual·artifact 가 1분이라 10배 크다 — 질문 나오면 그렇게 답한다. 연속 집계는 materialized_only=false 라 최근 2분 구간은 원본에서 실시간으로 메워 조회된다.
02. 주기

10분 주기는 총량이 아니라 도착 모양을 바꿉니다

상태 1초 · 실적 10분 · 산출물 10분

주기가 1분에서 10분으로 늘면 적재 평균은 오히려 16% 줄어듭니다. 바뀌는 것은 순간값입니다 — 10분에 한 번 4,550행이 한꺼번에 들어옵니다.

가장 나쁜 경우도 실측 처리량의 절반입니다

9,101행/초는 5.1 의 배치 쓰기 평균 17.8ms 에 배치당 162행을 나눈 값으로, 채널별 INSERT 와 상태 표 UPSERT 가 전부 끝난 뒤의 실효 처리량입니다. 다만 동시 발행은 현 발행기가 장비마다 시차를 두므로 아직 한 번도 관측되지 않았습니다 — PoC 에서 확인할 항목입니다.
OT LiDAR 필드 데이터 TimescaleDB 적재 검증
발표자 노트평균이 줄어든다는 점을 먼저 말하고 안심시킨 뒤, 문제는 버스트라고 넘어간다. 4,550 = 350대 × 13건(실적 1 + 산출물 12)이다. 질문이 나오면 현 발행기는 offset 으로 시차를 두므로 실제로는 초당 7.6행으로 퍼진다고 답한다.
02. 전달

값 하나가 Kafka 로 열 번 나갑니다

snapshotIntervalMs=60000 이 그대로일 때

발행 정책은 실적 · 산출물이 1분 주기이던 판에서 정해졌습니다. 60초 스냅샷은 그대로인데 값은 600초에 한 번만 바뀌므로, 나머지 아홉 번은 같은 값이 다시 실려 나갑니다.

DB 에 65만 행을 넣으려고 655만 항목을 파싱합니다

멱등 인덱스가 DB 행은 막아 주므로 데이터는 틀리지 않습니다. 대신 Kafka 대역과 소비자 파싱이 열 배로 듭니다. 실적 · 산출물의 snapshotIntervalMs 만 600000 으로 바꾸면 중복이 0 이 됩니다 — 채널별로 정책을 나눌 수 있는지가 ISL 측에 확인할 첫 번째 항목입니다.
OT LiDAR 필드 데이터 TimescaleDB 적재 검증
발표자 노트status 는 1초 주기가 스냅샷 60초보다 짧아 OnChange 가 지배하므로 이 문제가 없다. 관측 15분 동안 중복 스킵이 1건뿐이었던 것이 근거다. 이 슬라이드는 ISL 측 담당자가 있으면 그 자리에서 답이 나올 수 있으니 질문을 던지고 넘어간다.
