    LiDAR 필드 데이터가 세 DB 를 지나는 길

    Kafka 에서 들어온 LiDAR 필드 데이터가 lidar TimescaleDB(원천) → cdc-service(embedded-cdc-tsdb) → targetdb 로 옮겨지는 과정을 DB 관점에서 정리합니다. 각 구간이 무엇을 받고 무엇을 저장하는지를 표 단위와 컬럼 단위로 적었습니다. 수치는 2026-09-11 13:26 KST 에 실제로 돌고 있는 스택에서 읽은 값입니다14.

    원천 lidar · 59432 수신 targetdb · 60433 파이프라인 embedded-cdc-tsdb 실측 2026-09-11 13:26 KST

    00범위와 전제

    이 문서는 "DB 에 무엇이 들어오고 무엇이 남는가" 만 다룹니다. 발행 구간과 성능 비교는 다른 문서가 맡습니다.

    이 문서가 다루는 것

    • 세 구간(Kafka→원천 / 원천→CDC / CDC→수신)이 각각 받는 것과 저장하는 것
    • 표 단위 대응과 컬럼 단위 필드 카탈로그 — 누가 그 값을 채우고, CDC 로 건너가는지
    • CDC 의 경계 — 무엇이 건너가지 않으며 왜 그런지
    • 양쪽 DB 를 맞대 보는 대사 쿼리와 그 실측 결과

    다루지 않는 것

    • MQTT 22개 토픽 → Kafka 3개 토픽 발행 구간과 EES 메시지 포맷1
    • 압축·보존 정책의 용량·성능 실측 (같은 문서 5절)
    • Java · Go · custom 세 CDC 스택 비교2
    • car · computer · grade · member 네 데모 표의 변환 규칙 — 같은 publication 에 실려 있지만 LiDAR 데이터가 아닙니다

    전제

    원천은 lidar 스택(src/timescaledb)의 TimescaleDB 이고, 그 스택이 먼저 떠 있어야 합니다 — tsdb-net 은 그쪽이 만드는 external 네트워크입니다3. embedded-cdc 스택과 같은 원천 DB 를 동시에 읽으며, publication 하나를 공유하고 슬롯·오프셋 파일·heartbeat 행은 따로 팝니다. infra/db/docker-compose.source.yml 의 옛 원천 컨테이너(sourcedb)는 루트 compose 의 include 에서 빠져 있습니다 — 파일은 남아 있으나 이 흐름에는 등장하지 않습니다.

    02구조

    박스를 끌어 배치를 바꿀 수 있습니다. 바꾼 배치는 JSON 버튼으로 내보내 이 파일의 dgm-data 블록에 붙여넣으면 영구 반영됩니다.

    컴포넌트 구성 — 무엇이 무엇에 쓰는가

    그림에서 읽을 것

    tsdb 상자에서 나가는 선이 없습니다. 하이퍼테이블은 publication 에 실리지 않으므로 흐름이 거기서 끝납니다. 그럼에도 수신 측이 actual·artifact 두 채널까지 보게 되는 것은 rdb 의 블록 축 상태 표 둘 덕분입니다.

    한 항목이 지나는 순서 — 실패 경로 포함

    실패가 유실이 되지 않는 지점 셋

    파싱 실패는 항목 단위로 격리되고 같은 레코드의 나머지는 적재됩니다 — 원문과 사유를 lidar_ingest_reject 에 남깁니다. 적용 실패는 배치 재시도 3회(200 · 400 · 800ms) 뒤 건 단위로 좁혀 범인만 cdc_dead_letter 로 보냅니다. 구조 실패(한 배치의 50% 초과 격리)는 격리하지 않고 예외를 던져 오프셋을 전진시키지 않습니다 — 멈추는 것이 조용히 어긋나는 것보다 낫다는 판단입니다.

    031구간 · 원천 DB 가 받는 것과 저장하는 것

    Kafka 레코드 하나를 받아 표 여섯 곳에 나눠 씁니다. 어디에 쓰는지가 그 데이터의 운명을 정합니다.

    받는 것 — Kafka 레코드 3종

    채널은 Kafka 토픽이 정합니다. EES 메시지 하나가 토픽 하나이고, 토픽 이름의 마지막 마디(status · actual · artifact)로 분류합니다. content.tid 는 TagId 가 아니라 EES ParameterId(숫자) 이고 raw_payload 안에도 장비 id 필드가 없으므로, Kafka 만 읽어서는 어느 장비인지 알 수 없습니다 — 그것을 되돌리는 것이 rdb.lidar_tag_catalog 입니다4.

    축을 장비(tid)가 아니라 블록(hull_no, block_id)으로 잡은 이유

    actual·artifact 채널의 상태 표는 공정(stage)이나 산출물 종류(artifact_type)를 키에 넣지 않습니다. 키에 넣으면 블록 하나가 공정 수만큼 행으로 쪼개져 표가 계속 자라고, 결국 하이퍼테이블의 사본이 됩니다. 공정은 키가 아니라 마일스톤 컬럼으로 눕히고, 산출물 종류는 건수·용량 컬럼으로 눕힙니다. 발행기에서 hull_no · block_id 는 장비 Index 로 고정되므로(H{1200+Index%40} · B{100+Index%90}{P|S}) 이 두 표는 350행에서 멈추고 그 뒤로는 UPDATE 만 일어납니다 — 실측도 정확히 350행입니다.

    device_state 와 블록 표의 UPSERT 가 다른 이유

    lidar_device_state 는 최신 값만 있는 표라 ON CONFLICT ... WHERE EXCLUDED.last_event_at > ... 한 줄로 끝납니다. 블록 표에서는 같은 방법을 쓸 수 없습니다 — WHERE 로 행 전체를 막으면 늦게 온 이벤트의 누계와 마일스톤까지 같이 버려집니다. 그래서 행은 항상 갱신하고, 컬럼마다 위 네 규칙 중 하나를 적용합니다.
    src/timescaledb/dev/ingest/ingest.py — 한 배치가 한 트랜잭션 (발췌)
    def write_batch(conn, rows, rejects, message_rows):
    # 한 트랜잭션. 커밋된 뒤에만 Kafka 오프셋을 커밋한다 (at-least-once)
    with conn.transaction():
        with conn.cursor() as cur:
            for channel in CHANNELS:                    # 1) 원문 → tsdb 하이퍼테이블
                cur.execute(INSERTS[channel][1], (json.dumps(...),))
            if rows[CH_STATUS]:                         # 2) 장비 축 상태
                cur.execute(UPSERT_STATE, (json.dumps(state_rows_of(rows[CH_STATUS])),))
            if rows[CH_ACTUAL]:                         # 3) 블록 축 — 공정 마일스톤
                cur.execute(UPSERT_BLOCK_PROGRESS, (json.dumps(progress_rows(...)),))
            if rows[CH_ARTIFACT]:                       # 4) 블록 축 — 산출물 대장
                cur.execute(UPSERT_BLOCK_ARTIFACT, (json.dumps(artifact_rows(...)),))
            if rejects:                                 # 5) 격리
                cur.executemany(INSERT_REJECT, rejects)
            if message_rows:                            # 6) 레코드 단위 추적
                cur.executemany(INSERT_MESSAGE, message_rows)

    값 전달은 전부 json_populate_recordset(NULL::<표>, %s::json) 입니다 — JSON 키를 컬럼에 맞춰 DB 가 캐스팅하므로 timestamptz 문자열(7자리 소수초 포함)을 파이썬에서 다루지 않습니다.

    publication 에 스키마째 싣지 않는 이유

    ALTER PUBLICATION embedded_cdc_pub ADD TABLES IN SCHEMA rdb 로 두면 표가 늘어도 저절로 따라오고 하이퍼테이블은 구조적으로 못 들어옵니다. 그런데 이 publication 은 이미 cdc_user(비 superuser) 소유이고, 스키마 단위 항목을 가진 publication 은 superuser 소유여야 합니다. 그래서 표를 열거하고, 표가 늘면 04-cdc-lidar.sql 을 같이 고칩니다8.

    scripts/reconcile.sql 은 lidar 표에서 동작하지 않는다 실행으로 확인

    그 스크립트는 schemaname='public' 인 표를 찾아 ORDER BY t.id 로 체크섬을 냅니다. lidar 표 여섯 중 id 가 있는 것은 lidar_ingest_reject 뿐이라, 수신 DB 에서 그대로 돌리면 ERROR: column t.id does not exist 로 질의 전체가 실패합니다. 원천 쪽은 표가 rdb 스키마에 있어 아예 대상에서 빠집니다. 당분간 아래 쿼리를 씁니다.
    키 정렬 체크섬 — 표마다 ORDER BY 를 키로 바꾼다
    -- 원천 (rdb 스키마, 관리 컬럼 없음)
SELECT count(*), md5(string_agg(to_jsonb(t)::text, ','
                    ORDER BY t.send_topic, t.param_id))
FROM rdb.lidar_tag_catalog t;

-- 수신 (public 스키마, source_lsn 을 빼고 비교한다)
SELECT count(*), md5(string_agg((to_jsonb(t) - 'source_lsn')::text, ','
                    ORDER BY t.send_topic, t.param_id))
FROM public.lidar_tag_catalog t;

    움직이는 표는 체크섬이 맞을 리 없다

    device_state 는 초당 300행 남짓이 바뀌고 블록 표는 분 단위로 바뀝니다. 이 표들은 체크섬이 아니라 건수와 지연으로 봅니다. 체크섬 대사가 의미 있는 것은 tag_catalog 처럼 변경량이 0 에 수렴하는 표이거나, 쓰기를 멈춘 상태에서 돌릴 때입니다.

    세션 시간대가 같아야 한다

    timestamptz 의 텍스트 표현이 세션 시간대를 따르므로, 두 세션의 TimeZone 이 다르면 값이 같아도 체크섬이 갈립니다. 두 컨테이너 모두 TZ=Asia/Seoul 로 맞춰 두었습니다.
