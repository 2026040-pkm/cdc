센서 데이터 TimescaleDB 구성 문서

v0.1 · 2026-09-07 · 데이터플랫폼

    Development Document

    필드 센서 데이터 실시간 저장소를 TimescaleDB로 구성합니다

    현장 설비에서 초당 수천 건씩 들어오는 센서 값을 일반 PostgreSQL 테이블에 계속 쌓으면 디스크와 인덱스가 먼저 무너집니다. 이 문서는 같은 PostgreSQL 위에 TimescaleDB 확장을 얹어 적재 · 압축 · 집계 · 삭제를 정책으로 자동화하는 구성을 정의하고, 무엇을 어떤 순서로 만들어 어떤 수치로 완료를 판정할지까지 적습니다.

    백엔드 1명 · DBA 0.5명 예상 6일 PostgreSQL 17 + TimescaleDB 2.29.2 규모 파라미터 미확정

    00범위와 전제

    TimescaleDB는 설치하면 빨라지는 물건이 아니라, 청크 크기와 압축 시점과 보존 기간을 정하는 일입니다. 그 값을 정하는 것이 이 과제의 실체이고 나머지는 건드리지 않습니다.

    이번에 만드는 것

    • TimescaleDB 확장 설치와 PostgreSQL 파라미터 확정
    • 원본 하이퍼테이블 sensor_reading 과 멱등 배치 적재 경로
    • 컬럼스토어 전환 정책과 보존 정책
    • 1분 · 1시간 두 단계 연속 집계
    • 적재 지연과 잡 실패 지표를 기존 Prometheus · Grafana에 연결

    이번에 하지 않는 것

    • 엣지 게이트웨이 펌웨어와 수집망 변경 — 현재 HTTP 배치 전송을 그대로 받습니다
    • 이상 탐지 · 예측 모델 — 집계 테이블까지만 만듭니다
    • 다중 노드 분산 — TimescaleDB 2.14에서 멀티노드 지원이 제거되어 선택지가 아닙니다9
    • 기존 CDC 파이프라인 DB 변경 — 센서 저장소는 별도 인스턴스로 분리합니다12

    규모 전제

    아래 값이 뒤의 모든 계산(청크 인터벌, 압축 시점, 디스크 산정)의 입력입니다. 측정값이 아니라 설계 시작점이므로 작업 단위 S1에서 실제 수집망 통계로 교체하고, 그때 이 표를 갱신합니다.

    전제 · 에디션 선택이 3~5절 전체를 좌우합니다

    컬럼스토어(하이퍼코어) 압축, 연속 집계, 보존 · 압축 정책은 TimescaleDB Community Edition(TSL) 기능입니다. Apache 2 에디션(-oss 태그 이미지)에는 하이퍼테이블만 있고 이 문서의 압축 · 집계 구성이 전부 동작하지 않습니다10. 서비스형으로 재판매하지 않는 사내 사용은 TSL로 무상 사용이 가능하므로 -oss 가 아닌 태그를 씁니다. 이 판단을 S1에서 법무 확인과 함께 못 박고, 이미지 태그를 고정합니다.

    01개발 시나리오

    구현 전에 무엇을 성공으로 볼지 문장으로 고정합니다. 아래 ID는 4절 작업 분할과 6절 테스트에서 그대로 참조합니다.

    정상 흐름

    SC-01 · 실시간 배치가 원본 하이퍼테이블에 적재된다

    Given
    sensor_reading 하이퍼테이블이 청크 인터벌 6시간으로 생성되어 있다
    When
    게이트웨이가 500건 묶음을 POST /readings 로 보낸다
    Then
    500행이 현재 시각이 속한 청크 한 개에 적재되고, 수신에서 커밋까지 p99가 2초 이내다

    SC-02 · 1분 연속 집계가 확정 구간만 갱신한다

    Given
    reading_1m 연속 집계가 start_offset 3시간 / end_offset 5분 정책으로 등록되어 있다
    When
    집계 잡이 실행된다
    Then
    최근 5분 구간은 갱신되지 않고, 그보다 이전 3시간 구간의 버킷만 다시 계산된다

    예외 흐름

    SC-03 · 게이트웨이 복구 후 3시간 지연 데이터가 과거 청크로 들어간다

    Given
    게이트웨이가 3시간 끊겼다가 복구되어 로컬 버퍼 2,160만 건을 밀어 넣는다
    When
    해당 구간의 청크가 아직 로우스토어다(컬럼스토어 전환 기준 8일 이내)
    Then
    전량이 원래 계측 시각의 청크에 적재되고, 같은 시간 동안 실시간 적재의 p99 지연이 2초를 넘지 않는다

    SC-04 · 같은 (tag_id, time) 재전송이 행을 늘리지 않는다

    Given
    태그 101의 2026-09-07 02:00:00Z 값 23.4가 이미 적재되어 있다
    When
    게이트웨이 ack 유실로 같은 시각 · 같은 태그가 값 99.9로 재전송된다
    Then
    행 수는 1로 유지되고 값은 23.4로 남으며, 중복 카운터가 1 증가한다

    SC-05 · 보존 기간이 지난 원본은 삭제되고 집계는 남는다

    Given
    원본 보존 90일, reading_1h 보존 5년 정책이 등록되어 있다
    When
    보존 잡이 91일 전 청크를 대상으로 실행된다
    Then
    원본 청크는 삭제되고, 같은 구간의 reading_1h 행은 그대로 조회된다

    02목표 구조

    박스를 끌어 배치를 바꿀 수 있습니다. 구조가 바뀌면 JSON 버튼으로 내보내 이 파일의 dgm-data 블록에 붙여넣습니다.

    컴포넌트 구성

    원본 하이퍼테이블은 대시보드가 직접 읽지 않습니다. 조회를 전부 연속 집계로 보내야 압축된 청크를 훑는 무거운 쿼리가 실시간 적재를 방해하지 않습니다.

    배치 한 건이 지나는 순서

    이 그림에서 가장 비싼 경로

    n5 입니다. 컬럼스토어로 전환된 청크에 뒤늦은 행이 들어오면 해당 세그먼트를 풀었다가 다시 담아야 하고, 삽입된 행이 자동으로 재압축되지도 않습니다3. 그래서 압축 전환 기준을 지연 도착 상한보다 앞당기면 안 됩니다. 지연 상한 7일에 하루를 더해 전환 기준을 8일로 잡은 것이 ADR-02 입니다.

    03구현 방식 비교와 선택

    왜 TimescaleDB인가에 답이 없으면 반년 뒤 같은 논의를 다시 합니다. 탈락안도 이유와 함께 남깁니다.

    방식장점단점적합도
    A. 순수 PostgreSQL
    선언적 파티셔닝 + pg_partman    		 확장 추가 없음, 운영 · 백업 체계 그대로 압축이 없어 보존 90일이면 936GB, 롤업 뷰와 파티션 생성 · 삭제를 전부 직접 구현 보류
    B. PostgreSQL + TimescaleDB
    선택안 · Community Edition    		 같은 SQL · 같은 드라이버 · 같은 백업, 압축 · 집계 · 보존이 정책 3줄 확장 버전과 PostgreSQL 메이저 업그레이드가 서로 묶임, TSL 라이선스 확인 필요 채택
    C. 전용 시계열 DB
    InfluxDB · ClickHouse    		 압축률과 대량 집계 성능 우위 설비 마스터 테이블과 조인 불가, 운영 · 모니터링 · 백업 체계를 하나 더 떠안음 탈락

    ADR-01 · 원본은 하이퍼테이블 한 개에 좁은 스키마로 둔다

    배경
    설비가 증설될 때마다 태그가 늘어납니다. 태그마다 컬럼을 두는 넓은 스키마는 증설 때마다 ALTER TABLE 이 필요하고, 그 시점에 적재가 멈춥니다.
    결정
    (time, tag_id, value, quality) 네 컬럼으로 고정하고, 태그 메타(설비 · 단위 · 상하한)는 별도 sensor_tag 일반 테이블에 두어 조회 시 조인합니다.
    대가
    행 수가 태그 배수로 늘고, 한 시점의 여러 태그를 가로로 볼 때 FILTER 피벗이 필요합니다.
    재검토
    태그가 200개 미만으로 고정되고 조회의 80% 이상이 다중 태그 동시 조회가 되면 넓은 스키마를 재검토합니다.

    청크 인터벌을 6시간으로 정한 근거

    공식 기준은 "현재 적재 중인 청크의 인덱스가 shared_buffers 의 25% 안에 들어올 것"입니다7. 호스트 메모리 32GB · shared_buffers = 8GB 를 전제로 하면 한도는 2,048MB이고, (tag_id, time DESC) 인덱스는 행당 약 36B(키 12B + 아이템 포인터 · 페이지 여유)로 잡습니다.

    압축 전환을 미루면 디스크가 어떻게 되나

    일 10.4GB가 그대로 쌓이는 경우와, 8일이 지난 청크를 컬럼스토어로 전환해 90% 압축되는 경우를 비교합니다. 압축률은 데이터 형태에 따라 크게 달라지므로 여기서는 보수적으로 90%를 씁니다추정.

    ADR-02 · 청크 6시간 · 컬럼스토어 전환 8일 · 원본 보존 90일

    배경
    세 값은 서로 묶여 있습니다. 청크가 크면 인덱스가 메모리를 넘고, 전환이 이르면 지연 데이터가 압축 청크를 때리고, 보존이 길면 디스크가 모자랍니다.
    결정
    청크 인터벌 6시간(하루 4청크), 컬럼스토어 전환 8일(지연 상한 7일 + 1일), 원본 보존 90일, 1분 집계 2년, 1시간 집계 5년.
    대가
    하루 4개씩 90일이면 청크가 360개입니다. 전 구간을 훑는 쿼리는 청크 수만큼 계획 부담이 늘므로, 대시보드 조회는 반드시 연속 집계를 보게 합니다.
    재검토
    평균 적재율이 4,000행/초를 넘거나 shared_buffers 가 바뀌면 청크 인터벌을 다시 산출합니다. 게이트웨이 로컬 버퍼가 7일보다 커지면 전환 기준을 함께 미룹니다.
    01-schema.sql — 이 문서의 핵심 산출물
    -- 확장은 데이터베이스마다 한 번. shared_preload_libraries 에 timescaledb 가
-- 올라가 있지 않으면 이 줄에서 바로 실패한다(7절 "자주 나는 오류" 참고).
CREATE EXTENSION IF NOT EXISTS timescaledb;

-- 태그 메타. 일반 테이블이다 — 행이 2,000개뿐이고 시계열이 아니다.
CREATE TABLE sensor_tag (
    tag_id     INT         PRIMARY KEY,
    equip_code TEXT        NOT NULL,
    name       TEXT        NOT NULL,
    unit       TEXT        NOT NULL,
    min_value  DOUBLE PRECISION,
    max_value  DOUBLE PRECISION
);

-- 원본 계측값. 2.20.0 부터는 CREATE TABLE 한 문장으로 하이퍼테이블이 된다.
-- 그 이전 버전이면 일반 테이블을 만든 뒤 create_hypertable() 로 변환한다.
CREATE TABLE sensor_reading (
    time     TIMESTAMPTZ      NOT NULL,   -- 계측 시각. UTC 로만 저장한다
    tag_id   INT              NOT NULL REFERENCES sensor_tag(tag_id),
    value    DOUBLE PRECISION NOT NULL,
    quality  SMALLINT         NOT NULL DEFAULT 0  -- 0=정상, 1=센서이상, 2=보정값
) WITH (
    tsdb.hypertable,
    tsdb.partition_column = 'time',
    tsdb.chunk_interval = '6 hours',   -- 위 산출 근거 참고
    tsdb.segmentby = 'tag_id',            -- 압축 시 태그별로 묶는다
    tsdb.orderby   = 'time DESC'
);

-- 멱등 적재의 근거. 하이퍼테이블의 유니크 인덱스는 파티셔닝 컬럼(time)을
-- 반드시 포함해야 한다. tag_id 단독 유니크는 생성 자체가 거부된다.
CREATE UNIQUE INDEX sensor_reading_uq
    ON sensor_reading (tag_id, time);

-- 검증 실패 격리. 시계열이 아니라 운영자가 들여다보는 표라 일반 테이블로 둔다.
CREATE TABLE sensor_reject (
    id         BIGSERIAL   PRIMARY KEY,
    received_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    payload    JSONB       NOT NULL,
    reason     TEXT        NOT NULL
);
    02-policies.sql — 압축 · 보존 · 집계
    -- 1) 컬럼스토어 전환: 8일이 지난 청크를 열 지향으로 재배치한다.
--    add_columnstore_policy 는 2.18.0 부터의 이름이다. 그 이전 버전 문서에서
--    보이는 add_compression_policy 와 같은 일을 한다.
CALL add_columnstore_policy('sensor_reading', after => INTERVAL '8 days');

-- 2) 원본 보존: 90일이 지난 청크를 통째로 DROP 한다.
--    DELETE 가 아니라 청크 삭제라 VACUUM 부담이 없다.
SELECT add_retention_policy('sensor_reading', drop_after => INTERVAL '90 days');

-- 3) 1분 집계. materialized_only = false 로 두면 아직 집계되지 않은
--    최근 구간을 원본에서 실시간으로 메워 조회한다.
CREATE MATERIALIZED VIEW reading_1m
WITH (timescaledb.continuous, timescaledb.materialized_only = false) AS
SELECT time_bucket(INTERVAL '1 minute', time) AS bucket,
       tag_id,
       avg(value)   FILTER (WHERE quality = 0) AS avg_value,
       min(value)   FILTER (WHERE quality = 0) AS min_value,
       max(value)   FILTER (WHERE quality = 0) AS max_value,
       count(*)                                AS sample_cnt,
       count(*)     FILTER (WHERE quality <> 0) AS bad_cnt
FROM sensor_reading
GROUP BY bucket, tag_id
WITH NO DATA;   -- 생성 시점에 90일치를 한 번에 계산하면 DB 가 멎는다

-- end_offset 5분: 아직 들어오는 중인 최근 5분은 건드리지 않는다.
-- start_offset 3시간: 그 이전 3시간은 매번 다시 계산해 지연 도착분을 반영한다.
SELECT add_continuous_aggregate_policy('reading_1m',
    start_offset      => INTERVAL '3 hours',
    end_offset        => INTERVAL '5 minutes',
    schedule_interval => INTERVAL '1 minute');

-- 4) 1시간 롤업. 원본이 아니라 1분 집계를 다시 집계한다(계층 연속 집계).
CREATE MATERIALIZED VIEW reading_1h
WITH (timescaledb.continuous) AS
SELECT time_bucket(INTERVAL '1 hour', bucket) AS bucket,
       tag_id,
       avg(avg_value) AS avg_value,
       min(min_value) AS min_value,
       max(max_value) AS max_value,
       sum(sample_cnt) AS sample_cnt
FROM reading_1m
GROUP BY 1, 2
WITH NO DATA;

SELECT add_continuous_aggregate_policy('reading_1h',
    start_offset      => INTERVAL '1 day',
    end_offset        => INTERVAL '1 hour',
    schedule_interval => INTERVAL '10 minutes');

-- 5) 집계 테이블에도 보존을 건다. 원본 90일 < 1분 2년 < 1시간 5년.
SELECT add_retention_policy('reading_1m', drop_after => INTERVAL '2 years');
SELECT add_retention_policy('reading_1h', drop_after => INTERVAL '5 years');

    함수 이름과 인자는 TimescaleDB 2.29.2 기준입니다123456. 압축 정책 함수가 CALL 이고 나머지가 SELECT 인 것은 오타가 아니라 실제로 프로시저와 함수로 나뉘어 있기 때문입니다.

    경계 조건

    상황그대로 두면대응
    지연 데이터가 압축된 청크로 도착세그먼트 감압 · 재삽입이 반복되어 적재가 느려지고, 삽입분이 압축되지 않은 채 남아 청크가 부푼다전환 기준(8일)을 지연 상한(7일)보다 뒤에 둔다. 그래도 들어온 구간은 convert_to_columnstore 로 야간에 재압축
    같은 (tag_id, time) 재전송같은 시점 값이 2행이 되어 평균이 흔들린다UNIQUE (tag_id, time) + ON CONFLICT DO NOTHING. 하이퍼테이블 유니크 인덱스는 파티셔닝 컬럼 time 을 반드시 포함해야 한다8
    시간대 · 서머타임로컬 시각으로 저장하면 집계 버킷이 겹치거나 비어 하루치가 어긋난다저장은 전부 timestamptz(UTC). 일 단위 집계에서만 time_bucket(INTERVAL '1 day', time, 'Asia/Seoul') 로 시간대를 명시
    보존 잡이 집계 갱신보다 먼저 실행원본 청크가 사라진 구간이 집계에 영구적인 구멍으로 남는다보존 기준(90일)을 집계 start_offset(3시간)보다 훨씬 크게 두고, 두 잡의 next_start 를 timescaledb_information.jobs 로 확인
    백그라운드 워커 부족압축 · 보존 · 집계 잡이 대기열에 밀려 조용히 실행되지 않는다. 디스크가 찰 때까지 아무도 모른다timescaledb.max_background_workers = DB 수 + 동시 실행 잡 수. 잡별 마지막 성공 시각을 경보로 감시
    품질 코드 무시센서 이상값 · 보정값까지 평균에 섞여 지표가 낮게 나온다집계에 FILTER (WHERE quality = 0) 을 걸고, 제외 건수를 bad_cnt 로 함께 남긴다
    초기 백필과 실시간 적재 경합과거 데이터 대량 투입이 현재 청크의 인덱스를 밀어내 실시간 지연이 튄다백필은 야간에 COPY 로 청크 단위 진행. 백필 구간의 압축 정책은 백필이 끝난 뒤 건다
    값 정밀도계측값을 numeric 으로 두면 저장과 집계 비용이 몇 배가 된다계측값은 double precision 유지. 정산 · 과금에 쓰이는 파생값만 numeric 으로 별도 저장

    착수 전 체크 0 / 0

    • 규모 전제 표의 가정값을 수집망 실측으로 교체태그 수 · 주기 · 피크 배수. 이 값이 청크 인터벌을 결정한다

    @Testcontainers
class SensorReadingIdempotencyTest {

    // 일반 postgres 이미지로는 CREATE EXTENSION 이 실패한다.
    @Container
    static final PostgreSQLContainer<?> DB = new PostgreSQLContainer<>(
            DockerImageName.parse("timescale/timescaledb:2.29.2-pg17")
                           .asCompatibleSubstituteFor("postgres"));

    @Test
    // SC-04: 같은 (tag_id, time) 재전송은 행을 늘리지 않는다
    void resentReading_doesNotDuplicateRow() {
        var t = OffsetDateTime.parse("2026-09-07T02:00:00Z");

        repo.insertBatch(List.of(reading(t, 101, 23.4)));
        repo.insertBatch(List.of(reading(t, 101, 99.9)));  // 값이 다른 재전송

        assertThat(jdbc.queryForObject(
                "SELECT count(*) FROM sensor_reading WHERE tag_id = 101", Long.class))
                .isEqualTo(1L);
        assertThat(jdbc.queryForObject(
                "SELECT value FROM sensor_reading WHERE tag_id = 101", Double.class))
                .isEqualTo(23.4);   // DO NOTHING 이므로 먼저 온 값이 남는다
        assertThat(meter.count("sensor.reading.duplicate")).isEqualTo(1);
    }
}

    성공 판정

    make seed 를 두 번 돌린 뒤 make verify 의 행 수가 72,005행 그대로이고(늘어나면 멱등 적재 실패), 청크가 41개 안팎으로 나뉘어 있고, make compress && make size 의 after 가 before의 20% 이하이면 S2와 S4가 정상입니다. 청크 수는 10일 ÷ 6시간 = 40에 현재 진행 중 청크 1개가 더해진 값입니다.

    자주 나는 오류

    확장 로드 실패 — command: 로 postgres 인자를 덮어쓰면서 shared_preload_libraries=timescaledb 를 빠뜨리면 CREATE EXTENSION 이 "must be loaded via shared_preload_libraries" 로 실패합니다.
    파라미터가 안 먹음 — 볼륨이 남아 있으면 init/ 스크립트가 다시 돌지 않습니다. 스키마를 고쳤으면 make down(볼륨 삭제) 후 다시 올리십시오.

    09전환과 롤백

    기존에 쌓이던 일반 테이블이 있다면 그 위에서 바로 변환하지 않습니다. 새 테이블에 이중 적재한 뒤 읽는 쪽을 옮깁니다.

    1
    이중 적재
    수집 API가 기존 테이블과 sensor_reading 양쪽에 쓴다. 읽기는 아직 기존 테이블
    2
    과거 데이터 백필
    야간에 COPY 로 일 단위 이관. 백필 구간에는 압축 정책을 아직 걸지 않는다
    3
    결과 대조
    일별 행 수와 태그별 평균을 양쪽에서 비교. 3일 연속 불일치 0건
    4
    읽기 전환
    대시보드와 조회 API가 연속 집계를 보게 한다. 기존 테이블 쓰기는 유지
    5
    정리
    2주 안정 후 압축 · 보존 정책을 켜고 기존 테이블 쓰기를 끊는다

    롤백 기준

    읽기 전환(4단계) 후 24시간 안에 적재 p99가 2초를 3회 이상 넘거나 대조 불일치가 1건이라도 나오면, 기능 플래그 sensor.store.timescale.read-enabled=false 로 조회를 기존 테이블로 즉시 되돌립니다. 쓰기는 양쪽 모두 유지하므로 데이터는 삭제하지 않습니다.
    되돌릴 수 없는 지점은 5단계입니다. 보존 정책이 한 번 돌아 원본 청크가 삭제되면 그 구간은 복구되지 않습니다. 5단계 전에 백업 복원 리허설을 한 번 마쳐야 합니다.
