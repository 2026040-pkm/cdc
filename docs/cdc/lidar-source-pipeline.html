LiDAR 소스 적재 경로

v1.0 · 2026-09-11 · cdc

    Data Flow Document

    LiDAR 필드 데이터가 소스 DB 에 닿기까지

    장비에서 나온 값 하나가 MQTT 토픽 · Agent 태그 · Kafka 레코드를 거쳐 소스 DB 의 행 하나가 되기까지를 단계마다 필드 단위로 적는다. 알갱이가 단계마다 바뀌므로 "무엇이 하나로 세어지는가"를 각 절의 첫 표에 먼저 둔다.

    장비 350대 MQTT 토픽 22 · 태그 2,520 Kafka 토픽 3 소스 DB 표 9개 미확정: 페이로드 규격 · 발행 주기

    00범위와 전제

    경계를 먼저 못 박는다. 이 문서는 소스 DB 에 행이 들어가는 순간까지이고, 그 뒤는 다른 문서다.

    이 문서가 다루는 구간

    • 장비가 만드는 값과 그 필드 정의 (세 채널)
    • MQTT 브로커의 토픽 22개와 메시지 봉투
    • Mqtt.Agent 의 태그 2,520개와 태그 하나의 값
    • EES Kafka Provider 가 만드는 레코드 · 헤더 11개 · 항목 배열
    • 소비자가 그 레코드를 풀어 소스 DB 표 9개에 넣는 과정

    다루지 않는 것

    • 소스 DB 이후 구간 — CDC 로 targetdb 까지 가는 길9
    • 보존 · 압축 · 용량 추정 — 파이프라인 기술 문서10
    • PCD 파일 본체 전송 — 선로에는 경로와 체크섬만 실린다
    • Grafana 대시보드와 경보 임계

    전제 — Provider 선택이 이 문서의 모든 모양을 정한다

    지금 InterSysLink 에는 hot DB Provider 역할이 없다. 그래서 태그 값을 밖으로 내보내는 통로를 EES Kafka Provider 하나로 잡았다. 아래에 나오는 세 가지는 전부 그 선택에서 따라 나온 결과다. DB Provider 였다면 어느 것도 생기지 않는다.
    • MQTT 토픽 22개가 Kafka 토픽 3개로 접힌다 — 채널마다 EES 메시지가 하나씩이기 때문이다.
    • 메시지 하나가 레코드 하나가 아니다. 항목 수백 개가 묶여 레코드 하나가 된다.
    • 장비 id 가 선로에서 사라진다 — Provider 가 문자열 TagId 를 버리고 숫자 ParameterId 만 싣는다.

    Aspire 를 띄우지 않을 때

    util/mqtt-ees-bridge 가 Agent + Provider 자리를 대신한다. 같은 헤더 11개, 같은 항목 모양, 같은 토픽 이름으로 Kafka 를 채우므로 수신 측은 원본과 이것을 구분하지 못한다 — 구분할 근거가 레코드에 없다.3 이 문서의 값은 두 경로 모두에 그대로 적용된다.

    01전체 워크플로우

    박스를 끌어 배치를 바꿀 수 있다. 확정된 배치는 JSON 버튼으로 내보내 이 파일의 dgm-data 블록에 되붙인다.

    레코드 수와 행 수를 섞어 읽지 않는다

    Kafka 구간만 레코드로 세고 나머지는 전부 건수로 센다. 이 한 줄을 놓치면 "초당 3건"과 "초당 426건"이 같은 파이프라인의 같은 지점을 가리키는 것처럼 보인다. 발행 주기(1초 · 1분)는 레코드 빈도가 아니라 항목의 timestamp 에 남으므로, DB 에서는 원래 주기가 그대로 보인다.

    03MQTT 브로커의 토픽과 메시지

    토픽 이름이 곧 태그 이름의 한 조각이 된다. 여기서 정한 문자열이 끝까지 따라간다.

    메시지 봉투는 세 채널이 같다

    Agent 의 계약(Mqtt.Agent.Core.Domain.MqttPayloadParser)이 받는 형식 그대로, id 와 raw_payload 한 겹뿐이다. 필드 정의서의 중첩 객체는 브로커로 나갈 때 평탄화한다 — 중첩을 두면 나중에 tagMode=fields 로 바꿨을 때 키 이름이 달라지기 때문이다.

    토픽 22개

    채널마다 토픽 모양이 다르다. 상태는 구역으로, 실적은 공정으로, 산출물은 공장·베이로 갈린다. 한 장비의 태그가 그 구역의 공정 토픽 전부에 걸린다 — 스캔마다 stage 가 바뀌기 때문이다.

    채널토픽 패턴토픽 수실제 토픽토픽당 태그
    상태ot/device/{zone}/lidar/status2.../assembly/... · .../outfitting/...210 · 140
    실적ot/sensor/{stage}/actual6arrangement · fitting · welding · inspection · wiring · piping210 ×4 · 140 ×2
    산출물ot/pipeline/{zone}/{shop}/{bay}/artifact14assembly1/bay1~7 · outfitting1/bay1~790 · 60

    산출물 토픽의 태그 수가 장비 수의 3배인 것은 장비 하나가 종류마다 다른 id 로 발행하기 때문이다 (-REGISTERED_PCD · -TRANSFORMATION_MATRIX · -SEGMENTED_PCD). 조립 bay 하나에 30대이므로 90개다.

    브로커 포트

    이 저장소 주변에 MQTT 를 받는 컨테이너가 셋이다. mqtt-emqx = 1884, mqtt-mosquitto = 1883, mqtt-nats = 1885. 기본값은 EMQX(1884)다.

    프로토콜 3.1.1 고정

    MqttNetSession.BuildOptions 와 같은 조건으로 붙기 위해서다. v5 로 붙으면 브로커가 CONNACK 0x01 로 즉시 끊는다.

    04Mqtt.Agent 의 태그와 그 값

    Agent 는 메시지를 저장하지 않는다. 토픽과 장비를 태그 하나로 접고, 그 태그의 값만 갱신한다.

    태그 하나가 무엇인가

    태그 id 는 세 조각이다 — 토픽의 / 는 _ 로 접힌다. 세 채널 모두 tagMode=raw 라 raw_payload 객체 통째가 태그 하나의 STRING 값이 된다. 필드마다 태그를 만들지 않는다.

    태그 한 줄이 만들어지는 규칙
    # 들어온 MQTT 메시지
토픽   ot/device/assembly/lidar/status
본문   {"id": "LDR-GJ-A1B3-07", "raw_payload": { ... }}

# Agent 안에서
TagId      LDR-GJ-A1B3-07.ot_device_assembly_lidar_status.raw_payload
           └ 장비 id ────────┘ └ 토픽(/ 를 _ 로) ──────────┘ └ 필드 ┘
dataType   STRING
value      {"device_role":"LIDAR","site":"geoje", ... }   # JSON 문자열 통째
changedAt  raw_payload.occurred_at                        # 도착 시각이 아니다

    태그 등록 — 파일 하나가 토픽 하나

    UI 의 MQTT 태그 가져오기는 한 파일이 정확히 한 토픽을 설명한다. 그래서 22개 토픽이면 CSV 22장이다. 발행기의 --export-tags 가 발행 토픽에서 그대로 뽑는다 — 발행기와 태그 목록을 따로 관리하면 반드시 어긋나므로 출처를 하나로 뒀다.1

    FITTING 210개가 등록부에 없다

    조립 공정 4종 중 ot/sensor/fitting/actual 만 태그 등록이 빠져 있다. 그래서 조립 210대의 FITTING 실적이 InterSysLink 에서는 조용히 사라진다 — 등록 2,310 = 350 + 910 + 1,050 이고 실적은 1,120 이어야 하므로 차이 210 이 그대로 FITTING 이다. 브리지로 돌릴 때는 기본값(AUTO_REGISTER_TAGS=true)이 900000번부터 번호를 새로 매겨 살려 보내고, 그 사실이 ees_bridge_tag_unregistered_total 에 남는다.3

    TagId 100자 상한

    Engine 의 TagCatalogId 컬럼 제약이자 MqttTagId.MaxLength 다. 산출물 채널은 id 에 -TRANSFORMATION_MATRIX 가 붙고 토픽에 shop·bay 까지 들어가 현재 최대 97자로 여유가 3자뿐이다. shop·bay 이름을 늘리면 넘치고, 넘친 태그는 내보내기에서 제외된다.

    05Kafka Provider 가 내보내는 레코드

    여기서 알갱이가 바뀌고 장비 id 가 사라진다. 이 절이 이 문서에서 가장 중요한 구간이다.

    태그 값 하나가 레코드에 실리기까지

    MQTT 토픽 22개가 Kafka 토픽 3개로 접힌다

    EES 메시지 하나가 Kafka 토픽 하나이고, 채널마다 메시지를 따로 만들어 두었다 (msgHeaderFormat.topic.send_topic). 그래서 토픽 하나에 채널 하나가 실린다 — 수신 측이 채널을 토픽 이름의 마지막 마디로 판정할 수 있는 근거가 이것이다.

    Kafka 토픽묶어 온 MQTT 토픽레코드/초항목/레코드항목/초
    ot.lidar.statusot/device/{zone}/lidar/status (2개)1350350
    ot.lidar.artifactot/pipeline/{zone}/{shop}/{bay}/artifact (14개)17070
    ot.lidar.actualot/sensor/{stage}/actual (6개)166

    MQTT 메시지 하나가 Kafka 레코드 하나가 아니다. 채널마다 따로 묶어 항목 500개 또는 1초 중 먼저 오는 쪽에서 끊는데, 지금 유량에서는 늘 시간 쪽이 먼저다. 그래서 토픽마다 초당 레코드 하나가 나가고, 채널 차이는 레코드당 항목 수로 나타난다. 1분 주기인 실적·산출물이 한 번에 터지지 않는 것은 발행기가 장비마다 시작을 밀어 두기 때문이다(offset = interval × index / 350).3

    레코드의 모양

    ot.lidar.status — 레코드 1개 (Key = "ot.lidar.status")
    // 헤더 11개 (Kafka 메시지 헤더)

infra_proc_name = ot.lidar.status

message_version = 1.0
msg_timestamp   = 1789012763360318900    // 레코드를 만든 시각의 ns epoch
uniqueid        = 3f0c...                // 레코드마다 새 GUID

// 본문 — 항목 350개의 배열
[{"content": {"timestamp": 1789012763353205000,          // raw_payload.occurred_at 의 ns epoch
              "tid": "1",                                 // 숫자 ParameterId. TagId 가 아니다
              "value": "{\"device_role\":\"LIDAR\",...}",  // raw_payload 통째의 JSON 문자열
              "pm_mode": false}},
 ... 349건 더 ...]

    장비 id 가 선로에서 사라진다 — 이 문서에서 가장 자주 발이 걸리는 지점

    Provider 는 태그를 실을 때 문자열 TagId 를 버리고 등록부의 ParameterId(숫자) 만 싣는다 (ValueMessageFormatterV1_0). 그리고 raw_payload 안에도 장비 id 필드가 없다. 즉 Kafka 만 읽어서는 어느 장비인지 알 수 없다. 되돌리는 유일한 근거가 등록부 사본(rdb.lidar_tag_catalog)이다.
    숫자를 장비로 되돌리는 길
    MQTT   {"id": "LDR-GJ-A1B3-07"}  on  ot/device/assembly/lidar/status
  TagId    LDR-GJ-A1B3-07.ot_device_assembly_lidar_status.raw_payload
  조회표   (send_topic "ot.lidar.status", param_id 1)
  tid      "1"        # Kafka 에는 이것만 실린다

    조회 키가 (토픽, 숫자)인 이유

    ParameterId 는 워크플로우·PType 안에서만 1부터 매기는 일련번호다. 메시지가 다르면 같은 숫자가 다른 태그를 가리킬 수 있다. 그래서 param_id 단독이 아니라 (send_topic, param_id) 가 기본 키다.5

    토픽이 파티션 1개인 것은 설정 실수가 아니다

    Provider 는 Kafka Key 를 정규화한 project_id 로 쓰는데 그 값이 채널마다 상수다. 파티션을 늘려도 레코드는 전부 한 파티션에 간다 — 계약의 성질이다.

    필드가 컬럼에 앉는 규칙

    컬럼 이름은 raw_payload 의 키를 그대로 쓴다. 이름을 바꾸면 필드 정의서와 대조가 안 된다. 예외는 넷뿐이다.

    컬럼원본왜 이름이 다른가
    timeraw_payload.occurred_at하이퍼테이블의 파티션 컬럼. 도착 시각이 아니라 장비 발생 시각이라야 늦게 온 항목도 제 자리에 들어간다
    tid조회표가 푼 장비 id못 풀면 #2257 로 남는다 — 틀린 장비를 지어내지 않는다
    tag_id조회표의 문자열 TagId선로에는 실리지 않는 값이라 별도 컬럼
    param_idcontent.tid실려 온 숫자를 그대로 보존한다

    나머지는 json_populate_recordset 이 JSON 키를 컬럼에 맞춰 캐스팅한다. timestamptz 문자열은 PostgreSQL 이 직접 파싱하므로(7자리 소수초도 받는다) 파이썬에서 날짜를 다루지 않는다. 여기에 더해 content_ts(= content.timestamp), pm_mode, kafka_offset, received_at 이 붙는다.

    중복과 유실을 무엇이 막는가

    중복 — 유니크 인덱스

    MQTT 는 QoS 1, Kafka 는 at-least-once 라 재전달이 온다. 세 하이퍼테이블 모두 (idempotency_key, time) 유니크 인덱스를 두고 ON CONFLICT DO NOTHING 으로 넣는다. 하이퍼테이블의 유니크 인덱스는 파티션 컬럼을 반드시 포함해야 해서 time 이 같이 들어간다.

    유실 — 커밋 순서

    DB 트랜잭션이 커밋된 뒤에만 Kafka 오프셋을 커밋한다. DB 쓰기가 실패하면 오프셋을 커밋하지 않고 같은 배치를 다시 시도한다. 순서가 뒤집히면 실패한 배치가 조용히 사라진다.

    스키마 둘로 가른 선

    rdb / tsdb — CDC 가 성립하는가로 가른다

    하이퍼테이블은 청크가 주기마다 새 표로 생기고, 압축이 행을 내부 청크로 옮기며, 보존이 청크째 DROP 한다. 어느 것도 행 단위 INSERT/UPDATE/DELETE 로 보이지 않아 논리 복제가 성립하지 않는다. 그래서 이 DB 의 진짜 경계를 주석이 아니라 스키마로 두었다 — publication 에 하이퍼테이블이 실수로 끼어드는 것을 구조가 막는다. CDC 로 나가는 것은 rdb 의 여섯 표뿐이고, 그 뒤 구간은 별도 문서다.9

    07경계 조건과 지금 어긋나 있는 것

    지금 돌려 보면 실제로 나오는 것들이다. 모르고 보면 데이터가 맞는 것처럼 읽힌다.

    상황그대로 두면대응
    실적·산출물의 tid 를 조회표가 못 푼다실적은 장비 축이 전부 틀리고 산출물은 대부분 틀린다. 상태 채널만 멱등 키에서 장비를 되찾을 수 있다조회표를 먼저 채운다. 못 풀면 #숫자 로 남겨 미해석을 눈에 보이게 둔다
    FITTING 태그 미등록조립 210대의 FITTING 실적이 ISL 에서 조용히 사라진다등록부에 추가. 브리지 경로는 AUTO_REGISTER_TAGS 로 살려 보내고 지표에 남긴다
    같은 블록이 한 배치에 여러 번산출물은 한 스캔이 12건을 낸다. 그대로 UPSERT 하면 cannot affect row a second time 으로 배치가 통째로 죽는다배치 안에서 먼저 블록 축으로 합친 뒤 넣는다. 합치는 규칙이 SQL 쪽과 같아야 한다
    늦게 온 재전달오래된 상태가 최신 값을 덮는다최신 값 컬럼만 last_event_at 비교로 막는다. 누계는 조건 없이 더하고 마일스톤은 GREATEST 로 민다
    Kafka 토픽을 지웠다브로커가 auto.create.topics.enable=false 라 초당 426건이 계속 들어와도 토픽이 돌아오지 않는다. 실행 중 삭제는 produce() 가 예외를 내지 않고 전달 콜백으로만 온다브리지가 기동할 때와 송신 실패 때 직접 만든다. 복구는 그 채널의 다음 발행 때(1분 주기면 최대 1분)
    브리지·소비자가 죽어 있는 동안MQTT 는 clean session 이라 그동안 온 메시지를 잃는다. Kafka 구간은 오프셋이 남아 다시 읽는다브로커 큐(EMQX 기본 1000)를 금방 넘기므로 쌓다 버리는 대신 흘려보내는 쪽을 택했다. MQTT_CLEAN_SESSION=false 로 바꿀 수 있다
    replication slot 을 둔 채 CDC 를 안 쓴다슬롯은 만료되지 않는다. 붙잡은 WAL 이 계속 쌓여 이 DB 디스크가 고갈된다SELECT pg_drop_replication_slot('embedded_cdc_slot');
    배치 창을 줄인다항목 수는 그대로인데 레코드가 잘아져, 레코드 수로 눈금을 잡아 둔 Kafka 지연 경보의 의미가 달라진다BATCH_MAX_WAIT_MS 를 바꾸면 경보 임계도 같이 본다
