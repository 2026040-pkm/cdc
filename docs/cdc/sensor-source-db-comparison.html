    이번 기본 비교는 이 세 측정값을 모두 저장하고 HANA에도 모두 보낸다는 가정입니다. 최신값 22도만 보내는 경우는 뒤에서 따로 설명합니다.

    TSDB

    시간에 따라 쌓이는 측정 이력을 저장·조회하는 DB.
    여기서는 과거 이력을 압축해 보관하는 역할입니다.

    RDB

    일반 테이블에 데이터를 저장하는 DB.
    센서 원본을 보관하거나 CDC 전달용으로 잠시 보관합니다.

    CDC

    DB에 저장된 변경을 읽어 다른 DB로 전달하는 기능.
    저장용 DB 자체가 아닙니다.

    제품 예시는 현재 프로젝트의 TimescaleDB와 PostgreSQL입니다. 제품이 달라지면 압축·CDC 지원 범위도 달라집니다.

    ②의 두 DB를 같은 서버에 두면?

    역할은 나뉘어도 CPU와 디스크는 함께 사용합니다. TSDB의 압축 작업이 RDB 쓰기와 CDC에 영향을 줄 수 있습니다. 별도 서버로 나누면 자원을 분리할 수 있지만, 두 곳 중 한 곳에만 저장된 실패를 복구하는 처리가 필요합니다.

    02압축 효과는 “RDB에 얼마나 남기느냐”에 달립니다

    질문하신 우려는 두 곳에 같은 원본을 오래 보관하는 경우에 해당합니다. TSDB 쪽은 압축되지만 RDB 원본이 그대로 남아 전체 저장량은 커집니다.

    같은 조건으로 보는 계산 예시 — 실측 아님

    하루 비압축 데이터 100 GB, 보관 30일, 최근 3일은 비압축, 나머지는 10배 압축한다고 가정합니다. RDB도 같은 비압축 크기로 계산합니다. 로그·백업·복제본은 제외합니다.
    저장 방식계산총량
    ① TSDB 30일최근 300 + 과거 2,700 ÷ 10570 GB
    ② TSDB 30일 + RDB 2일570 + 200770 GB
    ② TSDB 30일 + RDB도 30일570 + 3,0003,570 GB
    ③ RDB 30일100 × 303,000 GB

    ②에서 RDB를 짧게 보관하면 압축 이점을 살릴 수 있습니다.
    다만 두 곳에 저장하는 쓰기 작업은 여전히 발생합니다. “공간 절약”과 “쓰기 부하 감소”는 다른 문제입니다.

    ③에서 RDB를 2일만 보관한다면 200 GB면 됩니다. 하지만 원천에 30일 이력이 남지 않으므로 위 30일 보관 구성과 같은 기능은 아닙니다.

    내 센서 수와 보관 기간으로 직접 계산하기

    가정 기반 예시 · 실측 아님 단위: 1 GB = 10⁹ bytes. 행 폭은 메시지 크기가 아니라 테이블·인덱스를 포함한 평균 비압축 bytes/행입니다. 압축 배수도 같은 기준으로 측정합니다.

    시나리오Source 데이터 용량해석

    계산식

    λ = N × f 행/s
    G = λ × 86,400 × b / 10⁹ GB/일
    S_TSDB = G × [min(H,D) + max(D−H,0)/C]
    S_B2 = S_TSDB + G × R
    S_RDB = G × D

    정상 상태 단순 근사. TSDB/RDB 비압축 행 폭이 같다는 가정이며 실제 버퍼 스키마가 다르면 별도 행 폭을 사용합니다. 청크 경계와 정책 실행 시각에 따라 압축 전환이 늦어질 수 있습니다.

    데이터 표에 포함되지 않은 추가 WAL 여유분입니다. 동일 인스턴스 슬롯이 막히면 CDC 대상 외 쓰기도 공유 WAL 보관량에 영향을 줄 수 있습니다. 여러 슬롯의 보유 구간은 겹치므로 단순 합산하지 않습니다.

    기본값: 350행/s, 하루 3,024만 행, 9.072 GB/일. A 51.7104 GB, B2 69.8544 GB, 전기간 중복 323.8704 GB, C 전기간 272.16 GB. WAL·복제본·백업·집계 표·임시 공간·bloat·운영 여유는 별도입니다. B1 상태 크기는 센서/태그 수로 따로 산정하고 메시지 원장·격리 표는 기간 증가분을 더합니다.

    04현재 조건에서 무엇을 먼저 검토할까?

    원하는 것우선 검토할 구성이유
    원천에서도 오랜 센서 이력을 조회해야 함② TSDB 장기 + RDB 단기압축 조회와 CDC 전달을 함께 충족
    원천은 전달·재전송 역할이면 충분함③ RDB 단기 보관별도 TSDB를 운영할 이유가 적음
    원본을 한 곳에만 저장하면서 TSDB 기능도 필요함① TSDB 직접 CDC사용 버전의 압축·재시작·복구 검증을 먼저 통과해야 함

    현재 프로젝트는 “전체 원본 전달”과 다릅니다

    현재 코드는 TSDB에 이력을 저장하고, RDB의 상태·대장 등을 CDC로 전달합니다. TSDB의 센서 원본 전체가 HANA로 넘어가는 구조는 아닙니다. 원본 전량이 필요하면 ②의 RDB에도 측정값마다 별도 행을 남기는 전달용 테이블이 필요합니다.

    HANA에 최신값만 필요하다면?

    20도 → 21도 → 22도 중 22도만 필요하면 RDB는 최신 상태를 보관하는 역할을 할 수 있습니다. 반대로 HANA에서도 온도 변화 이력을 보려면 세 측정값을 모두 전달해야 합니다. 이 둘을 같은 구성으로 비교하면 용량과 부하 판단이 달라집니다.

    상태 표가 작아도 매초 UPDATE하면 CDC 변경은 계속 생깁니다. 상태 표 크기가 작다는 이유만으로 CDC 부하까지 작다고 볼 수는 없습니다.

    05압축·장애에 관한 세부 근거

    여기부터는 구현을 검토할 때 필요한 상세 내용입니다. 앞의 구성 선택을 이해한 뒤 필요한 항목만 펼쳐 보면 됩니다.

    TSDB 압축이 CDC에서 왜 문제가 될 수 있는가

    PostgreSQL 로그 기반 CDC는 테이블을 계속 전체 조회하는 방식이 아니라 WAL을 해석합니다.3 저장 압축률과 CDC 변경 건수·전송량은 별개입니다. 디스크를 10분의 1로 줄여도 원본 이벤트 전송량이 자동으로 10분의 1이 되지는 않습니다.

    오래된 프로젝트 문서의 “압축이 대량 DELETE로 전달”된다는 설명은 2026-09-17 실험에서 정정됐습니다. 압축은 논리 데이터 삭제가 아닌 저장 표현 변경입니다. 이번에는 기존 실험을 재실행하지 않았습니다.

    A의 채택 조건은 신규 청크, 압축·재압축, 과거 지연 INSERT/UPDATE/DELETE, 보존 만료, CDC 중단·재개, 압축 이력 초기/재스냅샷 검증입니다. “최근 데이터만 캡처 후 나중에 압축”은 경합을 줄일 수 있지만 호환성을 대신 보장하지 않습니다.

    RDB 데이터는 언제 지워도 되는가 / CDC 중단 시 어떻게 복구하는가
    항목설계 기준
    B2 전달 테이블event_id, sensor_id, event_time, ingested_at, payload/version을 가진 append 중심 일반 테이블. 안정적인 키로 재전송 중복 제거
    같은 인스턴스의 BTSDB 원본과 RDB 전달 행을 한 트랜잭션으로 커밋 가능. 자원·장애는 공유
    별도 인스턴스의 B내구성 있는 입력 로그의 독립 소비 또는 outbox/재시도·대사. 단순 두 번 INSERT는 원자성 보장 불가
    버퍼 기간최대 장애 + 적체 해소 + 재조회/복구 여유. 예시 2일은 운영 확정값이 아님
    버퍼 정리시간 만료 + downstream 내구성 완료 지점 확인. 슬롯 ack가 HANA 커밋을 의미하는지는 커넥터 설계에 따라 다름
    Source 보존 삭제업무 삭제와 구분. 행 DELETE를 그대로 전파하면 HANA 이력도 지워질 수 있음
    파티션 DROP행 DELETE와 다른 DDL. Target 보존 자동 동기화 가정 금지. 신규 파티션 캡처 확인4
    로그 유실·재스냅샷남은 Source 데이터만 복원. B2는 TSDB 백필과 CDC 경계 연결 필요. C는 별도 원본 없이 삭제 이력 복구 불가
    시각·순서센서 event_time과 수신 ingested_at 분리. 지연 도착 때문에 event_time만으로 전달 완료 판단 금지

    WAL 한도는 디스크 고갈을 막지만 무손실을 자동 보장하지 않습니다. 필요한 로그가 사라지면 재동기화가 필요합니다. 장애 중 WAL이 압축된 데이터보다 커질 수 있으므로 데이터 용량과 따로 관리합니다.3

    현재 프로젝트의 설정과 선택 기준

    src/timescaledb는 동일 인스턴스의 tsdb 하이퍼테이블과 rdb 일반 표를 분리하고 RDB 표만 publication에 넣습니다. B1에 가깝고 원본 전량 전달 B2와는 다릅니다. 상태·공정·산출물 대장 외 메시지 원장과 오류 격리 표도 있으므로 RDB 전체가 고정 크기는 아닙니다.6

    정책 파일은 원본 3일 이후 컬럼 저장 전환, 원본 31일 보관을 설정합니다. 계산기의 30일·10배 압축·2일 버퍼는 가정입니다. README의 350대·약 426 msg/s도 발행기 기본 모델이며 실측 DB 행/s가 아닙니다.6
