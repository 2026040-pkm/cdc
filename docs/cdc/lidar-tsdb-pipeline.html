    Technical Document

    OT LiDAR 필드 데이터 적재 파이프라인 · 기술 문서

    Mqtt.Agent 가 받은 LiDAR 350대의 세 채널이 EES Kafka Provider 를 거쳐 TimescaleDB 표 아홉 개에 담기기까지, 필드 하나까지의 계약과 실측치, 그리고 그 DB 를 CDC 원천으로 열었을 때의 경계를 정의합니다.

    2026-09-11 실측 장비 350대 · 태그 2,380 TimescaleDB 2.29 / PostgreSQL 17 미확정: 페이로드 규격 벤더 합의 전

    00범위와 전제

    목표 구조는 Mqtt.Agent → Engine → HotData Provider → HotData 입니다. 이 문서가 다루는 것은 그 구조의 Provider 자리에 EES Kafka Provider 를, 저장소 자리에 TimescaleDB 를 세워 먼저 돌려 본 판입니다. 두 자리를 바꿔 끼워도 앞단(Agent · Engine · 태그 등록)은 그대로이므로, 여기서 확인한 계약과 지연은 HotData 판으로 넘어갈 때 대부분 그대로 유효합니다.

    이 문서가 정의하는 것

    • MQTT 토픽 22개 → EES 메시지 3개 → Kafka 토픽 3개의 매핑과, 그 사이에서 무엇이 유실되는가
    • 세 채널 페이로드의 필드 단위 계약 — 누가 어떤 값을 채우고 어느 컬럼에 앉는가
    • TimescaleDB 표 아홉 개의 역할 분담과 청크 · 압축 · 보존 정책의 근거
    • 1개월 보존 조건에서의 실측 용량 · 압축비 · 지연
    • 이 DB 를 CDC 원천으로 열 때 넘을 수 있는 선과 넘을 수 없는 선

    이 문서가 다루지 않는 것

    • HotData Provider 자체의 설계 — 아직 구현체가 없습니다
    • 점군 파일(PCD) 본체의 저장 · 수명 관리. 메시지에는 storage_uri 만 옵니다
    • Mqtt.Agent · Engine 내부 구현. 계약 경계까지만 봅니다
    • 고가용성 구성(복제 · 페일오버). 단일 인스턴스 전제입니다

    전제 세 가지

    1. Kafka 는 이 스택이 띄우지 않습니다. Aspire(InterSysLink) 세션이 띄운 컨테이너를 네트워크에 붙여 씁니다 — 세션을 다시 띄웠으면 scripts/up 을 다시 돌려야 합니다. 2. 페이로드 규격은 필드 정의서의 제안 규격이며 ISL 벤더 합의 전입니다. 확정되면 컬럼과 빌더를 함께 고칩니다. 3. 발행 주기는 필드 인터페이스 정의서의 등급 주기 — 상태 1초 · 실적 10분 · 산출물 10분 — 으로 확정했습니다. 용량 산정(5.2)은 이미 이 주기로 했고, 지연 실측(5.1)은 발행기 기본값(스캔 1분)으로 잰 값입니다. 항목 하나가 지나는 경로는 주기와 무관하므로 지연은 그대로 유효하지만, 도착 패턴과 전송량은 달라집니다 — 3.2.2 와 5.4 에서 따로 답합니다.

    확인 필요 — 60초 스냅샷이 재전송을 만드는가

    FullBatch 는 변화 여부와 무관하게 태그 전량을 다시 싣습니다. 이론상 직전 ChangedBatch 가 이미 보낸 값과 겹쳐 멱등 인덱스가 걸러 낼 재전송이 60초마다 350건씩 생겨야 하지만, 관측 15분 동안 중복 스킵은 1건뿐이었습니다. 스냅샷이 실제로 재전송을 만드는지, 아니면 상태가 1초마다 바뀌어 늘 새 값으로 나가는지는 이번 관측으로 가르지 못했습니다. lidar_ingest_rows_duplicate_total 을 60초 주기와 겹쳐 보면 판정됩니다.

    4.2 저장 방식 비교

    방식장점단점1개월 보존 적합도
    일반 PostgreSQL추가 확장 없음. 운영 인력이 이미 안다31일치 349GB. 매일 3,000만 행 DELETE + VACUUM부적합 삭제 비용이 적재를 방해한다
    PostgreSQL + 선언적 파티셔닝DROP PARTITION 으로 삭제 비용 해결압축이 없어 용량 그대로. 파티션 생성 · 집계를 직접 만들어야 한다부분 삭제만 풀린다
    TimescaleDB청크 자동 생성 · 컬럼스토어 12.6배 · 청크 DROP 보존 · 연속 집계확장 의존. 하이퍼테이블은 CDC 원천이 될 수 없다적합 네 가지가 한 번에 풀린다
    전용 TSDB (InfluxDB 등)시계열 전용 최적화SQL 조인 불가에 가깝다. CDC · 기존 PostgreSQL 자산과 단절부적합 블록 · 호선 조인이 핵심 요구다

    ADR-01 · 센서 원문은 TimescaleDB 하이퍼테이블에 담고, CDC 대상에서 제외한다

    배경
    1개월 보존에서 용량 · 삭제 비용 · 집계 조회가 동시에 문제가 됩니다. 셋을 한 엔진에서 푸는 것이 TimescaleDB 이고, 그 대가로 청크 · 압축 · 보존이 행 단위 DML 로 보이지 않아 논리 복제가 성립하지 않습니다.
    결정
    원문 셋은 tsdb 스키마의 하이퍼테이블에 담고 publication 에 넣지 않습니다. 수신 측이 필요로 하는 것은 rdb 스키마의 유계 상태 표 셋으로 대신합니다.
    대가
    수신 측은 원문 시계열을 볼 수 없습니다. 원문이 필요하면 TimescaleDB 에 직접 조회하거나 적재 API 에서 분기해야 합니다.
    재검토
    수신 측이 원문 시계열을 요구하면 재검토합니다. 그때는 CDC 가 아니라 소비자에서 두 곳으로 쓰는(dual write) 쪽이 싼지 먼저 비교합니다.

    ADR-02 · 채널마다 표를 나누고 청크 간격을 따로 준다

    배경
    status 는 초당 350행, actual 은 10분당 350행입니다. 1,700배 차이입니다. 한 표에 담으면 청크 간격을 어느 쪽에 맞춰도 다른 쪽이 망가집니다.
    결정
    채널당 표 하나, 청크 간격은 status 6시간 · actual 1일 · artifact 6시간. 압축은 세 표 모두 3일 후, 보존은 31일로 같게 둡니다 — 셋 다 INSERT 만 있고 정정이 없기 때문입니다.
    대가
    채널을 가로지르는 조회는 조인이 필요합니다. scan_id 가 actual 과 artifact 를 잇습니다.
    재검토
    정정(UPDATE)이 들어오는 채널이 생기면 그 표에는 압축을 걸지 않습니다 — 정정마다 세그먼트를 풀었다 담아야 합니다.

    ADR-03 · 멱등은 발신 키로, 전달은 at-least-once 로 한다

    배경
    MQTT 가 QoS 1 이고 Kafka 소비도 at-least-once 라 재전달은 예외가 아니라 정상 동작입니다.
    결정
    (idempotency_key, time) 유니크 인덱스 + ON CONFLICT DO NOTHING. DB 커밋이 끝난 뒤에만 Kafka 오프셋을 커밋합니다.
    대가
    인덱스가 하나 더 늘고, 하이퍼테이블 제약상 파티션 컬럼(time)을 키에 포함해야 합니다. 같은 키가 다른 occurred_at 으로 오면 걸러지지 않습니다.
    재검토
    발신 측이 멱등 키 형식을 바꾸면 세 채널의 빌더를 함께 고칩니다. artifact 는 지금도 소비자가 만들고 있습니다.

    8.6 10분 주기에서 깨지는 패널과 경보

    대시보드와 경보는 전부 1초 주기 흐름을 전제로 창 길이와 임계를 잡아 두었습니다. 실적 · 산출물이 10분 주기가 되면 관측 창보다 발행 주기가 길어져 그래프가 거짓말을 시작합니다. 아래는 지금 설정을 그대로 둘 때 무엇이 어떻게 보이는지와, 무엇으로 바꿔야 하는지입니다.

    패널 · 경보현재 식10분 주기에서 보이는 모습고칠 값
    채널별 수신 항목/초rate(lidar_ingest_items_total[1m])깨짐 actual · artifact 가 열 칸 중 아홉 칸에서 빈칸. 10분에 한 번 뾰족한 스파이크만 선다rate(...[15m])
    적재 행/초rate(lidar_ingest_rows_inserted_total[1m])깨짐 같은 이유. 채널 레이블로 쪼개 보면 더 심하다rate(...[15m])
    배치당 행 수 · 배치 시간rate(batch_rows_sum[1m]) / rate(batch_rows_count[1m])주의 버스트가 온 1분만 평균이 튀고 나머지는 status 평균으로 눌린다평균 대신 max_over_time 패널을 함께 둔다
    LidarIngestStalledsum(rate(messages_total[3m])) == 0 · for 3m못 잡음 status 하나만 살아 있어도 합이 0이 아니다 — 10분 채널만 죽으면 영원히 안 뜬다채널별로 쪼갠다. by (channel) + 채널마다 다른 for
    LidarKafkaLagHighsum(kafka_lag) > 200 · for 5m못 잡음 artifact 버스트는 4,200항목이지만 레코드로는 9개뿐이라 임계 근처에도 못 간다레코드 수가 아니라 지연 시간 기준으로 바꾼다
    LidarDataStalefleet_freshness_seconds > 120 · for 1m부분 status 채널만 본다. 실적 · 산출물이 끊겨도 이 경보는 조용하다채널별 신선도 지표를 새로 낸다(8.7)
    LidarIngestRejectsincrease(rejects_total[10m]) > 0경계 관측 창 10분과 발행 주기 10분이 정확히 겹쳐 버스트가 창을 걸치면 두 번 세거나 놓친다increase(...[15m])
    중복 스킵lidar_ingest_rows_duplicate_total급증 3.2.2 의 스냅샷 중복이 그대로 여기 찍힌다 — 하루 590만 건경보를 새로 건다. A안 적용 여부의 판정 지표가 된다
    연속 집계 1분 버킷 lidar_scan_1mtime_bucket(INTERVAL '1 minute', time)톱니 10분에 한 번만 값이 있어 버킷 열 개 중 아홉이 빈다. 선 그래프가 끊긴다10분 주기 두 채널은 10 minutes 버킷 집계를 따로 만든다

    관측 창은 발행 주기보다 길어야 합니다

    rate() 는 창 안에 점이 최소 둘 있어야 값을 냅니다. 10분 주기 채널에 1분 창을 걸면 점이 하나도 없는 창이 대부분이라 Prometheus 가 값을 내지 않고, 그래프는 장애와 구분되지 않는 빈칸이 됩니다. 경험칙은 창 = 발행 주기 × 1.5 이상 입니다 — 10분 주기면 15분입니다. 같은 이유로 increase() 창이 발행 주기와 정확히 같은 값인 것도 피해야 합니다.

    지연 분포와 압축비 측정
    -- 5.1 지연 분포 (최근 5분)
SELECT count(*) AS n,
       round(avg(extract(epoch FROM received_at - time))::numeric, 3) AS avg_s,
       round(percentile_cont(0.50) WITHIN GROUP (
             ORDER BY extract(epoch FROM received_at - time))::numeric, 3) AS p50,
       round(percentile_cont(0.99) WITHIN GROUP (
             ORDER BY extract(epoch FROM received_at - time))::numeric, 3) AS p99
FROM tsdb.lidar_status
WHERE received_at > now() - interval '5 minutes';

-- 5.3 압축비. 운영 표를 건드리지 않도록 사본에서 잰다.
-- 측정이 끝나면 DROP SCHEMA scratch CASCADE 로 지운다.
CREATE SCHEMA IF NOT EXISTS scratch;
CREATE TABLE scratch.t (LIKE tsdb.lidar_status INCLUDING DEFAULTS)
  WITH (tsdb.hypertable, tsdb.partition_column = 'time',
        tsdb.segmentby = 'tid', tsdb.orderby = 'time DESC');
INSERT INTO scratch.t SELECT * FROM tsdb.lidar_status;
SELECT compress_chunk(c) FROM show_chunks('scratch.t') c;

SELECT pg_size_pretty(sum(before_compression_total_bytes)) AS before,
       pg_size_pretty(sum(after_compression_total_bytes))  AS after,
       round(sum(before_compression_total_bytes)::numeric
           / sum(after_compression_total_bytes), 1)        AS ratio
FROM chunk_compression_stats('scratch.t');
