LiDAR 적재 경로 비교

2026-09-17 · src/lidar-compare · 실행 중 구성 기준

    Development Document

    같은 MQTT 입력을 두 경로로 적재하면 ISL 경로는 산출물의 65%를 합쳐 버립니다

    발행기 350대의 LiDAR 데이터를 A(ISL Engine → Kafka)와 B(MQTT 직결 서비스) 두 경로로 각자의 hot DB 에 넣고, 같은 적재 코드 · 같은 스키마 · 같은 대시보드로 나란히 봅니다. 이 문서는 지금 떠 있는 구성이 어떻게 동작하는지를 그림으로 설명합니다.

    A · isl-kafka B · mqtt-direct 입력 426 msg/s 실행 중 (2026-09-17 11:10~) C · isl-db 추가 (14:08~) · 115분 실측 ISL 은 Debug 빌드

    00범위와 전제

    무엇을 비교하고 무엇은 비교하지 않는지를 먼저 고정합니다. 차이가 어디서 오는지 헷갈리지 않게 하기 위해서입니다.

    이 문서가 설명하는 것

    • 두 경로가 메시지 한 건을 hot DB 까지 옮기는 단계와 실패 경로
    • 경로마다 메시지에 실리는 필드 (누가 어떤 값을 넣는가)
    • 10분 실측: 도달률 · 지연 · 경로 전용 자원
    • 세 경로(C 포함) 115분 실측 · Grafana 패널 값 · actual 누락 원인 (04-2)
    • 모니터링 구성과 실행 · 확인 절차

    다루지 않는 것

    • CDC 복제(embedded-cdc-tsdb) — 이번 비교 구성에는 띄우지 않았습니다
    • ISL 운영 빌드의 자원 사용량 — 지금 수치는 Debug 빌드 · 단일 PC 기준입니다
    • B 경로의 고가용성(서비스 다중화 · 공유 구독)

    비교를 공정하게 만든 장치

    두 적재 서비스는 같은 이미지 · 같은 ingest.py 입니다. 소스만 SOURCE=kafka / SOURCE=mqtt 로 다르고, 파싱 뒤의 행 만들기 · DB 쓰기 · 지표 이름은 같은 함수를 탑니다1. 두 hot DB 도 같은 이미지(TimescaleDB 2.29.2 · PG17), 같은 스키마 · 메모리 설정이고, 두 서비스 모두 1초에 한 트랜잭션으로 씁니다. 그래서 결과 차이는 경로의 차이입니다.

    01동작 시나리오

    두 경로의 차이가 드러나는 대표 상황 넷입니다. 아래 그림과 측정 절에서 이 ID 로 다시 가리킵니다.

    정상 흐름

    SC-01 · 장비 상태 한 건은 두 DB 에 모두 같은 장비 id 로 적재된다

    Given
    발행기가 ot/device/assembly/lidar/status 에 {"id":"LDR-GJ-A1B3-07","raw_payload":{...}} 를 QoS 1 로 보낸다
    When
    A 는 Agent → Engine → Provider → ot.lidar.status 를 거치고, B 는 EMQX 에서 바로 받는다
    Then
    두 DB 의 tsdb.lidar_status 에 tid = LDR-GJ-A1B3-07 행이 생긴다. A 는 Kafka 의 숫자 tid 를 lidar_tag_catalog 로 되돌려 얻고, B 는 메시지의 id 를 그대로 쓴다

    SC-02 · 서비스가 커밋 전에 죽어도 두 경로 모두 유실되지 않는다

    Given
    배치 하나를 DB 에 쓰는 중이다
    When
    적재 서비스 컨테이너가 재시작된다
    Then
    A 는 커밋 안 된 Kafka 오프셋부터, B 는 EMQX 가 세션에 보관한 미확인(PUBACK 전) 메시지부터 다시 받는다. 이미 들어간 행은 (idempotency_key, time) 유니크 인덱스가 거른다

    차이가 드러나는 흐름

    SC-03 · 한 스캔의 세그먼트 PCD 10건은 A 에서 한두 건으로 합쳐진다

    Given
    장비 하나가 1분마다 산출물 12건(정합 PCD 1 · 변환행렬 1 · 세그먼트 10)을 연달아 보낸다. 세그먼트 10건은 모두 같은 id(LDR-…-SEGMENTED_PCD) · 같은 토픽이라 ISL 에서는 같은 태그다
    When
    Provider 가 태그마다 최신값 하나를 들고 있다가 전송 주기에 내보낸다
    Then
    A 의 artifact 는 분당 약 1,480행(기대 4,200 · 35.2%), B 는 4,200행 그대로다

    SC-04 · 등록되지 않은 태그는 A 에서만 사라진다

    Given
    ISL 모니터링 등록부에 없는 id 가 같은 토픽으로 들어온다
    When
    Agent 가 모니터링 태그(2,380개)로 거른다
    Then
    A 에는 적재되지 않는다. B 는 토픽 구독만 맞으면 적재한다 — 새 장비를 붙일 때 A 는 태그 등록 · 카탈로그 재생성이 먼저다
