    필드 데이터 TSDB 기술 검토 — 장비 상태 · 실적 결과 · PCD 메타

    필드 인터페이스 정의서의 세 데이터 등급을 ISL MQTT Agent → ISL Engine → hotdata provider → Hot DB 경로로 받아 PostgreSQL + TimescaleDB 에 1개월 보관하는 구성을 정의합니다. 세 등급은 주기도 크기도 성격도 달라 같은 정책으로 묶으면 셋 다 손해이므로, 등급별로 테이블 · 압축 · 보존을 나누어 정하고 무엇을 어떤 순서로 만들어 어떤 수치로 완료를 판정할지까지 적습니다.

    백엔드 1명 · DBA 0.5명 예상 7일 PostgreSQL 17 + TimescaleDB 2.29.2 규모 파라미터 미확정 보존 요건 해석 미확정

    00범위와 전제

    TimescaleDB 는 설치하면 빨라지는 물건이 아니라, 등급마다 청크 크기와 압축 시점과 보존 기간을 정하는 일입니다. 그 값을 정하는 것이 이 검토의 실체입니다.

    • Hot DB 인스턴스 확보와 TimescaleDB 확장 · 파라미터 확정

    전제 · "최대 1개월" 이 필요 하한인지 보관 상한인지가 설계를 가릅니다

    필요 하한(최소 1개월은 조회할 수 있어야 한다)이면 연속 집계는 1개월보다 길게 둘 수 있고, 보존 잡이 하류 동기화를 기다리며 늦게 지우는 것도 허용됩니다.
    보관 상한(1개월이 넘은 데이터를 이 DB 에 두면 안 된다)이면 반대입니다. 집계 테이블도 31일을 넘길 수 없고, 동기화가 밀렸다는 이유로 삭제를 미루는 04절 ADR-03 이 규정 위반이 되므로 그때는 "삭제하되 미동기 구간을 별도 파일로 덤프" 로 설계가 바뀝니다. 이 문서는 필요 하한으로 가정하고 썼습니다. S1 에서 현업 · 보안과 확정하십시오.

    전제 · 에디션 선택이 3~05절 전체를 좌우합니다

    컬럼스토어(하이퍼코어) 압축, 연속 집계, 보존 · 압축 정책은 TimescaleDB Community Edition(TSL) 기능입니다. Apache 2 에디션(-oss 태그 이미지)에는 하이퍼테이블만 있고 이 문서의 압축 · 집계 구성이 전부 동작하지 않습니다13. 서비스형으로 재판매하지 않는 사내 사용은 TSL 로 무상 사용이 가능하므로 -oss 가 아닌 태그를 씁니다. S1 에서 법무 확인과 함께 이미지 태그를 고정합니다.

    01필드 인터페이스 — 무엇이 오는가

    테이블을 먼저 그리면 반드시 틀립니다. 어떤 설비가 어떤 값을 어떤 단위로 어떤 주기에 보내는지가 정해져야 상하한 검증도, 태그 마스터도, 집계 방식도 정해집니다. 이 절이 equip_tag 마스터의 원본입니다.

    품질 코드와 값 타입 규약

    같은 value DOUBLE PRECISION 컬럼에 다섯 가지 성격의 값이 들어옵니다. 타입을 모르고 집계하면 숫자는 나오는데 의미가 없습니다 — 이 두 표가 없으면 대시보드가 조용히 거짓말을 합니다.

    quality의미집계 처리
    0정상avg · min · max 에 포함
    1센서 이상 (레인지 밖 · 단선)제외. bad_cnt 로만 셈
    2보정값 (캘리브레이션 적용)제외. 원값이 아니다
    3통신 두절 중 홀드값제외. 아래 경고 참고

    quality = 3 을 Agent 가 반드시 찍어야 합니다

    MODBUS 폴링 Agent 는 응답이 없을 때 마지막 값을 그대로 반복 송신하는 구현이 흔합니다. 그 값이 quality=0 으로 들어오면 설비가 멎었는데도 대시보드는 평온한 직선을 그립니다. 값이 없는 것보다 나쁜 상태입니다 — 데이터가 없으면 이상하다고 느끼지만, 있으면 아무도 의심하지 않습니다.
    값 타입저장집계에서 읽는 법
    아날로그doubleavg · min · max 전부 유효
    디지털double 0/1avg = 가동률. min · max 는 의미가 얕다
    카운터double 누적avg 금지. 구간 증분 = max − min. 리셋 구간은 음수가 되므로 걸러야 한다
    비트필드double 정수산술 집계 금지. last_value 만 읽는다. 253 까지는 정밀도 손실이 없다
    열거double 정수산술 집계 금지. last_value 또는 값별 건수로 본다

    그래서 1분 집계에 last_value 를 넣습니다

    avg · min · max 만 있으면 비트필드 · 열거 태그는 집계 테이블에서 읽을 방법이 없어 대시보드가 원본 하이퍼테이블을 직접 훑게 됩니다. 그러면 04절 ADR-02 의 "조회는 연속 집계만" 전제가 무너집니다. value_type 은 equip_tag 에 두고, 해석은 조회 계층이 담당합니다.

    D3 · PCD 원본 메타 — LiDAR Controller 송신 필드

    03목표 구조

    박스를 끌어 배치를 바꿀 수 있습니다. 구조가 바뀌면 JSON 버튼으로 내보내 이 파일의 dgm-data 블록에 붙여넣습니다.

    전체 흐름 한눈에 — 세 등급이 어디서 갈라지는가

    필드에서 나온 세 가지가 같은 경로로 들어와 hotdata provider 에서 갈라집니다. 갈라진 뒤로는 테이블도 정책도 서로 다르므로, 이 그림 한 장이 04절 ADR-01 의 요약입니다.

    이 세 줄이 서로 다른 이유

    D1 은 초당 1,440행이 들어오고 값이 바뀌지 않습니다 — 그래서 압축이 이득이고 DO NOTHING 이 맞습니다.
    D2 는 하루 11.5만 행뿐인데 실적 정정이 들어옵니다 — 압축을 걸면 정정 한 건마다 세그먼트를 풀었다 담아야 해서, 아끼는 44MB 보다 비용이 큽니다. 그래서 DO UPDATE 이고 압축이 없습니다.
    D3 는 하루 864행이지만 본체가 DB 밖(NAS)에 있습니다 — 시간만 보고 지우는 drop_chunks 를 쓰면 파일과 카탈로그가 어긋나므로, 하이퍼테이블조차 쓰지 않습니다.
    같은 정책으로 셋을 묶으면 D2 는 정정 때마다 느려지고, D3 는 NAS 에 주인 없는 파일이 일 52GB 씩 쌓입니다.

    컴포넌트 구성

    이 그림에서 읽어야 하는 것

    Hot DB 는 원본 보관소가 아닙니다. 31일이 지나면 지워지므로, 그 구간의 유일본은 SAP HANA 쪽에 있어야 합니다. 그래서 보존 · 동기 잡 이 한 상자에 묶여 있습니다 — 지우는 일과 넘기는 일이 서로를 모르면 넘기기 전에 지우는 사고가 납니다(04절 ADR-03).
    점선 고아 파일 대조 도 같은 이유입니다. D3 의 본체는 NAS 에 있고 DB 에는 카탈로그만 있으므로, 둘 중 한쪽만 지워지면 주인 없는 파일 이나 없는 파일을 가리키는 행 이 남습니다.

    한 배치가 지나는 순서

    이 그림에서 가장 비싼 경로는 recomp 입니다. 컬럼스토어로 전환된 청크에 뒤늦은 행이 들어오면 해당 세그먼트를 풀었다가 다시 담아야 하고, 삽입된 행이 자동으로 재압축되지도 않습니다7. 그래서 압축 전환 기준을 지연 도착 상한보다 앞당기면 안 됩니다. 지연 상한 24시간에 하루를 더해 전환 기준을 2일로 잡은 것이 ADR-02 입니다.

    시계 오차 검사를 별도 단계로 둔 이유

    엣지 PC 의 NTP 가 끊겨 계측 시각이 미래로 튀면, TimescaleDB 는 아무 불평 없이 미래 청크를 만들어 둡니다. 그 청크는 압축 정책(2일)도 보존 정책(31일)도 한참 뒤에나 건드리므로 조용히 남아 있고, 연속 집계는 존재하지 않는 시간대의 버킷을 갖게 됩니다. 기동 실패로 드러나지 않으므로 수신 단계에서 막아야 합니다.

    적재된 한 행의 31일

    앞의 두 그림은 공간(무엇이 무엇과 연결되는가)이고, 이것은 시간입니다. 04절과 05절에 흩어져 있는 정책 숫자들 — 2분 · 24시간 · 2일 · 31일 — 이 실제로 한 행에 어떤 순서로 적용되는지를 한 줄로 폅니다. D1 장비 상태 한 행 기준입니다.

    1
    T+0초 · 적재
    계측 시각이 속한 6시간 청크의 로우스토어에 들어간다. UNIQUE (tag_id, time) 로 QoS 1 재전송이 여기서 걸린다(SC-07)
    2
    T+2분 · 집계 확정
    end_offset 2분 이 지나 그 버킷이 equip_status_1m 에 확정된다. 1시간 뒤 _1h 로 다시 말린다. 대시보드는 이 두 표만 본다
    3
    T+24시간 · 지연 도착 마감
    엣지 로컬 버퍼 상한. 여기까지는 늦게 와도 원래 청크에 그냥 들어간다(SC-04). 이 선을 넘겨 오는 값이 5번을 비싸게 만든다
    4
    T+2일 · 컬럼스토어 전환
    청크가 열 지향으로 재배치되어 디스크가 10분의 1이 된다. 이후 이 청크로 오는 행은 감압 · 재삽입을 유발해 야간 재압축 큐로 간다
    5
    T+n일 · 하류 동기화
    SAP HANA 가 이 구간을 받으면 hotdata_sync_watermark 가 전진한다. 이 단계가 6번의 전제 조건이다. 지연 7일에 warning, 14일에 critical
    6
    T+31일 · 삭제
    cutoff = LEAST(now−31일, 워터마크). 5번이 뒤처져 있으면 지우지 않고 blocked_seconds 를 남긴다(SC-06)

    이 타임라인에서 순서가 뒤집히면 안 되는 두 곳

    3번 < 4번 — 지연 도착 마감(24시간)이 컬럼스토어 전환(2일)보다 먼저 와야 합니다. 뒤집히면 정상적인 지연 데이터가 매번 압축 청크를 때립니다. 엣지 버퍼가 커지면 4번을 함께 미뤄야 하는 이유입니다.
    5번 < 6번 — 동기화가 삭제보다 먼저 와야 합니다. 뒤집히면 그 구간은 어디에도 남지 않습니다. 이것만은 정책으로 표현할 수 없어 자체 잡으로 만들었습니다(ADR-03). 나머지 순서는 어긋나도 느려질 뿐이지만, 이 둘은 데이터가 사라지거나 깨집니다.

    04구현 방식 비교와 선택

    "왜 TimescaleDB 인가"에 답이 없으면 반년 뒤 같은 논의를 다시 합니다. 탈락안도 이유와 함께 남깁니다.

    방식장점단점적합도
    A. 단일 테이블 + DELETE 보존
    지금 가장 흔한 모양    		 구현이 없다시피 하고 운영 체계 그대로 일 1.24억 행을 DELETE 로 지우면 autovacuum 이 못 따라가 테이블이 계속 부풀고, 31일치 인덱스가 메모리를 벗어난다 탈락
    B. 선언적 파티셔닝 + pg_partman
    확장 없이 가는 길    		 보존은 DROP PARTITION 으로 해결. 확장 추가 없음 압축이 없어 31일에 231GB, 롤업 뷰와 파티션 생성 · 삭제를 전부 직접 구현 보류
    C. PostgreSQL + TimescaleDB
    선택안 · Community Edition    		 같은 SQL · 같은 드라이버 · 같은 백업. 압축 · 집계 · 보존이 정책 3줄. 설비 · 블록 마스터와 조인 가능 확장 버전과 PostgreSQL 메이저 업그레이드가 서로 묶임, TSL 라이선스 확인 필요 채택
    D. 전용 시계열 DB
    InfluxDB · ClickHouse    		 압축률과 대량 집계 성능 우위 설비 · 블록 마스터 조인 불가. D2 의 정정 UPDATE 와 D3 의 카탈로그 성격에 맞지 않아 어차피 PostgreSQL 을 하나 더 둬야 한다 탈락

    1개월 보존에서는 압축보다 drop_chunks 가 더 큰 이득입니다. A 안이 탈락하는 결정적 이유가 압축이 아니라 삭제 방식이라는 점을 놓치면 "1개월밖에 안 쌓이는데 TimescaleDB 까지 필요한가" 라는 질문에 답을 못 합니다. 일 1.24억 행을 DELETE 로 지우면 죽은 튜플이 그만큼 생기고, 그 회수를 autovacuum 이 실시간 적재와 경쟁하며 해야 합니다. 청크 삭제는 DROP TABLE 이라 회수 비용이 0 입니다.

    ADR-01 · 세 등급을 한 테이블에 합치지 않고 등급별로 테이블과 정책을 나눈다

    배경
    세 등급은 행 수가 5자리 차이(1.24억 : 11.5만 : 864)이고, D1 은 append-only, D2 는 정정 UPDATE 가 있으며, D3 는 본체가 NAS 에 있는 카탈로그입니다. 하나로 묶으면 D2 의 UPDATE 가 D1 의 압축 청크를 때리고, D3 의 행이 파일과 무관하게 청크째 삭제됩니다.
    결정
    equip_status 는 하이퍼테이블 + 컬럼스토어 + 연속 집계, work_result 는 하이퍼테이블이되 압축을 걸지 않고 보존만, pcd_scan_meta 는 일반 테이블 + 파일 정합 기반 삭제로 둡니다.
    대가
    보존 정책이 세 곳에 흩어져 각각 감시해야 합니다. 잡별 마지막 성공 시각을 하나의 Grafana 패널에 모아 이를 상쇄합니다.
    재검토
    D2 의 일 적재가 500만 행을 넘거나 D3 가 일 10만 행을 넘으면 각각 압축 · 하이퍼테이블 전환을 다시 검토합니다.

    D3 를 하이퍼테이블로 만들지 않는 세 가지 이유

    1. 월 26,784행 · 18MB 입니다. 청크 프루닝과 압축의 이득이 관리 비용보다 작습니다.
    2. 삭제 순서가 파일 먼저, 행 나중이어야 합니다. drop_chunks 는 조건을 못 걸고 시간만 보고 지우므로 이 순서를 표현할 수 없습니다.
    3. PCD 학습 서비스가 scan_id 를 외래키로 참조할 여지가 있습니다. 하이퍼테이블을 참조당하는 쪽으로 두는 것은 제약이 있어 일반 테이블이 안전합니다 확인 필요 — 06절 스파이크 Q3 에서 확정합니다.

    청크 인터벌을 6시간으로 정한 근거

    공식 기준은 "현재 적재 중인 청크의 인덱스가 shared_buffers 의 25% 안에 들어올 것"입니다10. 호스트 메모리 32GB · shared_buffers = 8GB 를 전제하면 한도는 2,048MB 이고, (tag_id, time DESC) 인덱스는 행당 약 36B(키 12B + 아이템 포인터 · 페이지 여유)로 잡습니다.

    보존이 1개월뿐이면 전환 시점이 더 중요해진다

    같은 방식으로 90일 보존을 전제한 센서 저장소 문서는 전환을 8일로 잡았습니다1 — 그러면 전체의 91% 가 압축 상태입니다. 그런데 31일 보존에서는 8일이 전체의 26% 이므로 전환을 미룰수록 손해가 훨씬 빨리 커집니다. 압축률은 데이터 형태에 따라 크게 달라지므로 여기서는 보수적으로 90% 를 씁니다 추정.

    ADR-02 · 청크 6시간 · 컬럼스토어 전환 2일 · 보존 31일 롤링

    배경
    세 값은 서로 묶여 있습니다. 청크가 크면 인덱스가 메모리를 넘고, 전환이 이르면 지연 데이터가 압축 청크를 때리고, 보존이 길면 디스크가 모자랍니다.
    결정
    D1 청크 인터벌 6시간(하루 4청크), 컬럼스토어 전환 2일(지연 상한 24시간 + 1일), 원본 보존 31일. D2 는 청크 1일 · 압축 없음 · 보존 31일. 연속 집계는 1분 31일 · 1시간 31일.
    대가
    하루 4개씩 31일이면 D1 청크가 124개입니다. 전 구간을 훑는 쿼리는 청크 수만큼 계획 부담이 늘므로, 대시보드 조회는 반드시 연속 집계를 보게 합니다. 또 전환이 2일로 이르므로 지연 상한이 24시간을 넘는 순간 재압축 비용이 바로 발생합니다.
    재검토
    평균 적재율이 2,900행/초를 넘거나(그 지점에서 6시간 청크 인덱스가 한도 2,048MB 에 닿습니다) shared_buffers 가 바뀌면 청크 인터벌을 다시 산출합니다. Agent 로컬 버퍼가 24시간보다 커지면 전환 기준을 함께 미룹니다.

    단건 적재로는 피크를 받지 못한다

    같은 사내 환경에서 이미 측정된 값이 있습니다. 기존 CDC PoC 의 target 적재 경로(이벤트당 한 문장 UPSERT)는 배치를 키울수록 처리량이 올라가다 약 8,200 events/s 에서 수렴했습니다4. D1 피크 요구 5,760행/초는 그 상한의 70% 입니다.

    여유가 30% 뿐이고, 그 8,200/s 는 다른 부하가 전혀 없을 때의 값입니다. 같은 인스턴스에서 압축 잡 · 연속 집계 잡 · 동기화 읽기가 함께 돌면 그만큼 깎입니다. 같은 실측에서 UPDATE 10만 건은 감사 쓰기가 붙자 2,872/s 로 절반 아래까지 떨어졌습니다4 — 부가 작업 하나가 처리량을 절반으로 만든다는 것이 이 실측의 핵심입니다. 그래서 hotdata provider 의 적용 경로는 처음부터 CopyManager 배치로 만듭니다. 단건 INSERT 로 만들어 두고 나중에 바꾸는 것은 재작성입니다.

    ADR-03 · 보존 삭제는 하류 보관소가 받았음을 확인한 뒤에만 실행한다

    배경
    Hot DB 는 31일치만 갖습니다. 그 구간이 SAP HANA 로 넘어가기 전에 삭제되면 그 데이터는 어디에도 없습니다. D3 도 같습니다 — NAS 파일보다 카탈로그 행을 먼저 지우면 파일이 무엇인지 아는 사람이 사라지고, 반대면 없는 파일을 가리키는 행이 남습니다. TimescaleDB 의 add_retention_policy 는 시간 조건만 받으므로9 이 조건을 표현할 수 없습니다.
    결정
    보존 정책을 등록하지 않고, hotdata_sync_watermark 를 읽어 cutoff = LEAST(now() − 31일, 워터마크) 로 drop_chunks 를 호출하는 자체 잡을 add_job 으로 등록합니다. D3 는 NAS 파일 삭제 확인(file_state=2) 이후에만 행을 지웁니다.
    대가
    동기화가 밀리면 디스크가 계속 늘어납니다. 250GB 볼륨에서 정상 46GB 를 빼면 여유 200GB, 일 7.46GB 증가 기준 약 26일 버팁니다. 그래서 동기화 지연 7일에 warning 경보를 걸어 19일의 대응 시간을 남깁니다.
    재검토
    00절 전제가 "보관 상한" 으로 확정되면 이 ADR 은 폐기하고, 미동기 구간을 삭제 전에 파일로 덤프하는 설계로 바꿉니다.

    01-schema.sql — 등급별 테이블

    init/01-schema.sql
    -- 확장은 데이터베이스마다 한 번. shared_preload_libraries 에 timescaledb 가
-- 올라가 있지 않으면 이 줄에서 바로 실패한다(08절 "자주 나는 오류" 참고).
CREATE EXTENSION IF NOT EXISTS timescaledb;

-- ── D1 장비 상태 ────────────────────────────────────────────────
-- 태그 메타. 일반 테이블이다 — 행이 1,440개뿐이고 시계열이 아니다.
CREATE TABLE equip_tag (
    tag_id      INT  PRIMARY KEY,
    area_code   TEXT NOT NULL,         -- MCH 가공 · ASM 조립 · OUT 의장 · PNT 도장
    equip_type  TEXT NOT NULL,         -- GHT 가스히터 · DHM 제습기 · PLC · ASM · OUT
    equip_code  TEXT NOT NULL,
    tag_name    TEXT NOT NULL,         -- 01절 카탈로그의 이름. 존 · 축은 .z2 로 전개
    value_type  TEXT NOT NULL,         -- ANALOG · DIGITAL · COUNTER · BITFIELD · ENUM
                                       -- 이 값 없이 집계를 읽으면 카운터 평균 같은 무의미한 수가 나온다.
    unit        TEXT NOT NULL,
    min_value   DOUBLE PRECISION,      -- 상하한 검증에 쓴다(03절 valid 단계)
    max_value   DOUBLE PRECISION,
    sample_period_ms INT NOT NULL DEFAULT 1000,
    UNIQUE (equip_code, tag_name)      -- 미등록 태그 거부의 근거(01절 전송 규약)
);

-- 원본 계측값. 2.20.0 부터는 CREATE TABLE 한 문장으로 하이퍼테이블이 된다.
-- 그 이전 버전이면 일반 테이블을 만든 뒤 create_hypertable() 로 변환한다.
CREATE TABLE equip_status (
    time        TIMESTAMPTZ      NOT NULL,   -- 계측 시각(엣지가 찍은 값). UTC 로만 저장
    tag_id      INT              NOT NULL REFERENCES equip_tag(tag_id),
    value       DOUBLE PRECISION NOT NULL,
    quality     SMALLINT         NOT NULL DEFAULT 0,
                                              -- 0=정상 1=센서이상 2=보정값 3=통신두절 홀드값
                                              -- 3 을 Agent 가 안 찍으면 멎은 설비가 직선으로 보인다(01절).
    ingested_at TIMESTAMPTZ      NOT NULL DEFAULT now()
                                              -- provider 커밋 시각. time 과의 차이가 곧 수집 지연이라
                                              -- 이 컬럼 없이는 SC-01 의 p99 를 사후에 계산할 수 없다.
) WITH (
    tsdb.hypertable,
    tsdb.partition_column = 'time',
    tsdb.chunk_interval = '6 hours',   -- 04절 산출 근거
    tsdb.segmentby = 'tag_id',                -- 압축 시 태그별로 묶는다
    tsdb.orderby   = 'time DESC'
);

-- 멱등 적재의 근거. 하이퍼테이블의 유니크 인덱스는 파티셔닝 컬럼(time)을
-- 반드시 포함해야 한다. tag_id 단독 유니크는 생성 자체가 거부된다.
CREATE UNIQUE INDEX equip_status_uq ON equip_status (tag_id, time);

-- ── D2 실적 결과 ────────────────────────────────────────────────
-- 하이퍼테이블이되 압축은 걸지 않는다. 사후 정정 UPDATE 가 있기 때문이다(ADR-01).
CREATE TABLE work_result (
    time        TIMESTAMPTZ NOT NULL,   -- 실적 발생 시각
    area_code   TEXT        NOT NULL,
    block_no    TEXT        NOT NULL,   -- 블록 · 부재 식별자
    result_seq  INT         NOT NULL,   -- 판별 서비스가 부여한 회차
    judge_code  SMALLINT    NOT NULL,   -- 0=미판정 1=양품 2=재작업 3=보류
    qty         NUMERIC(12,3),          -- 수량은 정산에 쓰이므로 numeric
    detail      JSONB,
    ingested_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at  TIMESTAMPTZ             -- 정정이 들어왔을 때만 채워진다(SC-02)
) WITH (
    tsdb.hypertable,
    tsdb.partition_column = 'time',
    tsdb.chunk_interval = '1 day'       -- 일 11.5만 행. 6시간으로 쪼갤 이유가 없다
);
CREATE UNIQUE INDEX work_result_uq
    ON work_result (area_code, block_no, result_seq, time);

-- ── D3 PCD 원본 메타 ────────────────────────────────────────────
-- 일반 테이블이다. 월 26,784행이고, 삭제 순서가 NAS 파일에 묶여 있어
-- 시간만 보고 지우는 drop_chunks 로는 표현할 수 없다(ADR-01 · ADR-03).
CREATE TABLE pcd_scan_meta (
    scan_id      UUID        PRIMARY KEY,
    scanned_at   TIMESTAMPTZ NOT NULL,
    station_code TEXT        NOT NULL,
    area_code    TEXT        NOT NULL,
    block_no     TEXT,
    nas_path     TEXT        NOT NULL,   -- \\nas01\pcd\2026\09\ST3-0908-0210.pcd
    file_format  TEXT        NOT NULL,   -- pcd · las · ply
    file_bytes   BIGINT      NOT NULL,   -- 정합 대조 1차 키
    checksum     TEXT        NOT NULL,   -- sha256. 정합 대조 2차 키
    point_count  BIGINT,
    resolution_mm NUMERIC(6,2),
    bbox         JSONB,
    scanner_model TEXT,                  -- 학습 서비스가 도메인을 나눌 때 쓴다
    calib_ref    TEXT,
    file_state   SMALLINT    NOT NULL DEFAULT 0,
                                          -- 0=메타만 등록 1=파일 확인됨 2=NAS 삭제 확인됨
                                          -- 행 삭제는 2 인 것만 대상으로 한다.
    ingested_at  TIMESTAMPTZ NOT NULL DEFAULT now()

CREATE UNIQUE INDEX pcd_scan_meta_path_uq ON pcd_scan_meta (nas_path);

CREATE TABLE field_reject (

    02-policies.sql — 압축과 연속 집계

    init/02-policies.sql
    -- 1) D1 컬럼스토어 전환: 2일이 지난 청크를 열 지향으로 재배치한다.
--    add_columnstore_policy 는 2.18.0 부터의 이름이다. 그 이전 버전 문서에서
--    보이는 add_compression_policy 와 같은 일을 한다.
CALL add_columnstore_policy('equip_status', after => INTERVAL '2 days');

-- 2) D2 에는 걸지 않는다. 실적 정정 UPDATE 가 압축 청크를 때리면
--    세그먼트를 풀었다 담는 비용이 매번 발생한다(ADR-01).
--    일 44MB 라 압축해서 아끼는 양보다 그 비용이 크다.

-- 3) 1분 집계. materialized_only = false 로 두면 아직 집계되지 않은
--    최근 구간을 원본에서 실시간으로 메워 조회한다.
CREATE MATERIALIZED VIEW equip_status_1m
WITH (timescaledb.continuous, timescaledb.materialized_only = false) AS
SELECT time_bucket(INTERVAL '1 minute', time) AS bucket,
       tag_id,
       avg(value)   FILTER (WHERE quality = 0) AS avg_value,
       min(value)   FILTER (WHERE quality = 0) AS min_value,
       max(value)   FILTER (WHERE quality = 0) AS max_value,
       last(value, time)                       AS last_value,
                   -- 비트필드 · 열거 태그는 avg 가 무의미하다. 이 컬럼이 없으면
                   -- 그 태그들 때문에 대시보드가 원본을 직접 훑게 된다(01절 값 타입 규약).
       count(*)                                AS sample_cnt,
       count(*)     FILTER (WHERE quality <> 0) AS bad_cnt
FROM equip_status
GROUP BY bucket, tag_id
WITH NO DATA;   -- 생성 시점에 31일치를 한 번에 계산하면 DB 가 멎는다

-- end_offset 2분: 아직 들어오는 중인 최근 2분은 건드리지 않는다.
-- start_offset 2시간: 그 이전 2시간은 매번 다시 계산해 지연 도착분을 반영한다.
-- 24시간짜리 버퍼 방출분은 이 창을 벗어나므로 S5 의 수동 refresh 경로로 처리한다.
SELECT add_continuous_aggregate_policy('equip_status_1m',
    start_offset      => INTERVAL '2 hours',
    end_offset        => INTERVAL '2 minutes',
    schedule_interval => INTERVAL '1 minute');

CREATE MATERIALIZED VIEW equip_status_1h

       tag_id,

    03-retention.sql — 이 구성에서 가장 중요한 파일

    일반적인 TimescaleDB 문서라면 여기가 add_retention_policy 한 줄입니다. Hot DB 가 31일치만 가진 유일본 구간을 품고 있기 때문에 그 한 줄로는 안 됩니다.

    init/03-retention.sql
    -- 보존 삭제는 두 조건의 AND 다.
--   (1) 31일이 지났다        — 요건
--   (2) 하류가 이미 받았다   — 안전장치 (ADR-03)
-- LEAST 로 둘 중 이른 시점을 잡으면 하나만 만족해도 지우는 일이 없다.
CREATE OR REPLACE PROCEDURE hotdata_retain(job_id INT, config JSONB)
LANGUAGE plpgsql AS $$
DECLARE
    keep   INTERVAL    := COALESCE((config->>'keep')::INTERVAL, INTERVAL '31 days');
    tbl    TEXT        := COALESCE(config->>'table', 'equip_status');
    grd    TEXT        := COALESCE(config->>'grade', 'D1');
    wm     TIMESTAMPTZ;
    cutoff TIMESTAMPTZ;
BEGIN
    SELECT synced_upto INTO wm
      FROM hotdata_sync_watermark WHERE grade = grd;

    -- 워터마크가 없으면 아무것도 지우지 않는다. 여기서 조용히 넘어가면
    -- 동기화가 한 번도 안 돈 상태에서 31일치를 통째로 날린다.
    IF wm IS NULL THEN
        RAISE EXCEPTION 'sync watermark for % is missing - retention aborted', grd;
    END IF;

    cutoff := LEAST(now() - keep, wm);
    PERFORM drop_chunks(tbl, older_than => cutoff);

    -- 워터마크가 발목을 잡은 경우를 지표로 남긴다. 이 값이 0 보다 크면
    -- 디스크가 계속 늘고 있다는 뜻이고, 26일 뒤에는 볼륨이 찬다.
    INSERT INTO hotdata_retention_log (grade, cutoff, blocked_seconds)
    VALUES (grd, cutoff,
            GREATEST(0, EXTRACT(EPOCH FROM ((now() - keep) - wm))::BIGINT));
END;
$$;

CREATE TABLE hotdata_retention_log (
    id              BIGSERIAL   PRIMARY KEY,
    ran_at          TIMESTAMPTZ NOT NULL DEFAULT now(),
    grade           TEXT        NOT NULL,
    cutoff          TIMESTAMPTZ NOT NULL,
    blocked_seconds BIGINT      NOT NULL
);

-- 정책이 아니라 잡으로 등록한다. 실패하면 timescaledb_information.job_errors
-- 에 남고, 그 표를 그대로 경보에 태운다(S7).
SELECT add_job('hotdata_retain', INTERVAL '1 hour',
                config => '{"table":"equip_status","grade":"D1","keep":"31 days"}');
SELECT add_job('hotdata_retain', INTERVAL '1 hour',
                config => '{"table":"work_result","grade":"D2","keep":"31 days"}');

-- D3 는 청크가 아니라 행 단위다. NAS 삭제가 확인된(file_state=2) 것만 지운다.
CREATE OR REPLACE PROCEDURE pcd_meta_retain(job_id INT, config JSONB)
LANGUAGE plpgsql AS $$
BEGIN
    DELETE FROM pcd_scan_meta
     WHERE scanned_at < now() - INTERVAL '31 days'
       AND file_state = 2;
END;
$$;
SELECT add_job('pcd_meta_retain', INTERVAL '1 day');

class RetentionWatermarkTest {

    // 일반 postgres 이미지로는 CREATE EXTENSION 이 실패한다.
    @Container
    static final PostgreSQLContainer<?> DB = new PostgreSQLContainer<>(

    // SC-06: 동기화가 밀린 구간은 31일이 지나도 삭제하지 않는다.
    // 이 테스트가 없으면 "정상적으로 삭제된" 사고를 아무도 못 잡는다.
    void retention_doesNotDropChunksBeyondSyncWatermark() {
        var now = OffsetDateTime.parse("2026-10-18T00:00:00Z");
        seedOnePerHour(now.minusDays(40), now);          // 40일치
        watermark.set("D1", now.minusDays(35));      // HANA 는 35일 전까지만 받았다

        retentionJob.run(Clock.fixed(now.toInstant(), UTC));  // keep = 31일

        // 31일 기준이면 9일치를 지워야 하지만, 워터마크가 막아 5일치만 지운다.
        assertThat(oldestChunkStart())
                .isAfterOrEqualTo(now.minusDays(35).toInstant());

                .isEqualTo(Duration.ofDays(4).toSeconds());   // 35 - 31

        watermark.delete("D1");
        assertThatThrownBy(() -> retentionJob.run(fixedClock()))
                .hasMessageContaining("watermark for D1 is missing");
        assertThat(chunkCount()).isEqualTo(chunkCountBefore);
    }
