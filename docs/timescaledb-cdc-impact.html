source DB TimescaleDB 전환 영향 분석

v0.1 · 2026-09-07 · CDC PoC

    Impact Analysis

    source DB를 TimescaleDB로 바꾸면 CDC 파이프라인은 어디가 깨지는가

    현재 CDC 원천은 postgres:16 이고, 센서 저장소 과제에서 같은 PostgreSQL 위에 TimescaleDB를 얹는 구성이 검토되고 있습니다. 이 문서는 그 변경이 기존 CDC 파이프라인에 미치는 영향을 확장만 설치하는 경우와 테이블을 하이퍼테이블로 전환하는 경우로 나눠 정리하고, 코드의 어느 줄이 왜 깨지는지와 무엇을 먼저 확인해야 하는지를 적습니다.

    분석 · 결정 대기 기준 커밋 75be7dc embedded-cdc · embedded-cdc-go · cdc-custom 확인 필요 3건

    00질문과 답

    질문은 한 줄인데 답은 두 갈래입니다. 갈림길은 "TimescaleDB를 설치하느냐"가 아니라 "기존 테이블을 하이퍼테이블로 만드느냐"입니다. 이 구분을 하지 않으면 영향 범위를 실제보다 훨씬 크게 보게 됩니다.

    A안 · 확장만 얹고 기존 테이블은 그대로

    car · computer · grade · member 를 일반 테이블로 두는 한 TimescaleDB는 그냥 설치된 확장일 뿐이고, logical decoding 경로에 아무 영향이 없습니다.

    인프라 3줄 변경으로 끝

    publication · slot · REPLICA IDENTITY · Debezium 설정 · 핸들러 · V1~V6 실측치가 전부 그대로 유효합니다.

    B안 · 실제로 하이퍼테이블로 전환

    파이프라인이 기대는 전제가 여러 개 동시에 깨집니다. 이름 매칭 · PK · 스냅샷 · 삭제의 의미 · 처리량이 전부 다시 정의되어야 합니다.

    치명 3건 · 주의 5건

    그중 두 건은 조용히 target 데이터를 지우거나 갈라지게 합니다. 기동 실패로 드러나지 않습니다.

    영향 지점 한눈에

    영향 지점A안 · 확장만B안 · 하이퍼테이블 전환
    컨테이너 이미지 · 파라미터변경변경 동일
    publication 정의그대로재설계 청크가 주기마다 새로 생긴다
    이벤트의 테이블 이름그대로깨짐 청크명으로 도착해 전량 무시된다
    압축 · 보존 정책의 부작용해당 없음데이터 손상 대량 DELETE · 보이지 않는 삭제
    PK · REPLICA IDENTITY그대로재설계 복합키 + FULL 비용
    초기 스냅샷그대로불가 백필 경로 별도 설계
    처리량 목표그대로미달 실측 2,467 vs 피크 8,000/초
    V1~V6 검증 결과유효재측정 전제가 달라진다

    이 분석의 위치

    센서 저장소 구성 문서 00절은 이미 "기존 CDC 파이프라인 DB 변경 — 센서 저장소는 별도 인스턴스로 분리"를 범위 밖으로 못 박고 있습니다1. 아래 B안 목록은 그 결정을 뒤집자는 제안이 아니라, 그 결정의 근거이자 나중에 "센서 데이터도 CDC로 내보내자"는 요구가 왔을 때 꺼낼 목록입니다.

    01A안 · 확장만 얹는 경우 바뀌는 것

    여기서 바뀌는 것은 인프라 정의 파일 두 개뿐입니다. 애플리케이션 코드는 한 줄도 손대지 않습니다.

    위치변경
    docker-compose.source.yml:22postgres:16 → timescale/timescaledb:2.29.2-pg16

    docker-compose.source.yml:29-c shared_preload_libraries=timescaledb 추가
    빠지면 CREATE EXTENSION 이 그 자리에서 실패한다. wal_level=logical 과는 충돌하지 않는다

    source/init/01-schema.sql맨 위에 CREATE EXTENSION IF NOT EXISTS timescaledb; 한 줄

    A안에서 바뀌지 않는 것 — 이게 결론입니다

    CREATE PUBLICATION embedded_cdc_pub FOR TABLE car, computer, grade, member(01-schema.sql:75), 네 테이블의 REPLICA IDENTITY FULL(:33 · :62), replication slot, table-include-list(application.yml:49), snapshot-mode: initial(:50), SlotContinuityGuard, heartbeat 구성, 세 스택의 핸들러와 매퍼 — 전부 그대로입니다. V1~V6에서 측정한 지연 · 처리량 · 페일오버 결과도 재측정 없이 유효합니다.

    02B안 · 하이퍼테이블로 전환하면 깨지는 지점

    아래 8건은 독립된 문제가 아니라 대부분 "하이퍼테이블은 부모 테이블 + 청크의 상속 구조"라는 한 가지 사실에서 파생됩니다. 치명 3건은 기동 실패로 드러나지 않고 조용히 데이터를 어긋나게 합니다.

    B1논리 디코딩이 부모가 아니라 청크 이름으로 나온다치명
    무엇이
    WAL의 relation이 public.sensor_reading 이 아니라 _timescaledb_internal._hyper_1_1_chunk 로 옵니다. 하이퍼테이블은 선언적 파티셔닝이 아니라 상속 기반이라 publish_via_partition_root 로 우회할 수도 없습니다.
    연쇄 1 · publication
    FOR TABLE <하이퍼테이블> 로는 행이 나오지 않습니다. FOR ALL TABLES 로 가거나 청크를 계속 추가해야 하는데, 청크는 인터벌마다 새로 생깁니다(센서 문서 기준 6시간).
    연쇄 2 · 필터
    table-include-list(application.yml:49)의 정확한 목록이 _timescaledb_internal\._hyper_.* 정규식으로 바뀝니다.
    연쇄 3 · 디스패치
    SourceTable.fromName() 이 "car" 문자열 정확 일치입니다(SourceTable.java:34, 이름을 뽑는 곳은 DebeziumEventDeserializer.java:50). 청크명이 들어오면 매칭에 실패해 전 이벤트가 무시됩니다. Go 스택도 decoder.go:31 에서 같은 구조입니다.
    연쇄 4 · 두 정체성
    스냅샷(op=r)은 부모 이름으로, 스트리밍(op=c/u/d)은 청크 이름으로 옵니다. 같은 테이블이 두 이름으로 도착하므로 매핑 계층이 양쪽을 모두 받아야 합니다.
    대응
    청크명 → 논리 테이블명 역매핑 계층을 새로 만듭니다. _timescaledb_catalog.chunk · hypertable 조인으로 해석해 캐시하거나 청크명에서 하이퍼테이블 id를 추출합니다. 청크가 계속 생기므로 캐시 미스 경로가 반드시 필요합니다.
    B2압축(컬럼스토어) 전환이 대량 DELETE로 보인다치명
    무엇이
    청크 압축은 메타데이터 조작이 아니라 실제 DML입니다. 원본 행을 읽어 compress_hyper_* 에 넣고 원본 청크를 비웁니다.
    결과
    FOR ALL TABLES publication이면 이것이 청크 한 개 분량의 DELETE 이벤트로 흘러가 target을 지웁니다. 압축 테이블 쪽 INSERT는 배열 뭉치라 해석도 불가능합니다.
    왜 안 잡히나
    지금의 halt-on-dead-letter-ratio(기본 0.5)는 실패를 막는 장치입니다. 이 삭제들은 문법적으로 정상이라 성공적으로 적용되고, DLQ에도 남지 않고, 지표에도 이상으로 보이지 않습니다.
    대응
    _timescaledb_internal.compress_hyper_% 를 publication 또는 include-list에서 제외하고, 압축 잡이 만든 삭제를 식별해 거릅니다. 선택이 아니라 필수입니다.
    B3보존 정책(drop_chunks)은 CDC에 아예 보이지 않는다치명
    무엇이
    drop_chunks 는 DROP TABLE, 즉 DDL입니다. 행 삭제 이벤트가 하나도 생기지 않습니다.
    결과
    source는 90일치를 유지하는데 target은 무한히 쌓입니다. 시간이 갈수록 갈라지고, scripts/reconcile.sql 의 건수 대조는 상시 불일치가 됩니다 — 즉 대조 스크립트가 진짜 문제를 가려버립니다.
    대응
    target에 별도 보존 잡을 두거나, target도 하이퍼테이블로 만들어 같은 보존 정책을 겁니다. 어느 쪽이든 "source와 target이 같아야 한다"는 대조 기준을 "보존 창 안에서만 같다"로 다시 씁니다.
    B4연속 집계 갱신이 또 하나의 쓰기 소스가 된다주의
    무엇이
    연속 집계는 뷰가 아니라 _timescaledb_internal._materialized_hypertable_N 이라는 실제 하이퍼테이블이고, refresh마다 대량 INSERT/DELETE가 일어납니다.
    결과
    FOR ALL TABLES 면 집계 갱신 트래픽이 전부 CDC로 흘러갑니다. 파이프라인 부하가 적재량이 아니라 잡 스케줄에 따라 튑니다.
    대응
    materialization 하이퍼테이블도 제외 목록에 넣습니다. B2와 같은 목록이므로 함께 관리합니다.
    B5PK와 REPLICA IDENTITY 전제가 깨진다주의
    PK
    하이퍼테이블의 유니크 제약은 파티셔닝 컬럼을 포함해야 하므로9 PK가 (time, tag_id) 복합키가 됩니다. 지금은 네 매퍼가 전부 row.longValue("id") 단일 long PK를 전제하고 target UPSERT 키도 동일합니다. 복합키 지원이 새로 필요합니다.
    REPLICA IDENTITY
    지금 FULL을 건 이유는 소프트 삭제 판정에 before 전체 이미지가 필요해서입니다(01-schema.sql:29~34 주석). 시계열은 append-only라 그 요구가 없고, 초당 2,000행 규모에서 FULL은 UPDATE/DELETE의 WAL을 배로 불립니다.
    확인 필요
    하이퍼테이블에 건 REPLICA IDENTITY가 이후 생성되는 청크에 자동 상속되는지는 버전에 따라 다릅니다. 상속되지 않으면 새 청크마다 걸어줘야 합니다. 확인 필요
    대응
    시계열 테이블은 FULL을 쓰지 않고 DEFAULT + 복합 PK로 갑니다. "삭제 전 값"을 알아야 하는 요구가 따로 있으면 CDC가 아니라 원천 설계에서 풉니다.
    B6초기 스냅샷이 현실적으로 불가능하다주의
    무엇이
    snapshot-mode: initial(application.yml:50)이 90일 × 1.7억 행/일 = 약 155억 행을 SELECT로 훑습니다.
    연쇄
    never 또는 no_data + 별도 백필로 가야 하는데, 그러면 SlotContinuityGuard 가 전제하는 "슬롯 생성 시점부터 연속"과 백필 경계를 어떻게 잇는지를 새로 정의해야 합니다. 지금 로직대로면 fail-on-capture-gap: true(:54)에 걸려 기동을 거부합니다.
    대응
    백필 완료 LSN을 체크포인트 초기값으로 심는 경로를 만들고, 그 경로를 Guard가 정상으로 인정하도록 규칙을 명시합니다. Guard를 끄는 것은 답이 아닙니다 — 그러면 V3에서 잡았던 캡처 갭이 다시 조용해집니다.
    B7처리량이 모자란다주의
    수치
    실측 2,467 events/s(변경 감사를 켜면 1,654)인데 센서 피크는 8,000행/초입니다. 이벤트당 한 문장 UPSERT 구조로는 받지 못합니다.
    연쇄
    못 따라가면 슬롯 지연 → WAL 누적 → 원천 디스크 고갈입니다. compose 주석에 적어둔 위험("slot 은 만료되지 않는다")이 실제 시나리오가 됩니다.
    스택 차이
    Go 스택(go-pq-cdc)은 standby status update를 이벤트 전달과 같은 고루틴에서 보내는 구조라 적재가 밀리면 응답도 함께 멎습니다 — 이미 wal_sender_timeout 을 5min으로 올려 대응한 그 문제이고(실측 panic 9회), 이 부하에서 먼저 재발합니다.
    대응
    적용을 COPY 기반 배치로 바꿉니다. hibernate.jdbc.batch_size: 50 은 이미 설정되어 있지만 "이벤트당 한 문장이라 효과가 없다"고 주석에 적혀 있습니다 — 그 배치 적용을 실제로 넣는 일이 여기에 딸려옵니다.
    B8전환 작업 자체가 이벤트를 만든다주의
    무엇이
    기존 테이블을 create_hypertable(..., migrate_data => true) 로 바꾸면 부모 → 청크 행 이동이 DELETE + INSERT로 WAL에 나가 target에 그대로 재생됩니다.
    대응
    전환은 CDC를 멈추고 → 변환하고 → 슬롯과 오프셋을 재생성하는 순서로 합니다. 돌아가는 파이프라인 위에서 변환하지 않습니다.

    cdc-custom(트리거 · outbox) 스택은 다른가

    이름 문제(B1)는 겪지 않습니다. 트리거와 sync_outbox 는 사용자 테이블 수준에서 동작하기 때문입니다. 그러나 B3는 동일하게 발생합니다 — drop_chunks 는 DDL이라 트리거를 거치지 않고, outbox에 아무것도 남지 않습니다. 압축 역시 내부 경로라 사용자 트리거를 거치지 않을 가능성이 높습니다확인 필요. 즉 세 스택 중 어느 것도 B3를 그냥 넘기지 못합니다. 세 스택의 모니터링과 대조 기준을 같게 유지한다는 원칙상, 대응도 세 곳에 함께 들어가야 합니다.

    03B안에서 손대야 하는 코드

    "어디를 고쳐야 하나"를 파일 단위로 못 박아 둡니다. 아래가 B안의 실제 작업량입니다.

    매퍼 4종 · target 엔티티단일 long id PK복합키 지원, UPSERT 키 변경
    BatchApplier이벤트당 한 문장COPY 배치 적용
    SlotContinuityGuard슬롯 생성 시점부터 연속백필 경계를 정상으로 인정하는 규칙 추가
    scripts/reconcile.sqlsource · target 전량 건수 일치보존 창 기준 비교로 재정의

    B안은 "설정 몇 줄"이 아니라 매핑 계층 신설 + 적용 경로 재작성 + 대조 기준 재정의입니다. A안(인프라 3줄)과는 규모가 다릅니다.

    04먼저 확인해야 하는 3건

    위 목록 중 세 건은 버전과 이미지에 따라 답이 달라져 문서로 단정할 수 없습니다. B안을 검토하게 되면 반나절 스파이크로 이 셋부터 확정합니다. 결과에 따라 B1과 B2의 대응 난이도가 크게 달라집니다.

    Q1 · 하이퍼테이블을 publication에 넣으면 이후 생기는 청크가 자동 편입되는가

    Given
    쓰기로 정한 이미지 태그에서 ALTER PUBLICATION p ADD TABLE sensor_reading 을 실행한다
    When
    청크 경계를 넘겨 새 청크가 생성된 뒤 그 청크에 INSERT 한다
    Then
    pg_recvlogical 출력에 그 행이 나오는지 본다. 나오면 FOR ALL TABLES 를 피할 수 있고, B2 · B4의 제외 목록 관리 부담이 크게 줄어든다

    Q2 · 압축 잡이 실제로 DELETE 이벤트를 내보내는가

    Given
    행이 든 청크 하나에 FOR ALL TABLES publication을 걸어 둔다
    When
    그 청크를 컬럼스토어로 전환한다
    Then
    디코딩 출력에 DELETE가 몇 건 나오는지 센다. 0이 아니면 B2는 대응 없이는 진행 불가로 확정된다

    Q3 · 청크명 역매핑과 relation 증가의 비용은 얼마인가

    Given
    90일 · 6시간 인터벌이면 청크가 약 360개, 여기에 압축 청크가 더해진다
    When
    커넥터가 청크마다 relation 메시지를 받고 스키마 캐시를 유지한다
    Then
    커넥터 메모리와 새 청크 생성 시점의 지연 스파이크를 잰다. 청크 인터벌이 짧을수록 나빠지므로 센서 문서의 6시간 결정과 맞물린다

    진행 전 체크 0 / 0

    • A안과 B안 중 무엇을 묻고 있는지 먼저 합의"TimescaleDB로 바꾼다"는 말이 두 가지를 뜻한다. 여기서 갈리지 않으면 논의가 겉돈다
    • Q1~Q3 스파이크 실행쓰기로 정한 이미지 태그에서. 버전이 다르면 결과가 다르다
    • 센서 데이터를 CDC로 내보낼 요구가 실제로 있는지 확인없으면 B안 전체가 불필요하다. 있으면 별도 검증 과제로 세운다
    • 대조 기준(reconcile) 재정의 필요 여부 판단B3는 세 스택 모두에 해당한다
    • A안을 적용한다면 기준선 재측정 한 번코드 전제는 안 바뀌지만 이미지가 바뀐다. 기준선을 다시 찍어두는 편이 싸다

    05권고

    지금 결정할 수 있는 것과, 요구가 생겼을 때로 미룰 것을 나눕니다.

    ADR-01 · 센서 저장소는 CDC 원천과 별도 인스턴스로 둔다

    배경
    같은 인스턴스에 두면 2절의 B1~B8이 기존에 잘 돌던 파이프라인에까지 영향을 줍니다. 센서 적재의 WAL이 기존 슬롯을 통과하고, 압축 · 보존 잡의 부작용을 기존 파이프라인이 함께 떠안습니다.
    결정
    센서 저장소 문서 00절의 범위 결정을 유지합니다. 별도 인스턴스로 분리합니다.
    대가
    인스턴스가 하나 늘고, 설비 마스터와 CDC 대상 테이블을 조인하려면 애플리케이션 계층이나 FDW가 필요합니다.
    재검토
    센서 데이터를 다른 시스템으로 실시간 전파해야 하는 요구가 생기면 재검토합니다. 그때는 CDC가 아니라 적재 API에서 분기하는 쪽(dual write)이 더 싼지 함께 비교합니다.

    ADR-02 · car · computer · grade · member 는 하이퍼테이블로 만들지 않는다

    배경
    이 네 테이블은 시계열이 아닙니다. 행 수가 적고 시간축 조회가 없어 하이퍼테이블의 이득(압축 · 청크 프루닝)이 없습니다. 반면 2절의 비용은 전부 발생합니다.
    결정
    원천 인스턴스에 TimescaleDB 확장이 설치되더라도 이 네 테이블은 일반 테이블로 둡니다. 즉 A안 범위에서 멈춥니다.
    대가
    없습니다. 확장이 설치되어 있어도 하이퍼테이블을 만들지 않으면 비용이 발생하지 않습니다.
    재검토
    cdc_change_audit 같은 append-only 로그성 테이블이 커지면 그 테이블 하나만 하이퍼테이블로 만드는 것은 검토할 만합니다. 단 그것은 target 쪽 테이블이라 CDC 캡처 대상이 아니어서 2절이 적용되지 않습니다 — 이 구분이 재검토의 전제입니다.

    한 문장으로

    확장을 얹는 것은 인프라 3줄이고, 하이퍼테이블로 바꾸는 것은 파이프라인 재설계입니다. 현재 계획(센서 저장소 별도 인스턴스)대로라면 기존 CDC 파이프라인에 실질적 영향은 없습니다. 영향이 생기는 유일한 경로는 "센서 하이퍼테이블도 CDC로 내보내자"이며, 그건 별도 검증 과제로 세워야 할 크기입니다.
